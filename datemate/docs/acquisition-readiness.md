# 인수 실사 개선 상태 (2026-10-23)

## 이번 변경

- `/readyz`: SQLite 스키마 조회 성공 여부만 확인. 외부 API와 추천 정확성의 보증이 아님. 장애 시 503.
- `/api/*`: no-store 및 no-referrer 응답 헤더.
- `DELETE /api/me/data`: 현재 브라우저의 일정·대화·후기·피드백·의견·제보·세션 및 소유자 연결 초안 캐시 삭제. 다른 브라우저의 데이터는 삭제하지 않음.
- 화면 하단 데이터 삭제 버튼과 복구 불가 확인.
- `python scripts/backup_database.py backups/manual.sqlite`: SQLite backup API로 WAL 반영, 무결성 검사, 기존 파일 덮어쓰기 거부. 백업은 개인정보를 포함하므로 운영자가 접근을 제한해야 함.

## 검증 상태

회귀 테스트를 추가했지만 현재 편집 환경에는 Python 실행 명령이 없어 실행하지 못했다. 실행 환경에서 `python -m pytest tests/test_backup_database.py tests/test_privacy_controls.py -q`를 수행해야 한다. 기존 전체 테스트도 릴리스 전에 실행한다. 백업 복원 훈련은 별도로 필요하다.

## 해결되지 않은 우선 과제

1. 기존 일정 ID 공유는 별도 만료·철회 토큰 구조로 전환 필요. 협의·식당·대화 API 전체의 읽기 권한을 함께 점검해야 한다.
2. 삭제는 현재 브라우저 식별자 기준이다. 쿠키 분실 시 본인 확인·삭제 요청 절차, 백업 보관 및 삭제 주기, 외부 공급자 기록 정책이 필요하다. 자동 보관기간 삭제는 아직 구현하지 않았다.
3. 삭제와 동시에 진행 중인 요청이 데이터를 다시 기록할 수 있어 계정 폐쇄 상태와 쓰기 차단을 추가할 필요가 있다.
4. 실제 영업·가격·경로 검수: 날짜와 지역별 코스 표본을 독립 검수하고 실패 원인과 공급자별 신선도를 기록한다.
5. 데이터·사진·API별 상업 이용 및 양도 가능 권리 증빙을 확보한다. 코드 변경으로 계약을 대체하지 않는다.
6. 외부 API 비용·지연·실패율 계측과 공급자별 예산 제한을 추가한다.
7. 공유·방문·재사용률을 개인정보 최소 수집 원칙에 따라 측정한다. 코스 생성만으로 실제 방문이나 매출을 주장하지 않는다.

## 실사용 검증안

서울 일부 지역에서 동의한 참가자가 기존 계획 방법과 서비스를 각각 사용하게 한다. 계획 시간, 두 사람의 합의 여부, 실제 방문 실패, 다음 데이트 재사용, 추천당 변동비를 측정한다. 표본수와 성공 기준은 시작 전에 정하고 실패 사례도 포함한다. 인수가격·시장 적합성·수익성은 해당 결과와 실제 계약을 검토한 뒤 판단한다.
