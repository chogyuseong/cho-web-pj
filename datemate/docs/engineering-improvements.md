# 프론트엔드·백엔드 개선 적용 (2026-10-24)

## 적용 순서와 실제 변경

1. **조회·공유 권한**: 원본 `/api/plans/{id}` 하위 및 `/api/chat/plan/{id}`는 소유자만 접근. 타인은 존재 여부를 구별하지 않는 404. 공유는 해시로 저장한 별도 토큰, 발급 후 24시간, 일정별 최대 10개. 소유자는 전체 링크 철회 가능. 토큰은 URL fragment로 전달하고 API에는 Authorization 헤더로 전송. 공유 응답은 장소명·주소·유형·도착/출발 예정 시각만 허용한다. 원본 입력·출발지·귀가지·좌표·요청 문구·가격표·사적 대화는 포함하지 않는다. 상대방은 공유 화면에서 의견만 제출하며 원본 일정 수정은 불가.
2. **삭제와 작업 경합**: 삭제 트랜잭션에 세션 폐기 기록을 함께 저장한다. SQLite 트리거가 해당 세션의 늦은 일정·대화·후기·초안 캐시 쓰기를 차단한다. 메모리 검색 작업도 제거한다. 공유·의견의 삭제된 일정 참조를 차단한다. 답변 캐시는 세션별 분리하고 소유자 인덱스로 삭제한다. 기존 소유자 없는 답변 캐시는 1회 마이그레이션으로 무효화한다. 재생성 차단용 세션 식별자는 폐기 기록에 남으며 콘텐츠는 보관하지 않는다.
3. **요청 통제**: 직접 추천과 백그라운드 추천 모두 같은 동시성 제한(프로세스당 2개) 및 DB 기반 분당 횟수 제한을 통과한다. 기본 서버 전체 30회/분, 브라우저당 6회/분. 계측된 외부 HTTP 경로는 최대 동시 6개 및 공급자 호스트당 시간당 600회. 금액 한도가 아니라 호출 횟수 한도이며 LLM SDK와 모든 미디어 호출을 포함하는 것은 아니다.
4. **데이터 보존**: Docker Compose named volume 사용. 자동 캐시·공유 만료 정리. 백업 디렉터리 설정 시 시작 시점과 매시간 SQLite 온라인 백업·무결성 검사. 새 디렉터리로만 복원. Cloud Run은 영속 DB 연결 전 임시 데모임을 명시해야 실행된다.
5. **화면·요청 상태**: 요청당 30초 대기 제한, 검색 취소 API, 취소 후 늦게 도착한 결과 무시, 폴링 중단. 일시적 연결 실패로 작업 ID를 지우지 않음. 새로고침 복구 유지.
6. **입력 조건**: 직접 변경한 구조화 필드를 브라우저와 서버 모두 우선 적용. 자연어 적용 뒤 폼 유효성을 다시 검사하고 결과 화면에 적용 조건 요약 표시.
7. **구조 정리**: HTTP 처리를 독립 ES module로 분리하고 기존 UI와 어댑터로 연결. 폼 편집 상태를 별도 파일로 관리. 화면 표시·레이아웃 CSS를 별도 파일로 추출. 공통 렌더러의 원문 일괄 치환 제거. 전체 프론트엔드의 전면 모듈 전환은 하지 않았으며 기존 화면 API 호환성을 유지한다.
8. **운영 계측**: 계측한 지도·검색 HTTP 요청의 호스트별 호출 수·실패 수·평균 지연 집계. 검색어·주소·인증 헤더는 저장하지 않는다. 로컬 운영 보고서에 추천 건수·결과 없음·추천 지연 p95를 함께 표시. 실제 결제 비용·방문 여부는 추측하지 않는다.

## 실행과 복구

프로젝트 루트에서 `docker compose up --build -d`. 접속은 `http://127.0.0.1:8000`. 실제 Docker 빌드·기동은 이 변경에서 수행하지 않았다. `docker compose down -v`는 영속 볼륨도 삭제하므로 보존할 데이터가 있으면 사용하지 않는다. `/data` 디렉터리 지정만으로 영속성이 생기는 것은 아니며 Compose volume이 연결되어야 한다.

일반 Python 실행에서는 `DATEMATE_BACKUP_DIR`을 설정하면 자동 백업을 활성화할 수 있다. 자동 백업의 보관 개수 제한과 외부 저장소 복제는 아직 없으므로 운영자가 디스크 사용량과 보관 정책을 관리해야 한다. 동일 디스크 백업만으로 호스트 장애를 복구할 수는 없다.

`datemate` 폴더에서:

```powershell
.\.venv\Scripts\python.exe scripts/backup_database.py backups/manual.sqlite
.\.venv\Scripts\python.exe scripts/restore_database.py backups/manual.sqlite restore-check
.\.venv\Scripts\python.exe scripts/operations_report.py
```

복구는 새 폴더를 만든 뒤 무결성을 확인한다. 실제 전환 시 서버를 중지하고 `DATEMATE_RUNTIME`을 복구 폴더로 지정해 재시작한다. 백업에는 개인정보가 포함될 수 있으며, 과거 백업으로 복구하면 당시 이후의 삭제 기록도 되돌아갈 수 있으므로 운영 삭제 기록 대조가 필요하다. Chroma 검색 색인은 SQLite 백업에 포함되지 않아 재색인해야 한다.

## 검증 방법과 한계

실행 결과: 전체 회귀 테스트 **234개 통과(37.27초)**. 이후 공유 철회의 트랜잭션 재검사, 검색 접수 중 취소, Cloud Run 가드·자동 백업을 보완하고 관련 테스트 **37개 통과(9.39초)**. 후자는 전체 테스트에 더해지는 독립 37개가 아니라 관련 부분의 재검증이다. 두 실행 모두 Edge 브라우저 테스트를 포함하며 건너뛴 항목 없이 통과했다. 최종 상태에서 전체 테스트 총수는 236개이며 마지막 전체 실행 뒤 추가한 2개도 해당 부분 검증에 포함된다.

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest tests -q
```

브라우저 테스트는 설치된 Edge를 headless로 실행하고 데모 데이터·임시 DB를 사용한다. 외부 브라우저 트래픽을 차단하며 실사용 API 키나 운영 DB를 사용하지 않는다. 공유 투표/철회, 조건 유지, 화면 분리, 모바일 가로 넘침, JS 오류를 검증한다. 동시성 테스트는 작업 중 삭제·취소를 의도적으로 교차시킨다. 백업 복구는 새 SQLite 파일에 대해 확인한다.

실제 장소의 영업·가격·예약 정확성, 실 API 전체의 비용·지연, Docker/Cloud 배포, 다른 브라우저 접근성 감사, 사용자 재사용·결제 전환은 별도 검증이 필요하다. 다중 인스턴스 작업 큐와 프로세스 간 동시 실행 슬롯은 아직 구현하지 않았으며 현재 운영 범위는 단일 서버다. 실제 보안 취약점이 전혀 없다는 보증은 아니다.
