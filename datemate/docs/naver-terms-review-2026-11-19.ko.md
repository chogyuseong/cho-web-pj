# 네이버 약관 검토와 결정 (2026-11-19)

장소 카드에 '확인 필요'(위치·영업 정보·가격)가 많다는 사용자 신고에서 시작했다. 네이버 지도 화면에서 영업시간을 읽어 채우자는 제안을 하기 전에 약관을 먼저 확인했고, 그 결과 이미 쓰고 있던 화면 자동 조회도 그만두기로 했다(사용자 결정: "최대한 단점 보완해서 추천대로 진행").

## 확인한 원문

**네이버 서비스 이용약관**(2026-10-01 시행, policy.naver.com/rules/service.html)

> 네이버의 사전 허락 없이 자동화된 수단(예: 매크로 프로그램, 로봇(봇), 스파이더, 스크래퍼 등)을 이용하여 … 네이버 서비스에 게재된 회원의 아이디(ID), 게시물 등을 수집하거나, 네이버 검색 서비스에서 특정 질의어로 검색하거나 혹은 그 검색결과에서 특정 검색결과를 선택(이른바 '클릭')하는 등 이용자(사람)의 실제 이용을 전제로 하는 네이버 서비스의 제공 취지에 부합하지 않는 방식으로 네이버 서비스를 이용하거나 … 시도해서는 안 됩니다.

**검색결과 수집에 대한 정책**(policy.naver.com/policy/search_policy.html)

> robots.txt로 보호되고 있는 데이터 베이스를 네이버의 로봇이 아닌 타 검색 로봇이 수집하는 것을 불허합니다. … 경우에 따라 저작권 침해 또는 정보통신망 이용촉진 및 정보보호에 관한 법률 등에 위반될 …

**robots.txt**(2026-11-19 조회)

| 호스트 | 모든 로봇(`User-agent: *`) |
|---|---|
| search.naver.com | `Disallow: /` (전부 금지) |
| map.naver.com | `Disallow: /`, 첫 화면(`/`, `/p/`)만 허용 |
| m.blog.naver.com | 일부 경로만 금지(본문 수집은 약관의 '게시물 수집 금지'에 해당) |
| m.place.naver.com | robots.txt 없음(조회 중 429 차단 응답을 받음). 약관 적용 |

## 대신 잃는 것

- 업체가 네이버에 올린 사진이 더 이상 카드에 나오지 않는다. 관광공사에 없는 작은 가게는 사진이 없을 수 있다(사진 칸에 네이버 지도 링크가 남는다).
- 메뉴판 이미지와 전체 메뉴 목록이 없다. 블로그 요약문에 가격이 있을 때만 한두 개 보인다.
- 블로그 본문에만 장소 이름이 나오는 글은 '블로그 언급'으로 잡히지 않는다.
- 제목만 맞는 이미지 검색 결과로 사진을 채우지 않는다(다른 장소 사진이 섞이는 문제, tests/test_photo_source_priority.py).
  - 같은 날 뒤에 바뀜(사용자 피드백 "음식점 사진이 제대로 나오지 않는다"): 등록·관광공사 사진으로 2장이 안 되는 카페·미식 장소는
    공식 이미지 검색 API(약관상 허용된 공식 경로) 결과 중 제목에 가게 이름(지점 포함)과 동네·주소 낱말이 함께 나온 사진만
    '검색 사진'으로 원본·검색 링크와 함께 보여 준다. 다른 지점·다른 가게·동네 없는 제목·모음 글·다른 시·도 제목은 뺀다
    (app/image_search.strict_title_match, tests/test_strict_image_search.py). 끝내 없으면 사진 칸에 네이버 지도 링크.
  - 팝업 글 소개 옆에도 행사명·거점·'팝업'·올해가 맞는 이미지 검색 사진 한 장을 작은 칸으로 둔다(app/popup_api.post_photos).

## 남은 일

- 작은 가게의 영업시간은 여전히 대부분 없다. 근본 해결은 유료 장소 API(예: Google Places, 표시·저장 조건 검토 필요)나 업체 직접 등록.
- 공식 API 약관 7.3 ③(별도 데이터베이스 관리 금지)에 맞춰 API 결과 캐시는 짧게 둔다. 허용 기간은 여전히 확인하지 못했다(docs/popup-stage0-2026-11-14.md).
- 사진 썸네일 서버(app/photo_thumb.py)는 등록 사진과 엄격한 검색 사진의 원본(네이버 이미지·뉴스 사진 서버, 다음·카카오 사진 서버)을 줄인다.
  관광공사 사진 호스트는 넣지 않는다(제3유형 변경 금지).
  - 2026-11-20 바뀜: 검색 사진(이미지 검색 결과)은 더 이상 줄이거나 메모리에 담지 않는다(아래 '2026-09 특약 개정 대응').

## 이번에 한 일 (기능은 최대한 살리고 명백한 위반만 없앰)

### 2.3 AI 차단 (키가 설정돼도)

- 블로그 글에서 장소를 뽑던 LLM 추출(app/discovery.extract)을 없앴다. 언제나 `ai_blocked_by_naver_terms` 를 돌려준다. 규칙 기반 대체는 2단계.
- 코스 질문 답변(app/rag.py): 근거에 넣는 저장 코스를 `naver_terms.ai_safe_plan` 으로 정리한다. 블로그 검색 글(course_search)·블로그 점수,
  가격 근거 조각(price_evidence)·블로그 가격의 출처·금액, 네이버 검색 장소의 이름·주소·업종·좌표·링크를 빼고, 그 문자열이 다른 필드(구간 이름 등)에
  들어간 곳은 '네이버 검색 장소'로 가린다. 대화 기록(history)의 예전 답변도 같은 문자열을 가린다. 네이버 검색 장소 id 로는 색인을 찾지 않는다.
  답변 캐시 키 버전을 3으로 올렸다.
- 색인(app/indexing.py): `index_places`·`index_documents` 가 네이버 검색 장소를 넣지 않는다. 컨테이너 시작 색인(cloud_start)이
  `purge_naver_documents` 로 Chroma 에 남은 네이버 장소 문서를 먼저 지운다(예전 7일 공용 캐시의 발견 장소가 들어가 있었음).
  색인은 소유자 없는 문맥에서 만들므로 이제 발견 장소가 아예 보이지 않는다.
- 사진 내용 검사(app/photo_relevance.py): 네이버 사진 서버·네이버 검색 장소의 사진은 비전 모델에 보내지 않는다(그 검사의 대상이 모두 네이버 사진이라 사실상 꺼짐).
- 예전 답변 캐시 `answer:*` 는 마이그레이션 v0005 가 모두 지운다.

### 2.3·2.4 보관 기간

- 사용자 공용 캐시를 없앴다. 네이버 검색 결과와 파생물은 app/naver_cache.py 를 거친다.
  - 요청 안 메모: 한 요청(추천 작업 하나 포함) 안에서 같은 검색은 한 번만 부른다.
  - 사용자별 개인화 보관: 키 `nv:{목적}:{소유자}:{원래 키}`, 값에 소유자를 넣어 '내 데이터 삭제'·보존 기한 정리 때 함께 지워진다.
    수명은 원래 수명과 24시간 중 짧은 쪽. 목적은 plan(코스 추천·변경)·explore(둘러보기)·popups(팝업)·place(장소 상세).
  - 새 질의: 새 추천(recommendation_service.generate), 새 둘러보기 검색(캐시에 없는 조건), 새 팝업 검색(캐시에 없는 조건)이 그 목적과
    place 보관분을 지운다. 같은 조건으로 넘기기·더 보기는 새 질의로 보지 않는다.
  - 소유자가 없는 문맥(유지보수·스크립트·시작 색인)은 DB 에 남기지 않는다.
- 파생 장소(발견 장소 discovered-place, 둘러보기 장소 explore-place, 식당 restaurant:{id})를 다른 사용자의 후보나 카탈로그(/api/places)에 쓰지 않는다.
  `catalog.places('real')` 은 지금 요청 사용자의 보관분만 합친다. 팝업 거점 좌표 판정도 7일 공용 → 사용자별 24시간.
- 저장 코스(이력 조회 목적): maintenance 가 매시간 만든 지 21일이 지난 코스에서 네이버 유래 필드를 지운다(`naver_terms.cleanup_expired_plans`,
  plans.naver_cleared 에 시각 기록). 코스·시간표·비용 계산은 남기고 course_search·blog_score·price_evidence·블로그 가격 출처를 지우며,
  네이버 검색 장소는 이름을 '보관 기간이 지난 검색 장소'로 바꾸고 주소·업종·설명·링크·사진을 지운다. 화면은 안내 문구만 보여 주고 그 장소의 사진·블로그·메뉴는 다시 찾지 않는다.
  같은 기한에 실제 장소 대화 기록(chats, scope real:*)도 지운다.
- 24시간이 지나 개인화 보관에서 사라진 네이버 검색 장소의 상세(/api/places/{id}?mode=real)는 같은 사용자의 21일 안 저장 코스에서 찾는다(이력 조회).
- 마이그레이션 v0005: plans.naver_cleared 열, 예전 공용 캐시 행(네이버 결과·파생물, answer:*) 삭제. 유지보수도 같은 정리를 안전망으로 매번 한다(answer:* 제외).
- 쓸모없는 호출 정리: 블로그 본문을 읽지 않는 지금은 결과가 나올 수 없는 블로그 사진(blog_photos)·후기 영업 정보(review_facts)가 블로그 검색을 부르지 않는다.

### 2.1·2.2 표시

- static/naver-attribution.js: '네이버 검색결과 · {지역|블로그|이미지} 검색 · 원본 ↗ · NAVER 오픈 API' 한 줄. 'NAVER 오픈 API' 는 API HUB 상표·BI 가이드의
  텍스트 표기(이미지 대신 글자 허용)로 API HUB 포털에 새 창 링크. 로고 이미지는 쓰지 않았다(가이드의 로고 파일 링크가 서명 만료라 받지 않음).
  표시 위치는 가이드에 규정이 없어 각 항목 바로 아래(목록은 목록 위·아래)에 둔다.
- 붙인 곳: 둘러보기 카드(항목마다 원본=네이버 지도 검색), 둘러보기 목록, 코스 안의 지역 검색 장소(일정 카드·장소 정보 창·지도 목록·공유 화면),
  가격 근거(비용 표), 식당 제안(주변·지역 맛집·대신 들를 식당, 지도 정보 창), 레저 후보, 주차장(네이버 결과만), 블로그 후기 패널, 코스 조사 패널,
  팝업 목록, 검색 사진 출처 줄, 출발지 검색의 장소 이름 결과.
- 식당 제안 항목의 출처가 검색어 전체 링크였던 것을 항목마다 네이버 지도의 같은 업체 검색으로 바꿨다(검색어 링크는 search_url 로 남김).

## 줄어든 기능·느려진 점

- 같은 조건을 다른 사용자가 찾아도 다시 부른다(공용 캐시 적중이 없어짐). 첫 화면이 늦어지고 외부 호출이 늘어난다.
- 다른 사용자가 찾은 발견 장소가 추천 후보·장소 목록에 더 이상 들어가지 않는다(후보 수 감소). 새 추천을 하면 이전 추천의 발견 장소도 후보에서 빠진다.
- 공유 링크로 연 사람에게는 네이버 검색 장소의 사진·블로그가 나오지 않을 수 있다(장소 상세가 만든 사람의 보관분에만 있음).
- 21일이 지난 코스의 네이버 검색 장소는 이름·주소가 '보관 기간이 지난 검색 장소'로 바뀌고, 21일이 지난 실제 장소 대화 기록이 지워진다.
- 검색 사진은 서버에서 줄이지 않아 카드가 원본을 받는다(데이터 사용량 증가).
- 코스 질문(LLM 키가 있을 때)은 네이버 검색 장소에 대해 답하지 못한다. 블로그 글에서 장소를 찾는 기능은 키가 있어도 꺼진다.

## 외부 호출 수 (2026-11-20 측정·계산)

고정 자료로 실제 장소 추천 전체(generate)를 돌려 센 네이버 검색 API 호출(tests/test_recommendation_speed.py 의 가짜 응답, 블로그 본문 읽기는 꺼져 있어 0):

| 경우 | 전주 시나리오 | 성수 시나리오 | 예전(공용 캐시) |
|---|---|---|---|
| 사용자 A 첫 추천 | 16 (블로그 8 · 지역 8) | 8 (블로그 8) | 같음 |
| 사용자 A 같은 조건 다시 | 0 | 0 | 0 |
| 사용자 B 같은 조건 첫 추천 | 16 | 8 | 0 (공용 캐시 적중) |

코드로 센 화면별 상한(새 질의 한 번, 같은 사용자의 반복은 0):
둘러보기 기본 15건 · 활동만 4건 · 검색어만 6건 · 둘 다 3건, 팝업 블로그 2 + 거점 지역 검색 ≤3 + 사진 ≤3, 장소 상세 같은 업체 확인 1 + 블로그 1 + 엄격한 사진 ≤2(카페·식당),
주변 식당 장소당 2~6 + 지역 맛집 1~3, 주차장 ≤10. 예전에는 다른 사용자가 같은 장소·조건을 이미 봤으면 0 이었다.
블로그 사진·후기 영업 정보는 결과가 나올 수 없어 이번에 호출을 없앴다(장소마다 최대 1건씩 감소).

시간당 제공자 한도는 DATEMATE_PROVIDER_CALLS_PER_HOUR(기본 600, IP 대역당 절반)이고 네이버 검색 API 호스트 하나에 모두 걸린다.
추천 1번과 결과 보기(장소 10곳 안팎)를 한 사용자 몫으로 60~100건으로 잡으면 시간당 6~10명이 동시에 쓰면 한도에 닿는다.
한도에 닿으면 호출이 거절돼 '일부 자료 조회가 요청 한도에 도달'로 표시된다(오류는 아님). API HUB 하루 25,000건(시간당 약 1,040건) 안에서
값을 올릴지는 운영 결정으로 남겼다.

## 남은 위험·확인하지 못한 것

- 특약 원문(두 공지 본문)을 직접 확인하지 못했다. 특히 '새 질의'의 범위(장소 상세 조회를 새 질의로 볼지), '제3자 제공'에 공유 링크 열람이 드는지.
- 21일이 지난 코스에도 좌표와 블로그 가격에서 온 금액(비용 합계)이 남는다(일정 계산 유지). 출발지 이름이 지역 검색 결과의 주소이면 조건(conditions)에 그대로 남는다.
- 브라우저 저장소: '지난번처럼 추천'(static/form-state.js)이 출발지(지역 검색 결과일 수 있음)를 기한 없이 localStorage 에 둔다(기기 보관 24시간 규정과 충돌 가능).
- experience_events·partner_votes 등 다른 표에 장소 이름이 들어가는지 전수 확인하지 못했다.
- BI: 로고 이미지·크기·색 규정이 가이드에 없어 텍스트 표기로만 했다. 가이드 페이지가 오래된(stale) 표시였다.
- 외부 호출 증가로 시간당 제공자 한도(DATEMATE_PROVIDER_CALLS_PER_HOUR, 기본 600)에 닿을 수 있다. 값 조정은 운영 결정으로 남겼다(보고서 참고).
