# 네이버 검색 API 특약 2단계 설계 (2026-11-20)

1단계(docs/naver-terms-review-2026-11-19.ko.md 의 '2026-09 검색 API 특약 개정 대응')는 AI 이용 차단, 보관 기간(기기 24시간, 서버 개인화 24시간·이력 21일), '네이버 검색결과' 표시를 다뤘다.
같은 날 후속 작업(브랜치 fix/terms-followups)에서 21일 뒤에도 남던 좌표·블로그 가격 금액·출발지 주소와 브라우저 저장소를 정리했다.
이 문서는 그때 남겨 둔 **특약 2.2(가공 없이 독립적으로 노출, 순위·내용 수정 금지, 앞·뒤·중간에 다른 내용 삽입 금지)와 충돌하는 기능**을 어떻게 바꿀지 정한다.
코드는 바꾸지 않았다. 아래 '사용자가 정할 것'에 답을 받은 뒤 작업한다. (2026-11-20 답 받음 → 5-1절)

## 1. 전제와 해석

- 특약 요지(1단계 문서의 표): 2.1 '네이버 검색결과를 제공할 목적으로만 이용', 2.2 '독립적으로, 가공 없이 노출 · 앞·뒤·중간 삽입 금지 · 순위·내용 수정·변조·왜곡 금지 · 원본 출처와 링크', 2.3 '가공물·파생물의 저장 금지, AI 활용 금지'.
- **원문 두 공지(개발자센터 33400, 네이버 클라우드 2243)는 아직 직접 대조하지 못했다.** 아래 판단은 요청에 적힌 요약을 기준으로 한다. 원문과 다르면 이 문서를 고친다.
- 가장 엄격한 읽기: 검색 결과를 **우리 계산의 입력**으로 쓰는 것(후보 찾기, 점수, 가격 읽기, 판정)은 '네이버 검색결과를 제공할 목적'이 아니므로 2.1·2.2 모두에 걸린다. 화면에 원본을 그대로 보여 줘도, 그 결과로 우리 추천을 만들면 위반이다.
- 덜 엄격한 읽기: 화면에 보이는 '네이버 블록'만 가공하지 않으면 되고, 내부 계산에 쓰는 것은 2.3(저장·파생물)의 보관 기간만 지키면 된다.
- 어느 쪽인지는 네이버에 서면으로 물어야 한다(사용자 결정 Q1). **이 문서의 권장안은 엄격한 읽기를 기준으로 한다.** 덜 엄격한 답을 받으면 (a)만으로 끝나는 기능이 늘어난다.

  - 좌표의 시·군·구는 상가정보로 안다: 반경 안 약국(어디에나 고르게 있는 업종)의 시·군·구 코드를 세어 많은 곳부터 최대 3곳. 상가정보의 5자리 코드가 관광공사의
    법정동 시·도 2자리 + 시·군·구 3자리와 같다(세종만 36110/36110). 약국이 5km 안에 없으면 관광공사 목록 없이 상가정보·카탈로그만 쓴다.
  - 관광공사 항목을 먼저 쓰고(종류마다 가까운 순 12곳, 합쳐 60곳까지), **상가정보는 카탈로그·관광공사로도 모자란 종류만** 채운다. 상가정보에는 고를 신호가 없어
    '지점 표기 없는 곳 먼저, 가까운 순'으로 종류마다 몇 곳(식사 8·카페 6 등). 서울 표본에서 회사 이름('…푸드')·강습소('…미술교습소')·성인 게임장('○○게임')이
    뽑혀, 그런 상호를 빼고 공방·놀이 업종은 상호의 낱말 단서가 있을 때만 받게 좁혔다.
  - 활동 요청이 없고 종류가 충분해도 관광공사 목록은 늘 합친다(전에는 이 경우 검색하지 않아 서울 성수의 후보가 7곳뿐이었다). 목록이 공용 캐시라 호출이 늘지 않는다.
  - 찾은 후보는 그 사용자의 추천 범위에만 둔다(24시간, 새 추천 때 비움 — 네이버 결과용 보관 틀을 같이 쓴다). 공공 자료라 의무는 아니고 다른 동네 후보가 카탈로그에
    쌓이지 않게 하려는 것이다. 공공 API 응답 자체는 사용자 공용 캐시다.
  - 공공 API 를 1차와 같은 태도로 다룬다: 실패·시간 초과는 후보 없음으로 넘어가고 60초 동안 다시 부르지 않는다. 이 기능의 관광공사 호출에 하루 상한(기본 600)을,
    상가정보에 하루 상한(기본 5,000)을 걸었다. 제공자 지표·시간당 예산은 공공데이터포털을 기관별(B551011·B553077·1741000)로 나눠 센다.
  - 주변 식당(app/restaurants.py): 관광공사 음식점 먼저, 그다음 상가정보를 500m→1,000m→1,500m 순으로 3곳까지. '후기 많은 순'과 구 단위 '유명 맛집 TOP 5'는
    대신할 공공 자료가 없어 없앴다(네이버 검색 화면으로 가는 링크만).
  - 레저(app/leisure.py): 관광공사 레포츠 + 상가정보 예술·스포츠 업종, 종목마다 가까운 4곳. 주차장(app/parking.py): 공공데이터 전국주차장정보표준데이터만
    (네이버 결과에 이름으로 맞춰 붙이던 좌표 없는 서울 노외 주차장은 빠진다).
  - 식당·카페 후보가 네이버 검색 장소가 아니게 되어 1차의 공공 판정('위치' 줄: 상가정보 위치 확인, 인허가 영업 중·폐업)이 붙는다(1차에서는 엄격한 읽기 때문에 붙이지 못했다).
  - 저장된 코스는 건드리지 않았다(마이그레이션 없음). 배포 전에 만든 코스의 네이버 검색 장소는 1단계 규칙대로 21일 뒤 정보가 지워지고, 그때까지는 전처럼 출처 줄을 달고 보인다.
- 3.5(b) 둘러보기(app/explore.py):
  - 기본 목록 = 관광공사 시·도 목록(활동이 없으면 관광지·문화시설, 활동이 있으면 그 분류) + **동네를 알 때만** 그 주변 상가정보. 상가정보는 반경 조회뿐이라 중심이 필요한데,
    검색어에 우리 사전의 동네·거점 이름(서울 동네, 홈 동네 카드, 팝업 거점)이 있으면 그 좌표, 없으면 관광공사 이름 검색 결과 중 제목에 검색어가 든 항목들의 가운데 좌표를 쓴다.
    검색어가 없으면 관광공사 목록만 보이고 '동네 이름으로 검색하면 주변 가게도 보여 드려요'를 적는다(설계의 '상가정보 반경'을 시·도 전체에는 적용할 수 없어서).
  - 정렬: 사진 있는 관광공사 항목 → 나머지 관광공사 항목 → 상가정보. 공공 자료라 목록은 사용자 공용 캐시(6시간)다.
  - '네이버에서 더 찾기': 접어 두고 **펼쳤을 때만** 부른다. 검색어 최대 4개, 검색어마다 5건, 받은 그대로(다른 시·도, 병원, 같은 가게가 두 번 나와도 그대로). 블록의 가게는
    우리 장소로 만들지 않아 사진·상세·코스로 이어지지 않는다(네이버 지도 링크와 홈페이지 링크만).
- 3.7(a) 화면 블록(static/naver-attribution.js naverResultBlock):
  - 블록 = 테두리 상자 + 머리글 띠('네이버 검색결과 · 종류 · 원본 ↗ · NAVER 오픈 API', 검색어·건수 제목) + 본문(API 필드만). 블로그 글(장소 후기·코스 조사), 팝업 글,
    둘러보기 블록, 출발지 이름 검색 결과(홈 화면 검색·지도 선택 창)가 이 부품 하나를 쓴다. 우리 안내 문장·'더 보기' 밖 정보는 블록 밖에 둔다
    (Q2 답이 없어 같은 화면이라도 경계 안으로 넣지 않는 쪽).
  - 식당·레저·주차장 카드는 공공 자료가 되어 네이버 출처 표시가 없다. 대신 '공공 자료 · 한국관광공사 관광정보/소상공인 상가정보' 한 줄을 단다.
  - 공공 자료 때문에 '확인 필요'가 많은 까닭은 한 줄로: 장소 카드의 정보 확인 칸(관광공사/상가정보별 문장), 둘러보기 목록 아래, 주변 식당의 정렬 기준, 주차장 출처 줄.
- 정하지 않고 남긴 것:
  - **출발지 이름 검색**(역·가게 이름 → 네이버 지역 검색, app/geocoding.search_places)은 그대로 두고 화면만 블록으로 바꿨다. 사용자가 고른 한 곳의 좌표가 출발지가 되어
    거리 계산의 기준점이 된다. 엄격한 읽기에서는 이것도 '검색 결과를 계산의 입력으로' 볼 수 있다(1단계 문서의 남은 위험과 같은 항목). 없애면 '강남역' 같은 이름으로
    출발지를 못 찾는다(관광공사 자료에 지하철역이 없음). 선택지: 유지 / 관광공사 이름 검색으로 대체(역은 못 찾음) / 주소·지도 선택만.
  - Q1 답이 덜 엄격하면: 지역 검색 후보를 되살릴 수 있지만 공공 자료 후보가 표본에서 더 나은 수치를 보여 되돌릴 이유는 크지 않다. Q2 답에 따라 블록 경계는 느슨하게 할 수 있다.

## 6. 남은 위험

- 특약 원문 미대조(1단계와 같음). 카카오 저장 규정은 공식 약관 원문이 아니라 데브톡 공식 답변(2026-10-19·20) 기준이다.
- 공공 자료의 트래픽 한도 일부는 2차 자료로만 확인했다. 활용신청 화면에서 다시 봐야 한다.
- 상가정보는 분기(파일) 또는 실시간(API) 갱신이라 새 가게·폐업 반영이 늦을 수 있다. 인허가로 영업상태를 보완하는 설계가 필요하다.
- 공공 자료로 바꾸면 사진·영업시간·평판 신호가 줄어 추천 만족도가 떨어질 수 있다. 3단계 전에 측정 스크립트(scripts/measure_option_diversity.py 등)로 전후를 비교해야 한다.
  → 2026-11-20 측정함(docs/public-candidates-measure-2026-11-20.ko.md): 3안을 채운 건·조건 충족·사진·영업 안내는 나빠지지 않았다. 평판 신호(후기 많은 곳)는 잃었고
  사람이 매긴 만족도는 재지 않았다.
- 한국관광공사 TourAPI(KorService2)의 목록 API 는 2026-11-20 응답 기준으로 법정동 코드·새 분류만 믿을 수 있다(5-3). 제공 쪽이 예전 코드를 다시 채우거나 새 분류를 바꾸면
  대응표(app/public_places.TOUR_KINDS)와 시·군·구 목록 조회를 다시 확인해야 한다. 개발계정 하루 1,000건 한도는 하루 약 40~50명에서 찬다(운영계정 증량 필요).
