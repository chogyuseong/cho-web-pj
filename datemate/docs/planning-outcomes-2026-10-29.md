# 1단계: 코스 결정과 함께 고르기

인수 검토 관점의 개선안 중 1번(효과 측정)과 2번(두 사람의 합의)을 구현했다.
기능을 사용할 수 있는 상태와 사업 효과를 입증한 상태를 구분한다. 실제 참여자 실험은 아직 진행하지 않았다.

## 사용자 흐름

1. 기존처럼 지역·일시·예산을 입력해 추천을 받는다.
2. 결과 카드에서 ‘이 코스로 결정’을 누르면 현재 브라우저에 결정한 코스를 남긴다.
3. 같은 검색의 다른 코스를 결정하면 이전 결정을 대체한다. 별도로 검색한 다른 날짜의 결정은 유지된다.
4. 입력 화면의 ‘내가 결정한 코스 다시 보기’에서 최근 10개를 다시 연다.
5. ‘상대와 함께 고르기’로 공유 링크를 복사하고 본인의 의견도 입력한다.
6. 상대는 별도 공유 화면에서 상관없음·좋아요·꼭 가고 싶음·빼주세요 중 하나를 선택한다. 새로고침해도 본인 의견이 복구된다.
7. 꼭 가고 싶은 곳과 빼고 싶은 곳이 충돌하면 해당 장소를 안내한다. 충돌을 조정한 뒤 재계산한다.
8. 필수 선호와 양쪽의 좋아요는 유지하고, 거절한 장소는 제외한다. 변경 전후와 유지·제외한 장소를 확인한 후 적용한다.

의견은 두 브라우저 기준이다. 상대방은 원본 일정의 출발지·귀가지·자유 입력·상세 조건이나 측정 기록을 받지 않는다.
공유 링크의 24시간 만료, 철회, 소유자 변경 권한 검사를 유지했다.

## 선택적 경험 측정

‘인원·이동·식사 설정’ 안의 ‘계획 경험 측정 참여’는 기본 해제다.
참여하지 않아도 코스 결정·저장 목록·공동 선택은 사용할 수 있다.

참여한 검색은 서버에서 시작 시각을 기록한다. 결과에서 다음 항목에 선택적으로 응답할 수 있다.

- 추가 검색 없음 / 일부 검색 / 대부분 다시 검색 / 응답하지 않음
- 평소 직접 코스를 계획하는 시간(0~240분, 선택)

서버 시간은 **추천 요청부터 코스 결정까지**다. 폼 입력 전 시간은 측정하지 않고, 검색 대기와 자리 비움은 포함한다.
평소 시간과 추가 검색은 자기 신고이며, 자동 측정값이나 실제 방문 인증으로 취급하지 않는다.
측정 연결에 실패하면 추천을 계속 진행한다. 측정 상태가 24시간 뒤 만료돼도 기존 코스 결정은 가능하다.

기록에는 원문 요청·주소·대화·공유 토큰을 넣지 않는다. 브라우저 소유자와 연결된 내부 식별자를 사용하며, 전체 데이터 삭제 시 관련 상태와 기록도 삭제한다.

## 운영 지표

`python scripts/operations_report.py`의 `planning_study`에 다음을 추가했다.

- `enrolled_sessions`: 보고 기간에 측정 참여를 시작한 검색. 미완료·실패 검색도 분모에 포함.
- `decided_sessions`, `decision_rate`: 같은 기간 참여 검색 중 결정이 있는 검색. 코스 옵션을 바꿔도 중복 계산하지 않음.
- `median_request_to_decision_seconds`, `timing_samples`: 결정한 참여 검색의 시간 중앙값과 표본 수.
- `extra_search_answered`, `no_extra_search`, `no_extra_search_rate`: 응답한 참여 검색에서 추가 검색 없이 결정한 비율. 미응답은 이 비율의 분모에서 제외.
- `manual_baseline_samples`: 평소 계획 시간에 응답한 표본 수. 시간 절감 효과를 자동으로 주장하지 않음.

현재 브라우저의 ‘피드백 집계’에서도 참여·결정·추가 검색 응답 건수를 볼 수 있다.
이 값은 전체 이용자 전환율·실제 사람 수·검증된 방문율이 아니다. 삭제한 기록은 집계에서 제외된다.

## 실제 효과 검증 절차

소수 참여자부터 같은 수준의 다른 지역·활동 과제를 준비해 직접 검색과 서비스 이용을 번갈아 진행한다.
각 과제의 시작·결정 시간을 동일한 방식으로 측정하고, 추가 검색·최종 코스·방문 실패 원인을 별도로 기록한다.
자기 신고한 평소 시간을 직접 측정한 대조 실험 결과로 사용하지 않는다.
평가 기준과 수집 기간을 시작 전에 정하고, 실패와 미완료도 함께 보고한다. 초기 결과는 탐색적 평가로 설명한다.

## 구현·검증 범위

- `app/planning_outcomes.py`: 참여 상태, 소유자별 결정, 최근 결정 목록, 집계.
- `static/planning-outcomes.js`: 참여·결정·최근 목록 UI.
- 기존 공유·투표·초안 적용 기능에 필수 선호와 충돌 검사를 연결.
- 새 DB 테이블 없이 기존 소유자 보호 저장소와 트랜잭션을 사용.
- 자동 검사는 임시 DB, 실제 브라우저 검사는 통제된 시연 코스와 두 브라우저 문맥을 사용한다.

최종 전체 회귀 검사: **305 passed, 1 skipped (126.02초)**. PostgreSQL 전용 검사는 실행 환경이 없어 건너뛰었다.
측정 장애 시 추천 진행, 참여 기본 해제, 시간·답변 저장/복구, 다른 코스 결정 시 대체, 동시 중복 결정,
다른 브라우저 접근 차단, 전체 삭제, 필수 선호/거절 충돌, 상대 의견 복구 및 실제 변경안 적용,
가독성·모바일·기존 공유/후기/탐색 동작을 확인했다. 포맷 검사와 `git diff --check` 통과.
