# 팝업스토어 탐색 1단계 1a 보고 (2026-11-14)

- 계약: `datemate/docs/popup-stores-spec.md` (0-5 가 1단계 확정 사항). 0단계 보고: `datemate/docs/popup-stage0-2026-11-14.md`.
- 브랜치: 로컬 `popup-stage1` (`popup-stage0` 에서 갈라짐). main 은 그대로, push·배포·운영 데이터 수정 없음.
- 이번 범위: 1a(서버 API + 둘러보기 화면)만. 코스 결과 구역·주변 코스 버튼(1b), 지도(1c)는 만들지 않았습니다.
- 뉴스 검색은 부르지 않았습니다(권한 없음, 0단계 401). 모든 수치와 화면은 **블로그만**입니다.

## 1. 사용자 동작이 어떻게 달라졌나

- 헤더는 그대로(메뉴 4개)입니다. "장소 둘러보기" 화면 맨 위에 **[장소] [팝업스토어]** 전환이 생겼습니다.
- [팝업스토어]를 누르면 장소 둘러보기에서 고른 시·도로 네이버 블로그 검색 결과(최신 50건)에서 `팝업`이 들어간 글을 글마다 한 항목으로 보여 줍니다.
  시·도와 검색어(선택, 30자까지)를 바꿔 다시 찾을 수 있습니다. 상태는 한국시간 오늘 기준입니다.
- 각 항목은 위아래 두 칸입니다.
  - 위(원문 인용): "네이버 블로그 · 블로거 이름 · 글 날짜", 제목, 요약(받은 그대로, 말줄임 없음), "블로그 원문 보기 ↗".
  - 아래(회색 바탕, 점선 경계): "데이트메이트가 검색 요약에서 읽은 정보" — 기간과 장소 두 줄. 확인된 줄은 실선 홍색 역 원, 미확인 줄은 점선 회색 원 + "기간 미확인"·"위치 미확인" 글자.
- 일반 글("검색된 팝업 글 N건")과 모아 보기 글("여러 팝업을 모아 소개한 글 N건")을 나눠 보이고, 처음 10건 뒤는 "글 더 보기".
- 종료로 확인된 글은 숨기고 "오늘 기준 종료로 확인된 글 n건은 숨겼어요", 다른 시·도 장소의 글은 빼고 "다른 시·도 장소로 읽힌 글 n건은 뺐어요"라고 알립니다.
- 목록 아래 "출처: 네이버 블로그 검색 결과 · 순위나 인기순이 아니에요." 광고·별점·인기 표시는 없습니다.
- 화면 상태: 찾는 중 / 결과 / 결과 없음 / 일부 위치 확인 실패(partial) / 전체 실패(다시 찾기 버튼) / 키 없음(버튼 없음) / 요청 제한(429 문구).

## 3. 서버 API 계약 (`GET /api/popups?region=&visit_date=&q=`)

- 파일: `app/popup_api.py`(새), `app/main.py`(라우터 등록·`/api/status` 의 `popups_enabled`), `app/web_security.py`(EXPENSIVE), `app/maintenance.py`(시간 한도 정리), `.env.example`, `cloudflare/validation.mjs`.
- 입력: `region` 은 17개 시·도(별칭 허용, `부산광역시` → `부산`), 아니면 422. `q` 는 NFKC·제어/서식 문자 제거·공백 하나로 정규화 뒤 30자 초과면 422, 앞에 같은 시·도 이름이 있으면 뗌("서울 성수" = "성수"). `visit_date` 는 없으면 한국시간 오늘(`basis: today`), 있으면 오늘 기준 31일 전~366일 뒤만(축제와 같은 폭), 아니면 422.
- 상태: `ready` / `empty`(검색은 됐지만 보여 줄 글 0) / `partial`(검색은 됐지만 거점 좌표 확인 일부 실패) / `unavailable`(블로그 호출 실패·같은 검색 처리 중) / `key_missing`. 스위치가 꺼지면 404.
- 글마다: `id`(`popup-post:` + canonical URL 의 SHA-1 앞 16자, 1b·1c 가 그대로 씀), `title`·`description`(텍스트), `url`(받은 그대로, http/https 만), `blogger`, `posted_at`, `roundup`,
  `period`(`level`: confirmed / month_day / conflict / none, `start`·`end`(연도 확인 시만), `evidence`(요약의 근거 문자열), `status`, `end_only`),
  `place`(`hub_id`·`name`·`kind`·`anchor`·`region`, `level`: building / area_anchor / unverified, `reason`, 확인된 경우만 `lat`·`lon`).
  행사명·묶기 필드는 없습니다.
- 정렬(결정적): 일반 글 → 거점을 읽은 글 → 글 날짜 최신 → 글 ID. 모아 보기 글은 뒤.
- 그 밖에 `sources`(검색원 목록: 검색어·정렬·표시 수·받은 수·캐시 여부), `counts`(shown·general·roundup·location_unknown·hidden_ended·excluded_other_region·not_popup), `hub_checks`(requested·failed·skipped), `attribution`, `rules_version`, `hubs_version`.

### 확정한 캐시·한도 값

| 항목 | 값 | 비고 |
|---|---|---|
| 원본 검색 결과 | 성공 1시간, 팝업 글 0건 10분, 실패 캐시 안 함 | 키: 규칙·사전 버전, 시·도, 정규화 검색어(소문자), 정렬 date, 50건, 1페이지 |
| 방문일 상태 | 캐시 안 함, 요청마다 계산 | |
| 거점 좌표 판정 | 7일 | 상태·등급·위도·경도만 저장(업체 이름·주소는 저장 안 함). 실패는 캐시 안 함 |
| 요청당 외부 호출 | 블로그 1 + 좌표 미캐시 거점 최대 3(많이 나온 거점부터) | 나머지는 `not_checked`(위치 미확인)로 두고 다음 요청에서 확인 |
| 시간 제한·재시도 | 10초, 재시도 없음 | 모두 `observed_http` 경유(제공자 시간당 한도·지표 공유) |
| 같은 키 동시 호출 | 키별 잠금, 2.5초만 기다림(`image_search.LOCK_WAIT_SECONDS`), 넘기면 `unavailable`(busy) | 잠금을 얻은 뒤 캐시를 다시 봄 |
| 전용 한도 | 분당 3회(`ip:popup-search`), 시간당 30회(`popups:hour:`) | 외부 호출이 필요한 요청만 셈. 캐시로 답하면 쓰지 않음. 좌표만 필요한데 한도를 넘으면 429 대신 좌표 확인을 건너뜀 |
| EXPENSIVE | `^GET /api/popups$` | 기존 분당 120 비용 한도 |

설계상 알게 된 것: `web_security.ip_allow(..., seconds=3600)` 로 시간 한도를 두면 범위 이름이 `ip:` 로 시작해, `maintenance.py` 가 `ip:%` 를 분 단위 버킷으로 보고 2분 지난 것을 지우는 규칙에 걸려 시간 한도가 사실상 풀립니다(시간 버킷 번호가 분 버킷 번호보다 훨씬 작음). 그래서 시간 한도는 `popups:hour:` 범위에 두고 `maintenance.py` 에 시간 단위 정리 한 줄을 더했습니다.

### 스위치와 운영 전달

- `DATEMATE_POPUPS_ENABLED`(기본 켜짐, `0/false/off/no` 면 끔): API 404(피드백 탭과 같은 방식), `/api/status` 의 `popups_enabled: false` → 화면이 전환·팝업 칸을 아예 만들지 않음.
- Worker 는 `OPTIONAL_CONTAINER_ENV` 에 있는 이름만 컨테이너로 넘기므로, `DATEMATE_POPUPS_ENABLED`·`DATEMATE_IP_POPUP_SEARCHES_PER_MINUTE`·`DATEMATE_IP_POPUP_SEARCHES_PER_HOUR` 를 추가했습니다(기존 `DATEMATE_IP_EXPLORE_SEARCHES_PER_MINUTE` 는 목록에 없어 운영에서 바꿀 수 없는 상태 그대로).
- 정적 파일: `index.html` 에 `/static/popups.css`·`/static/popups.js` 를 넣었고 `static_pages.versioned_page` 가 두 주소에도 해시를 붙입니다(같은 정규식). 둘 다 같은 출처라 CSP `default-src 'self'`·`script-src 'self'` 안입니다. 공유 화면(`shared.html`)에는 넣지 않았습니다.

## 4. 추출 규칙 v1 재측정 (새 표본)

### 4-1. 순서와 호출

1. 규칙·사전 v1 을 커밋(`bc9fc3a`) → 진단 스크립트 커밋(`b6e201f`) → 호출.
2. 블로그 5건: `{지역} 팝업스토어`, `display=50, start=51, sort=date`(같은 검색어의 2페이지). 모두 200, 197~302ms. 재시도 0.
3. 좌표 확인(지역 검색) 19건(상한 20): 새 표본에서 v0·v1 어느 쪽이든 매칭된 거점마다 1건. 모두 200, 83~201ms.
4. 표본을 본 뒤 v1 오인식 3건을 보고 규칙·사전을 고쳤습니다(**사후 조정 v1.1**, 커밋 `52b1bd4`). 아래 표의 v1.1 열은 공식 수치가 아닙니다.
   - 규칙: "지난 10월 …" 같은 "지난 N월" 도 지난 장소로 봄, 검색 지역 거점과 다른 시·도 거점이 함께 나온 글은 단일 장소로 정하지 않음.
   - 사전: 부산 본점에 별칭 "부산 롯데백화점 본점"(해시태그 "# 부산 롯데백화점본점"이 서울 "롯데백화점 본점"에 걸리던 것).
5. 표본 글 날짜: 서울·부산 11-14, 대구 11-13~14, 강원 11-12~13, 전북 11-10~12. 원본은 `datemate/runtime/popup_stage1/`(Git 제외).
- 진단 스크립트(`scripts/popup_stage1.py`)는 0단계처럼 `observed_http` 를 거치지 않고 httpx 로 직접 불렀습니다(운영 DB 기록·한도와 섞지 않음).

### 4-2. v0 · v1 · v1.1 나란히 (분모 D = 지역별 URL 중복 제거 후 `팝업`이 든 글)

| 부산 | 41 | 3 (7%) → 2 (5%) +충돌 1 | 2 → 2 | 2 → 2 | 11 (27%) → **15 (37%)** → (14, 34%) | 11 (27%) → 15 (37%) → (14, 34%) | 14 → 13 |
| 대구 | 45 | 10 (22%) → 11 (24%) | 3 → 3 | 3 → 3 | 19 (42%) → **25 (56%)** → (22, 49%) | 13 (29%) → **25 (56%)** → (22, 49%) | 11 → 9 |

- "위치 확인"은 단일 거점이고 그 거점 좌표 판정이 `verified` 인 글. v0 은 같은 지역 검색 원본을 v0 검증(첫 통과 항목)으로, v1 은 쇼핑 업종 우선으로 판정했습니다. 대구 v0 → v1 의 큰 차이는 대구신세계가 v0 에서 "모호"(입점 매장이 300m 넘게 떨어짐)였다가 v1 에서 백화점 항목으로 확인된 것입니다.
- 부산 기간 후보가 3 → 2 로 준 것은 v1 에서 "열려"가 기간 문맥 낱말이 되어, 한 글(신세계 정기세일)에 기간 후보가 둘이 되어 "충돌(기간 미확인)"로 바뀐 것입니다(넓은 기간으로 합치지 않음).
- 0단계 1페이지 표본의 v0 공식 수치(서울 71%·부산 28%·대구 58%)와 이번 2페이지 수치는 표본이 달라 직접 비교하지 않습니다. 같은 표본 안의 v0 대 v1 만 비교합니다.
- 기간·상태는 여전히 대부분 미확인입니다(오늘 상태 판정 9/218). 1a 화면은 이것을 숨기지 않고 "기간 미확인"으로 보입니다.

### 4-3. 수동 검토 (v1 공식, 지역별 최대 10건)

- 선택: 지역별로 v1 이 기간 후보를 냈거나 거점을 하나 이상 매칭한 `팝업` 글을 canonical URL 의 SHA-1 순으로 최대 10건 → 서울 10, 부산 10, 대구 10, 강원 2, 전북 1 = 33건.
- 판정 기준은 0단계와 같음(낸 것 중 하나라도 어긋나면 오답, 놓침은 오답 아님, 판단 불가는 정답에 넣지 않음). 판정한 것: 채택한 기간, 단일 거점(또는 다른 지역 판정), 모아 보기 분류("애매"는 일반 글로 보이므로 모아 보기 아님으로 봄). 행사명은 운영에서 쓰지 않아 판정하지 않았습니다.
- **추출기를 만든 쪽(이 작업자)의 판정**이고, 판단 범위는 제목·요약까지입니다. 원문 링크를 열지 않았습니다.

## 7. 알려진 문제와 남은 제한

- **기간은 대부분 미확인**: 새 표본에서 오늘 상태 판정 9/218(4%). 실제 서울 응답도 37건 중 연도까지 확인 2건. 화면은 이를 "기간 미확인"으로 숨기지 않고 보입니다.
- **팝업 행사 글이 아닌 글도 섞임**: 제목·요약에 "팝업"이 있으면 보입니다(연예 기사형 글, 세일 안내, 몰 안내 등). 실제 서울 응답 첫 글도 연예인 착용 기사형 글(요약에 팝업스토어 언급)이었습니다.
- **해시태그 오매칭**: "#더현대 대구팝업" 같은 해시태그가 다른 지역 행사 글을 이 지역 거점에 붙임(검토 #21). v1.1 에서도 남아 있습니다.
- **사전 밖 지역**: 강원·전북은 거점이 없어 모두 위치 미확인이고, 강원 검색에 경기 동탄 행사 글이 "위치 미확인"으로 남습니다(다른 지역으로 뺄 근거가 없음).
- **모아 보기 놓침**: "총정리" 글 중 여러 행사 근거가 요약에 안 보이면 일반 글로 둡니다(방침상 애매하면 일반 글).
- **v1.1 의 대가**: 다른 시·도 회차가 함께 적힌 단일 행사 글은 위치 미확인이 됩니다(설산도 사례).
- **한 번 호출 = 하루치**: 최신순 50건이 대도시는 같은 날 글이라, 며칠 전 소개된 팝업은 잘 나오지 않습니다(0단계와 같음).
- **좌표 확인 대기**: 처음 보는 거점이 4곳 이상이면 3곳만 확인하고 나머지는 다음 요청까지 위치 미확인입니다.
- **같은 검색 동시 요청**: 첫 요청이 2.5초 넘게 걸리면 뒤 요청은 "같은 검색을 처리하고 있어요"(unavailable)를 받습니다.
- **조작 한 번 추가**: 헤더 B 안이라 팝업까지 2번 눌러야 하고, 장소 둘러보기를 열 때 기존 장소 검색이 먼저 돕니다(캐시가 없으면 지역 검색 최대 16건).
- 거점 좌표 7일 캐시는 사용자가 정한 값이며, 약관이 허용하는 보관 기간은 0단계처럼 여전히 확인하지 못했습니다.
