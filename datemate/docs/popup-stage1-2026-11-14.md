# 팝업스토어 탐색 1단계 1a 보고 (2026-11-14)

- 계약: `datemate/docs/popup-stores-spec.md` (0-5 가 1단계 확정 사항). 0단계 보고: `datemate/docs/popup-stage0-2026-11-14.md`.
- 브랜치: 로컬 `popup-stage1` (`popup-stage0` 에서 갈라짐). main 은 그대로, push·배포·운영 데이터 수정 없음.
- 이번 범위: 1a(서버 API + 둘러보기 화면)만. 코스 결과 구역·주변 코스 버튼(1b), 지도(1c)는 만들지 않았습니다.
- 뉴스 검색은 부르지 않았습니다(권한 없음, 0단계 401). 모든 수치와 화면은 **블로그만**입니다.

## 1. 사용자 동작이 어떻게 달라졌나

- 헤더는 그대로(메뉴 4개)입니다. "장소 둘러보기" 화면 맨 위에 **[장소] [팝업스토어]** 전환이 생겼습니다.
- [팝업스토어]를 누르면 장소 둘러보기에서 고른 시·도로 네이버 블로그 검색 결과(최신 50건)에서 `팝업`이 들어간 글을 글마다 한 항목으로 보여 줍니다.
  시·도와 검색어(선택, 30자까지)를 바꿔 다시 찾을 수 있습니다. 상태는 한국시간 오늘 기준입니다.
- 각 항목은 위아래 두 칸입니다.
  - 위(원문 인용): "네이버 블로그 · 블로거 이름 · 글 날짜", 제목, 요약(받은 그대로, 말줄임 없음), "블로그 원문 보기 ↗".
  - 아래(회색 바탕, 점선 경계): "데이트메이트가 검색 요약에서 읽은 정보" — 기간과 장소 두 줄. 확인된 줄은 실선 홍색 역 원, 미확인 줄은 점선 회색 원 + "기간 미확인"·"위치 미확인" 글자.
- 일반 글("검색된 팝업 글 N건")과 모아 보기 글("여러 팝업을 모아 소개한 글 N건")을 나눠 보이고, 처음 10건 뒤는 "글 더 보기".
- 종료로 확인된 글은 숨기고 "오늘 기준 종료로 확인된 글 n건은 숨겼어요", 다른 시·도 장소의 글은 빼고 "다른 시·도 장소로 읽힌 글 n건은 뺐어요"라고 알립니다.
- 목록 아래 "출처: 네이버 블로그 검색 결과 · 순위나 인기순이 아니에요." 광고·별점·인기 표시는 없습니다.
- 화면 상태: 찾는 중 / 결과 / 결과 없음 / 일부 위치 확인 실패(partial) / 전체 실패(다시 찾기 버튼) / 키 없음(버튼 없음) / 요청 제한(429 문구).

## 3. 서버 API 계약 (`GET /api/popups?region=&visit_date=&q=`)

- 파일: `app/popup_api.py`(새), `app/main.py`(라우터 등록·`/api/status` 의 `popups_enabled`), `app/web_security.py`(EXPENSIVE), `app/maintenance.py`(시간 한도 정리), `.env.example`, `cloudflare/validation.mjs`.
- 입력: `region` 은 17개 시·도(별칭 허용, `부산광역시` → `부산`), 아니면 422. `q` 는 NFKC·제어/서식 문자 제거·공백 하나로 정규화 뒤 30자 초과면 422, 앞에 같은 시·도 이름이 있으면 뗌("서울 성수" = "성수"). `visit_date` 는 없으면 한국시간 오늘(`basis: today`), 있으면 오늘 기준 31일 전~366일 뒤만(축제와 같은 폭), 아니면 422.
- 상태: `ready` / `empty`(검색은 됐지만 보여 줄 글 0) / `partial`(검색은 됐지만 거점 좌표 확인 일부 실패) / `unavailable`(블로그 호출 실패·같은 검색 처리 중) / `key_missing`. 스위치가 꺼지면 404.
- 글마다: `id`(`popup-post:` + canonical URL 의 SHA-1 앞 16자, 1b·1c 가 그대로 씀), `title`·`description`(텍스트), `url`(받은 그대로, http/https 만), `blogger`, `posted_at`, `roundup`,
  `period`(`level`: confirmed / month_day / conflict / none, `start`·`end`(연도 확인 시만), `evidence`(요약의 근거 문자열), `status`, `end_only`),
  `place`(`hub_id`·`name`·`kind`·`anchor`·`region`, `level`: building / area_anchor / unverified, `reason`, 확인된 경우만 `lat`·`lon`).
  행사명·묶기 필드는 없습니다.
- 정렬(결정적): 일반 글 → 거점을 읽은 글 → 글 날짜 최신 → 글 ID. 모아 보기 글은 뒤.
- 그 밖에 `sources`(검색원 목록: 검색어·정렬·표시 수·받은 수·캐시 여부), `counts`(shown·general·roundup·location_unknown·hidden_ended·excluded_other_region·not_popup), `hub_checks`(requested·failed·skipped), `attribution`, `rules_version`, `hubs_version`.

### 확정한 캐시·한도 값

| 항목 | 값 | 비고 |
|---|---|---|
| 원본 검색 결과 | 성공 1시간, 팝업 글 0건 10분, 실패 캐시 안 함 | 키: 규칙·사전 버전, 시·도, 정규화 검색어(소문자), 정렬 date, 50건, 1페이지 |
| 방문일 상태 | 캐시 안 함, 요청마다 계산 | |
| 거점 좌표 판정 | 7일 | 상태·등급·위도·경도만 저장(업체 이름·주소는 저장 안 함). 실패는 캐시 안 함 |
| 요청당 외부 호출 | 블로그 1 + 좌표 미캐시 거점 최대 3(많이 나온 거점부터) | 나머지는 `not_checked`(위치 미확인)로 두고 다음 요청에서 확인 |
| 시간 제한·재시도 | 10초, 재시도 없음 | 모두 `observed_http` 경유(제공자 시간당 한도·지표 공유) |
| 같은 키 동시 호출 | 키별 잠금, 2.5초만 기다림(`image_search.LOCK_WAIT_SECONDS`), 넘기면 `unavailable`(busy) | 잠금을 얻은 뒤 캐시를 다시 봄 |
| 전용 한도 | 분당 3회(`ip:popup-search`), 시간당 30회(`popups:hour:`) | 외부 호출이 필요한 요청만 셈. 캐시로 답하면 쓰지 않음. 좌표만 필요한데 한도를 넘으면 429 대신 좌표 확인을 건너뜀 |
| EXPENSIVE | `^GET /api/popups$` | 기존 분당 120 비용 한도 |

설계상 알게 된 것: `web_security.ip_allow(..., seconds=3600)` 로 시간 한도를 두면 범위 이름이 `ip:` 로 시작해, `maintenance.py` 가 `ip:%` 를 분 단위 버킷으로 보고 2분 지난 것을 지우는 규칙에 걸려 시간 한도가 사실상 풀립니다(시간 버킷 번호가 분 버킷 번호보다 훨씬 작음). 그래서 시간 한도는 `popups:hour:` 범위에 두고 `maintenance.py` 에 시간 단위 정리 한 줄을 더했습니다.

### 스위치와 운영 전달

- `DATEMATE_POPUPS_ENABLED`(기본 켜짐, `0/false/off/no` 면 끔): API 404(피드백 탭과 같은 방식), `/api/status` 의 `popups_enabled: false` → 화면이 전환·팝업 칸을 아예 만들지 않음.
- Worker 는 `OPTIONAL_CONTAINER_ENV` 에 있는 이름만 컨테이너로 넘기므로, `DATEMATE_POPUPS_ENABLED`·`DATEMATE_IP_POPUP_SEARCHES_PER_MINUTE`·`DATEMATE_IP_POPUP_SEARCHES_PER_HOUR` 를 추가했습니다(기존 `DATEMATE_IP_EXPLORE_SEARCHES_PER_MINUTE` 는 목록에 없어 운영에서 바꿀 수 없는 상태 그대로).
- 정적 파일: `index.html` 에 `/static/popups.css`·`/static/popups.js` 를 넣었고 `static_pages.versioned_page` 가 두 주소에도 해시를 붙입니다(같은 정규식). 둘 다 같은 출처라 CSP `default-src 'self'`·`script-src 'self'` 안입니다. 공유 화면(`shared.html`)에는 넣지 않았습니다.

## 4. 추출 규칙 v1 재측정 (새 표본)

### 4-1. 순서와 호출

1. 규칙·사전 v1 을 커밋(`bc9fc3a`) → 진단 스크립트 커밋(`b6e201f`) → 호출.
2. 블로그 5건: `{지역} 팝업스토어`, `display=50, start=51, sort=date`(같은 검색어의 2페이지). 모두 200, 197~302ms. 재시도 0.
3. 좌표 확인(지역 검색) 19건(상한 20): 새 표본에서 v0·v1 어느 쪽이든 매칭된 거점마다 1건. 모두 200, 83~201ms.
4. 표본을 본 뒤 v1 오인식 3건을 보고 규칙·사전을 고쳤습니다(**사후 조정 v1.1**, 커밋 `52b1bd4`). 아래 표의 v1.1 열은 공식 수치가 아닙니다.
   - 규칙: "지난 10월 …" 같은 "지난 N월" 도 지난 장소로 봄, 검색 지역 거점과 다른 시·도 거점이 함께 나온 글은 단일 장소로 정하지 않음.
   - 사전: 부산 본점에 별칭 "부산 롯데백화점 본점"(해시태그 "# 부산 롯데백화점본점"이 서울 "롯데백화점 본점"에 걸리던 것).
5. 표본 글 날짜: 서울·부산 11-14, 대구 11-13~14, 강원 11-12~13, 전북 11-10~12. 원본은 `datemate/runtime/popup_stage1/`(Git 제외).
- 진단 스크립트(`scripts/popup_stage1.py`)는 0단계처럼 `observed_http` 를 거치지 않고 httpx 로 직접 불렀습니다(운영 DB 기록·한도와 섞지 않음).

### 4-2. v0 · v1 · v1.1 나란히 (분모 D = 지역별 URL 중복 제거 후 `팝업`이 든 글)

- "위치 확인"은 단일 거점이고 그 거점 좌표 판정이 `verified` 인 글. v0 은 같은 지역 검색 원본을 v0 검증(첫 통과 항목)으로, v1 은 쇼핑 업종 우선으로 판정했습니다. 대구 v0 → v1 의 큰 차이는 대구신세계가 v0 에서 "모호"(입점 매장이 300m 넘게 떨어짐)였다가 v1 에서 백화점 항목으로 확인된 것입니다.
- 부산 기간 후보가 3 → 2 로 준 것은 v1 에서 "열려"가 기간 문맥 낱말이 되어, 한 글(신세계 정기세일)에 기간 후보가 둘이 되어 "충돌(기간 미확인)"로 바뀐 것입니다(넓은 기간으로 합치지 않음).
- 0단계 1페이지 표본의 v0 공식 수치(서울 71%·부산 28%·대구 58%)와 이번 2페이지 수치는 표본이 달라 직접 비교하지 않습니다. 같은 표본 안의 v0 대 v1 만 비교합니다.
- 기간·상태는 여전히 대부분 미확인입니다(오늘 상태 판정 9/218). 1a 화면은 이것을 숨기지 않고 "기간 미확인"으로 보입니다.

### 4-3. 수동 검토 (v1 공식, 지역별 최대 10건)

- 선택: 지역별로 v1 이 기간 후보를 냈거나 거점을 하나 이상 매칭한 `팝업` 글을 canonical URL 의 SHA-1 순으로 최대 10건 → 서울 10, 부산 10, 대구 10, 강원 2, 전북 1 = 33건.
- 판정 기준은 0단계와 같음(낸 것 중 하나라도 어긋나면 오답, 놓침은 오답 아님, 판단 불가는 정답에 넣지 않음). 판정한 것: 채택한 기간, 단일 거점(또는 다른 지역 판정), 모아 보기 분류("애매"는 일반 글로 보이므로 모아 보기 아님으로 봄). 행사명은 운영에서 쓰지 않아 판정하지 않았습니다.
- **추출기를 만든 쪽(이 작업자)의 판정**이고, 판단 범위는 제목·요약까지입니다. 원문 링크를 열지 않았습니다.

## 7. 알려진 문제와 남은 제한

- **기간은 대부분 미확인**: 새 표본에서 오늘 상태 판정 9/218(4%). 실제 서울 응답도 37건 중 연도까지 확인 2건. 화면은 이를 "기간 미확인"으로 숨기지 않고 보입니다.
- **팝업 행사 글이 아닌 글도 섞임**: 제목·요약에 "팝업"이 있으면 보입니다(연예 기사형 글, 세일 안내, 몰 안내 등). 실제 서울 응답 첫 글도 연예인 착용 기사형 글(요약에 팝업스토어 언급)이었습니다.
- **해시태그 오매칭**: "#더현대 대구팝업" 같은 해시태그가 다른 지역 행사 글을 이 지역 거점에 붙임(검토 #21). v1.1 에서도 남아 있습니다.
- **사전 밖 지역**: 강원·전북은 거점이 없어 모두 위치 미확인이고, 강원 검색에 경기 동탄 행사 글이 "위치 미확인"으로 남습니다(다른 지역으로 뺄 근거가 없음).
- **모아 보기 놓침**: "총정리" 글 중 여러 행사 근거가 요약에 안 보이면 일반 글로 둡니다(방침상 애매하면 일반 글).
- **v1.1 의 대가**: 다른 시·도 회차가 함께 적힌 단일 행사 글은 위치 미확인이 됩니다(설산도 사례).
- **한 번 호출 = 하루치**: 최신순 50건이 대도시는 같은 날 글이라, 며칠 전 소개된 팝업은 잘 나오지 않습니다(0단계와 같음).
- **좌표 확인 대기**: 처음 보는 거점이 4곳 이상이면 3곳만 확인하고 나머지는 다음 요청까지 위치 미확인입니다.
- **같은 검색 동시 요청**: 첫 요청이 2.5초 넘게 걸리면 뒤 요청은 "같은 검색을 처리하고 있어요"(unavailable)를 받습니다.
- **조작 한 번 추가**: 헤더 B 안이라 팝업까지 2번 눌러야 하고, 장소 둘러보기를 열 때 기존 장소 검색이 먼저 돕니다(캐시가 없으면 지역 검색 최대 16건).
- 거점 좌표 7일 캐시는 사용자가 정한 값이며, 약관이 허용하는 보관 기간은 0단계처럼 여전히 확인하지 못했습니다.

# 1b. 코스 결과의 팝업 글 구역 + 주변 코스 버튼

이번 범위는 1b 만입니다. 지도(1c)는 만들지 않았고, 팝업 글은 코스 지도·이동선에 연결하지 않습니다.

## 9-1. 사용자 동작이 어떻게 달라졌나

- 코스 결과 화면의 **축제 구역 바로 뒤**(부가 정보 `#plan-extras` 앞)에 "{지역}에서 찾은 팝업스토어 글" 구역이 생겼습니다. DOM 순서도 같아서 모바일 순서는 6-4 의 "… → 축제 → **팝업 글** → 부가" 입니다.
- 적용 화면: 새 추천, 저장된 코스 다시 열기(`/?plan=`), 새로고침으로 이어받은 검색. 공유 화면(`/shared`)은 `popups.js` 를 읽지 않아 구역이 없고 `/api/popups` 도 부르지 않습니다.
- 구역 머리: "네이버 블로그 검색 결과예요. 기간과 장소는 원문에서 확인해 주세요." / "코스에 넣지 않은 주변 후보예요. 주변 코스 버튼은 출발지만 그 장소로 바꾸고 날짜·시간·예산·교통·취향은 그대로 다시 추천해요."

## 9-3. 표시 규칙

- 조회: 코스 조건의 `region` 과 `visit_date` 로 `GET /api/popups` 를 코스·지도와 **따로** 부릅니다(코스 결과 표시를 기다리게 하지 않음). 새 추천·이어받기·다시 열기·"다시 찾기"마다 이전 요청을 `AbortController` 로 취소하고(기존 `api()` 가 `signal` 을 지원), 취소와 별개로 generation 으로 성공·오류·로딩 끝·카드 갱신을 모두 거릅니다.
- 기본 목록: 위치가 확인된 글(`building` / `area_anchor`, 좌표 있음)만. 출발지가 있으면 직선거리 가까운 순, 같으면 글 ID 순(같은 거점 글은 거리가 같음). 출발지가 없으면(데모, 이어받은 검색) 거리 없이 받은 순서이고 목록 제목에 "출발지 기준이 없어 받은 순서"라고 적습니다. 첫 6건 + "글 더 보기 (N건)".
- 거리 문구(읽은 정보 칸의 "거리" 줄): 건물 "출발지에서 직선거리 약 3.1km"(축제와 같은 문구), 동네 기준점 "출발지에서 직선거리 약 2km · 성수 일대 기준"(1km 미만은 "1km 이내"). 동네 기준점은 대략 위치라 km 단위로만 적었습니다. 고른 거점 글은 곧 출발지라 거리를 적지 않습니다.
- 위치 미확인 글: 기본으로 접고 "위치를 확인하지 못한 글 N건 보기"(aria-expanded)로 펼칩니다. 거리를 만들지 않고 버튼 대신 "위치를 확인하지 못해 주변 코스 추천을 할 수 없어요."
- 종료로 확정된 글: 서버가 이미 목록에서 뺍니다(1a, `hidden_ended`). 구역은 "… 종료로 확인된 글 n건은 숨겼어요."와 "다른 시·도 장소로 읽힌 글 n건은 뺐어요."를 한 줄씩 알립니다.
- 모아 보기 글은 따로 나누지 않고 같은 목록에 두되 읽은 정보 칸에 "종류: 여러 팝업을 모아 소개한 글" 줄을 붙입니다.
- 상태: 찾는 중(aria-busy) / 정상 / 정상이지만 위치 확인 0건("위치를 확인한 글이 없어 거리순으로 보여 드릴 글이 없어요." + 미확인 펼치기) / 글 0건 / partial(일부 좌표 확인 실패 안내 + 목록) / unavailable·HTTP 오류(다시 찾기) / 키 없음(버튼 없음) / 429(서버 문구 + 다시 찾기) / 방문일 범위 밖 422(서버 문구) / 스위치 꺼짐(구역 자체를 만들지 않음, 페이지를 연 뒤 꺼져 404 가 오면 구역을 내림). 실패 문구에는 "코스 추천에는 영향이 없어요."를 붙입니다.

| | 내용 |

- 팝업을 고른 상태에서 축제 버튼: 팝업 안내가 사라지고 축제 안내만 남습니다. 축제 쪽 "원래 조건으로 다시 추천"은 축제 코드(고치지 않음)대로 축제 직전 조건, 곧 팝업 거점 출발지로 돌아갑니다(팝업 안내는 되살리지 않음).

- 1a 의 한계(기간 대부분 미확인, 팝업 행사가 아닌 글 섞임, 해시태그 오매칭, 한 번 호출 = 하루치)는 그대로입니다.

# 1c. 코스 결과 구역을 거점별 묶음으로 + 코스 지도의 팝업 표시 층

이번 범위는 1c 만입니다(2026-11-15 새벽 작업, 브랜치 `popup-stage1`). 서버·API·축제 파일은 고치지 않았습니다.

## 10-1. 왜 묶음으로 바꿨나 (1b 의 문제)

- 1b 실제 화면(서울 성수, 390px)에서 구역 높이가 약 4,600px 였고, 첫 6개 글이 모두 "성수 일대"라 장소 줄·거리 줄·버튼·버튼 옆 상태 글자가 글마다 6번 되풀이됐습니다(9-8 의 "같은 뜻의 버튼이 여러 번").
- 9-2 에서 B 안(거점별 묶음)을 버린 이유는 "첫 6개를 글 단위로 센다"는 규칙과 맞추기 위해서였는데, 실제 데이터에서는 그 규칙이 같은 정보의 반복으로 나타났습니다. 그래서 B 안으로 바꿉니다. 글 단위 약관 대응(제목·요약·링크 그대로, 글끼리 합치지 않음)은 묶음 안에서 그대로 지킵니다.

## 10-2. 묶음 구조와 순서

- 목록 제목: "위치를 확인한 글 N건 · 장소 M곳 · 출발지에서 가까운 순(직선거리)" (출발지가 없으면 "… 출발지 기준이 없어 받은 순서").
- 묶음 머리(회색 바탕, 점선 아래 경계 = 데이트메이트가 읽은 정보): "데이트메이트가 검색 요약에서 읽은 장소" / 거점 이름(동네는 "성수 일대(대략)") + "검색된 글 N건"(이번 검색 범위의 글 수일 뿐, 인기 지표로 쓰지 않음) / 위치 줄(건물 "건물 위치 확인 · 층·입구는 원문 확인", 동네 "동네 기준점 성수역 · 대략 위치") / 거리 줄(한 번) / "이 장소(이 일대) 주변 코스 추천받기" 버튼(한 번)과 버튼 옆 상태 글자.
- 버튼 옆 상태: 묶음의 글마다 기간이 다를 수 있어 하나로 정하지 않고 글 수로 적습니다. 예: "방문일 기준 진행 중 1건 · 기간 미확인 13건 · 방문일에 열리는지 글마다 원문에서 확인해 주세요." 글이 1건이면 1b 문구 그대로, 모두 진행 중이면 적지 않음.
- 묶음 안의 글(독립 항목): 출처 줄, 제목, 요약(줄 수를 자르지 않음), "블로그 원문 보기 ↗", 읽은 정보 칸의 기간 줄(방문일 기준 상태 포함)과 모아 보기 글이면 종류 줄. 장소·거리·버튼은 글마다 되풀이하지 않습니다.
- 순서: 묶음은 출발지에서 가까운 순, 같으면 거점 ID. 출발지가 없으면 거점이 처음 나온 순서. 묶음 안은 진행 중 → 오픈 예정 → 나머지, 같으면 글 ID. 글마다 거점이 다르면 1b 와 같은 순서가 됩니다(동률 기준만 글 ID → 거점 ID).
- 첫 화면: 묶음마다 글 1건 + "이 장소의 글 N건 더 보기", 묶음 3곳 + "다른 장소 N곳 더 보기". 더 보기를 누르면 새로 열린 첫 항목으로 포커스를 옮깁니다.
- 그대로 둔 것: 위치 미확인 글 접기(펼친 안내에 "지도에도 표시하지 않아요"를 더함), 다른 시·도 제외·종료 숨김 안내, 각 상태 문구, 고른 거점 안내와 되돌리기, generation 처리. 둘러보기(1a) 목록은 바꾸지 않았습니다(공용 `PopupView.card` 에 `place:false`·`titleTag` 선택값만 더함, 1a 테스트 통과).

### 첫 화면 분량과 실측 높이 (390px, `#popup-course` 높이)

같은 실제 응답(서울, 방문일 2026-11-15, 팝업 글 38건 · 위치 확인 21건 · 거점 5곳 · 성수 일대 14건)으로 쟀습니다. 묶음 머리를 한 번 줄인 뒤(이름과 글 수 한 줄, 좁은 화면에서도 이름표·내용 한 줄, 위치 문구 단축)의 값입니다.

| 글/묶음 × 묶음 수 | 높이 |
|---|---|
| 1b(글 단위, 첫 6건) | 약 4,600px (1b 실측, 보고 값) |
| 2 × 4 (작업 지시의 기본값, 머리 줄이기 전) | 4,289px (실제 추천 화면에서는 4,424px) |
| 2 × 4 (머리 줄인 뒤) | 4,021px |
| 1 × 4 | 3,342px |
| **1 × 3 (선택)** | **2,647px** (1b 대비 약 43% 감소) |

- 2 × 4 는 머리를 줄여도 4,021px 로 거의 줄지 않았습니다. 글 하나가 약 370~390px(요약이 4~5줄, 원문 링크 44px, 기간 칸)이고 실제 데이터는 성수 일대에 글이 몰려 있어, 높이를 정하는 것은 묶음 수보다 "보이는 글 수"였습니다.
- 1 × 3 을 고른 이유: 지도에는 모든 거점이 표시되므로 첫 화면에서 장소 정보를 잃지 않고, 각 묶음에 대표 글 1건(진행 중·오픈 예정이 있으면 그 글)이 보입니다. 요약은 CSS 로 줄 수를 자르지 않았고 버튼 44px·본문 14px 이상은 그대로입니다(4개 폭 테스트).

## 10-3. 지도 표시 층 구조와 생명주기 (`static/maps.js`)

- 데이터: `PopupCourse.mapItems` = 카드 묶음과 **같은 배열**(위치 확인된 거점의 `{hub, posts, meters}`). 카드 묶음 수 = 지도 표시 수, 위치 미확인 글은 둘 다에 없습니다. `PopupCourse.setMapItems()` 가 값을 바꾸고 화면의 `.plan-map` 마다 `updatePopups()` 를 부릅니다(축제의 `FestivalPanel.mapItems`/`refreshMaps` 와 같은 모양, 축제 파일은 고치지 않음).
- `drawPlanMap` 안에 축제와 별도의 `popupMarkers`(정리 함수 배열)·`clearPopups`·`wrap.updatePopups`·`map-popup-note` 줄을 둡니다. 축제 관련 줄은 `wrap.append/replaceChildren/prepend` 에 새 안내 줄을 더한 것과 `disposeMap`·`render`·`fallback` 에 팝업 정리 한 줄씩을 더한 것뿐입니다.
- 네이버: `naver.maps.Marker`(icon content 는 고정 문자열 두 개뿐, 거점 이름·글 제목은 `title` 과 정보창 DOM 텍스트로만), `InfoWindow({content: popupMapInfo()})`, 클릭 리스너. 정리 때 정보창 닫기 → 리스너 제거 → `setMap(null)`.
- Leaflet: `L.marker` + `L.divIcon({html: node()})`(요소를 넘기므로 Leaflet 이 innerHTML 을 쓰지 않음), `bindPopup(DOM)`, `title`, 키보드 포커스. 정리 때 `closePopup → unbindPopup → off → remove`.
- 생명주기: 새 조회 시작(`load`) 때 바로 비움 → 이 세대 응답이 성공했을 때만 채움(지난 세대 응답은 `render` 전에 버려져 표시도 바뀌지 않음) · 실패·키 없음·0건이면 빈 채로 · 지도가 늦게 만들어져도 만들 때 `mapItems` 를 읽음 · 네이버→Leaflet 전환 때 네이버 표시를 지우고 Leaflet 에 같은 데이터를 다시 그림 · 코스 탭 전환(지도 다시 그림) 때 새 지도가 같은 데이터를 읽음 · `disposeMap` 에서 정리.
- 지도 범위: 팝업 표시는 `bounds.extend`·`fitBounds`·`setView` 에 넣지 않습니다(Leaflet 의 크기 변화 `fit` 도 코스 좌표만). 그래서 코스 범위 밖 거점의 표시는 화면 밖에 있을 수 있습니다(사용자가 지도를 움직여 봄). 이동선(`route-leg`)에도 잇지 않습니다.
- 정리 견고성: 네이버 인증 실패 뒤에는 SDK 마커의 `setMap` 이 오류를 낼 수 있어(10-6 실측), 팝업 정리 함수는 하나씩 `try` 로 감쌌습니다. 팝업 표시 때문에 대체 지도 전환이 새로 막히지 않게 하기 위해서입니다.

## 10-4. 표시 모양 선택

| 대상 | 모양 | 글자 |
|---|---|---|
| 코스 장소 | 홍색 채운 원(38px) | 번호·"출발"·"귀가" |
| 축제 | 노란 알약, 점선 갈색 테두리 | "축제" |
| 팝업 · 건물 | 흰 바탕 **네모**(모서리 2px), 청색 실선 3px | "팝업" |
| 팝업 · 동네 기준점 | 같은 네모, **점선** 테두리 | "팝업 일대" |

- 이유: 원(코스)·알약(축제)과 겹치지 않는 세 번째 모양이 네모이고, 흰 바탕이라 채운 원·노란 알약과 나란히 있어도 구분됩니다. 건물/동네는 테두리 실선/점선과 "일대" 글자 두 가지로 나눠 색만으로 구분하지 않습니다.
- 색: 새 색 없음. 기존 `--cheong`(청)·`--paper` 만 씁니다. CSS 는 `popups.css` 에만 두었고 `!important` 없음.
- 범례: `mapLegend` 끝에 "네모 ‘팝업’은 팝업 글에서 읽은 주변 장소예요(코스·이동선에 넣지 않음). 점선 네모 ‘팝업 일대’는 동네 기준점이라 위치가 대략이에요."를 붙이되 팝업 표시가 있을 때만 보입니다. 지도 아래에는 축제 줄과 별도로 "네모 ‘팝업’ 표시: 팝업 글에서 읽은 장소 N곳 (코스에 포함되지 않은 주변 후보예요 · 위치를 확인하지 못한 글은 지도에 없어요)".
- 정보창: 거점 이름, 위치 등급, "코스에 포함되지 않은 주변 후보예요. 기간과 장소는 원문에서 확인해 주세요.", "검색된 글 N건 · 네이버 블로그", 글 제목 링크 처음 3건, 더 있으면 "외 N건 · 아래 팝업 글 구역에서 모두 볼 수 있어요". 모바일 지도(290px)보다 길지 않게 최대 220px 안에서 스크롤합니다.

## 10-7. 스크립트 오류(`capitalize`/`isArray`)는 기존 문제인가

- 같은 조건 비교: 홈(390px, `http://127.0.0.1:8000`, CSP 켬) → 실제 축제 자료(서울, 2026-11-15, 17곳) → 합성 코스로 `drawPlanMap`(실제 네이버 키) → 12초 대기. 이 브랜치와 main(9213e13, `git worktree` 로 따로 꺼내 이미지를 만들고, 로컬 볼륨의 복사본·같은 compose 설정·같은 포트로 띄움)에서 각각 1회.
- 결과: **둘 다 같은 오류**가 같은 경로로 납니다. `Cannot read properties of null (reading 'capitalize')` ← 네이버 SDK `setMap` ← `clearFestivals`(maps.js) ← `fallback` ← `showMapFallback` ← `navermap_authFailure`. 둘 다 인증 401, 대체 지도·축제 표시 없음.
- 원인(스택으로 확인): 네이버 인증 실패 알림이 축제 마커를 올린 **뒤에** 오면, `fallback` 이 첫 줄에서 축제 마커를 `setMap(null)` 로 지우려다 SDK 내부 오류로 멈추고, 그 뒤의 Leaflet 대체 지도 그리기가 실행되지 않습니다. **이번 변경 때문이 아니라 main 에도 있는 기존 문제**입니다.
- 이번 작업은 축제 줄을 고치지 않았습니다(작업 범위·지시). 팝업 정리만 `try` 로 감싸 팝업 표시가 이 문제를 새로 일으키지 않게 했습니다. 고치려면 `clearFestivals` 의 정리도 같은 방식으로 감싸는 한 줄 변경이면 될 것으로 보이며, 축제 동작 변경이라 따로 결정이 필요합니다.
- `isArray` 는 이번 두 번의 확인에서 나오지 않아 원인을 가리지 못했습니다.

## 10-8. 알려진 문제

- 위 10-7 의 기존 문제: 운영 주소에서 네이버 인증이 늦게 실패하면 대체 지도도 나오지 않습니다(축제가 있을 때). 운영 주소는 등록돼 있어 보통은 인증이 성공할 것으로 추정하지만 확인하지 않았습니다.
- 팝업 표시는 지도 범위를 넓히지 않아 코스 범위 밖 거점은 처음 화면에 안 보일 수 있습니다(의도: 코스 지도를 팝업이 흔들지 않음). 지도 아래 줄의 "N곳"으로 수는 알 수 있습니다.
- 동네 기준점이 출발지와 같은 곳이면(성수 카드 출발지 = 성수역) "팝업 일대" 표시가 "출발" 표시와 겹칩니다.
- 실제 데이터에서 성수 일대 묶음의 대표 글이 "[용산 팝업] … 안전가옥 팝업스토어" 였습니다. 요약에 성수가 함께 적혀 거점이 성수로 읽힌 것으로, 1a 의 거점 매칭 한계(해시태그·여러 장소 언급)가 묶음 대표 글 자리에 드러난 사례입니다.
- 묶음을 바꾸지 않은 1b 의 한계(저장 코스·이어받은 검색에서 누른 버튼은 조건 화면 값을 씀, 고른 거점은 메모리에만 있음 등)는 그대로입니다.
- Leaflet 정보창이 지도 왼쪽 위 확대·축소 단추 아래에 일부 가립니다(Leaflet 기본 층 순서). 정보창 안 스크롤로 내용은 모두 읽을 수 있습니다.

9. **남은 제한과 알려진 문제**: 기간 대부분 미확인(표본 4%), 팝업 행사가 아닌 글 섞임, 해시태그·여러 장소 언급 오매칭(성수 묶음 대표 글이 용산 행사 글이었던 사례), 강원·전북 거점 없음, 한 번 호출 = 최신 50건(대도시는 하루치), 좌표 확인 요청당 3곳, 저장 코스·이어받기에서 버튼은 조건 화면 값 사용, 고른 거점은 메모리에만. 기존 문제: 네이버 인증이 축제 마커를 올린 뒤 실패하면 `clearFestivals` 에서 오류가 나 대체 지도가 그려지지 않음(main 9213e13 에서도 같은 스택으로 재현, 10-7).
