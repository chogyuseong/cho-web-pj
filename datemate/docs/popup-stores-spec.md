# 작업 계약: 데이트메이트에 신뢰할 수 있는 팝업스토어 탐색 기능 추가

작성: 2026-11-14. 사용자가 준 작업 프롬프트(1~19절)에, 저장소와 대조해 나온 보정 사항(0절)을 더한 문서입니다.
**0절과 본문이 충돌하면 0절이 우선합니다.**

## 0. 보정 사항 (저장소 대조 결과, 본문보다 우선)

### 0-1. 저장소 사실

- 경로는 모두 `datemate/` 아래입니다: `datemate/app/…`, `datemate/static/…`, `datemate/tests/…`, `datemate/scripts/…`.
  `README.md` 와 `배포-이어가기.txt` 만 저장소 최상위에 있습니다.
- 저장소에 `AGENTS.md` 는 없습니다.
- `node()`·`button()`·`link()` 는 `datemate/static/app.js` 에 있습니다. 공유 화면(`shared.js`)에는 `node`·`link` 만 따로 있습니다.
- 네이버 검색은 NAVER API HUB(`https://naverapihub.apigw.ntruss.com/search/v1/{blog,local,image}`, 헤더 `X-NCP-APIGW-API-KEY-ID`·`X-NCP-APIGW-API-KEY`)를 씁니다.
  뉴스(`/search/v1/news`)는 코드 어디에서도 쓰지 않고, 문서에는 "지역·블로그·이미지 권한 활성화"만 적혀 있습니다.
- 외부 호출은 `observed_http`(app/telemetry.py)를 거치고, 제공자별 시간당 한도(`DATEMATE_PROVIDER_CALLS_PER_HOUR`, 기본 600)를 추천과 함께 씁니다.
- 이 컴퓨터는 가상환경의 DLL 이 Windows 정책에 막혀 있습니다. 파이썬 실행과 테스트는 Docker 로 합니다
  (`배포-이어가기.txt` 2번·5번, 이미지 `datemate-test:local` 이 남아 있는지 먼저 확인).
- 실제 키는 `datemate/.env` 에 있습니다. 값을 읽어 출력하거나 파일·로그·보고에 남기지 않습니다(컨테이너에는 `--env-file` 로만 전달).

### 0-2. 0단계 실측 보정

1. **뉴스 권한**: 뉴스는 먼저 1건만 호출해 봅니다. 인증·권한 오류면 HTTP 상태와 오류 코드를 기록하고 뉴스 표본 없이 블로그만으로 진행합니다.
   이때 "뉴스 실측 불가(권한)"를 보고 맨 위에 적고, 블로그 표본을 늘려 메우지 않습니다.
2. **표본 지역**: 서울·부산·대구에 **강원·전북**을 더합니다(총 최대 500건). 비수도권 두 곳은 "결과 없음·후보 0건" 비율을 보기 위한 것입니다.
   검색 호출은 최대 10건(5지역 × 블로그·뉴스)입니다.
3. **거점 사전 고정**: 검색을 호출하기 전에 거점 사전 v0 을 확정해 파일로 남깁니다. 표본을 본 뒤 사전을 고치지 않습니다.
   v0 으로 잰 매칭률이 공식 수치입니다. 매칭되지 않았지만 자주 나온 장소명은 "사전 후보" 표로 따로 보고하고,
   사전을 고쳐 다시 잰 수치는 추가 실험 표에만 둡니다.
4. **분모 통일**: 기간 추출률·거점 매칭률·이름 식별률의 분모는 "지역·검색원별로 URL 중복 제거 후 제목·요약에 `팝업`이 들어간 글 수"입니다.
   설계 재검토 조건의 30% 도 이 분모입니다. 다른 분모를 쓰는 수치는 그렇다고 적습니다.
5. **연도 반사실 측정**: 엄격한 연도 정책(6절)의 수치가 공식입니다. 그와 별도 열로, 채택하지 않는 가정
   "연도 없는 월·일을 출처 날짜(블로그 postdate, 뉴스 pubDate)의 연도로 읽었다면"의 판정 가능 건수와 그 가정에서 발견한 오인식 사례를 보고합니다.
6. **수동 검토 표본 공개**: 검토한 글은 지역·검색원·제목·요약·출처 날짜·URL·추출 결과·판정(정답/오답/판단 불가)·사유를 표로 남겨
   사용자가 직접 다시 볼 수 있게 합니다. 추출기를 만든 쪽의 판정이라는 점을 보고에 적습니다.
7. **약관 확인**: 네이버 검색 API(NAVER API HUB) 이용 조건에서 검색 결과의 캐시 보관과 제목·요약 표시에 관한 조항을 공식 문서로 확인해 보고합니다.
   찾지 못했으면 찾지 못했다고 적습니다.
8. **좌표 확인 호출**: 0단계의 지역 검색(거점 좌표 확인)은 표본에서 실제로 매칭된 거점에 한해 거점당 1건, 최대 30건입니다.
9. **근접성 수치**: 사용자의 두 번째 질문("내 코스와 얼마나 가까운가")에 답할 수 있는지 보려고, 위치가 확인된 후보를 대상으로
   홈 인기 동네 좌표(서울 성수, 부산 해운대) 기준 직선거리 분포(2km·5km·10km 이내 건수)를 보고합니다.

### 0-3. 0단계 산출물과 Git

- 로컬 브랜치 `popup-stage0` 에서 작업합니다. main 은 건드리지 않습니다. push 와 배포는 하지 않습니다.
- 산출물: 진단 스크립트(`datemate/scripts/`), 순수 함수 모듈(`datemate/app/popups.py` — 라우터 등록·운영 연결 없음),
  그 단위 테스트(`datemate/tests/`), 보고서(`datemate/docs/popup-stage0-2026-11-14.md`), 이 계약 문서.
- 실제 응답 원본(블로그·뉴스 제목과 요약 전체)은 Git 에 올라가지 않는 `datemate/runtime/` 아래에만 둡니다.
  보고서에는 수동 검토 표와 오인식 사례에 필요한 만큼만 인용합니다.
- 관련 검사(새 단위 테스트, `scripts/format_sources.py --check`)가 통과한 0단계 변경만 그 브랜치에 커밋합니다.

### 0-4. 1단계에 적용할 보정 (0단계에서는 구현하지 않고, 보고의 "구현 계약"에 반영)

1. **주변 코스 추천 버튼**: 축제 버튼(`FestivalPanel.planAround`)은 출발지·지역을 바꾸고, 방문일을 축제 기간 안으로 옮기고,
   요청에 `festival` 기준점을 실어 저장합니다(app/models.py 의 `FestivalAnchor`). 팝업 버튼은 **출발지(와 필요하면 지역)만 바꾸고 방문일은 옮기지 않습니다.**
   팝업을 `festival` 필드에 싣지 않습니다(저장된 코스가 축제로 복원됨). 기준점 필드가 필요한지, 없이 출발지만으로 충분한지는 0단계 보고에서 근거와 함께 제안합니다.
2. **전용 요청 제한**: 팝업 조회에는 `EXPENSIVE` 등록과 별도로 `require_ip` 전용 한도를 둡니다(피드백 탭의 방식).
   둘러보기의 자유 검색어가 추천과 함께 쓰는 시간당 제공자 한도를 소진하지 못하게 하는 값이어야 합니다.
3. **끄는 스위치**: 환경변수 하나(예: `DATEMATE_POPUPS_ENABLED=0`)로 탭·구역·API 를 내릴 수 있게 합니다.
4. **헤더**: 지금 메뉴 4개도 320px 에서 "피드백"이 둘째 줄입니다. 디자인 비교(14절)에 "다섯 번째 탭" 안과
   "장소 둘러보기 안의 전환" 안을 함께 넣고, 320·390px 에서 헤더가 몇 줄이 되는지 실측해 고릅니다.
5. **적용 화면**: 첫 구현의 코스 결과 구역은 새 추천, 저장된 코스 다시 열기, 새로고침으로 이어받은 검색에 나옵니다. 공유 화면(`/shared`)에는 넣지 않습니다.
6. **단계 분할**: 1단계는 1a(서버 API + 둘러보기) → 1b(코스 결과 구역 + 주변 코스 버튼) → 1c(지도 레이어)로 나누고,
   각 단계가 끝날 때마다 검사 결과를 보고합니다.
7. **계측**: 뉴스 호출을 쓰게 되면 `app/perf_trace.py` 의 종류 표에 `/search/v1/news` 를 더합니다.

### 0-5. 1단계 확정 사항(2026-11-14)

사용자가 0단계 보고 8절 초안을 아래처럼 고쳐 확정했습니다. 본문(3·6·8·9·11절 등)과 충돌하면 이 절이 우선합니다.

1. **범위는 "출처 중심 팝업 탐색"**: 글(출처) 하나 = 항목 하나. 행사명 추출·행사명 묶기는 운영 경로(API 응답·화면)에 쓰지 않습니다(코드는 남겨도 됨). 모아 보기 글 구분은 유지하되 애매하면 일반 글로 둡니다.
2. **약관(0단계 보고 2-3)**: 제목·요약·URL 은 바꾸지 않고(강조 태그·엔티티만 텍스트로) 글마다 독립 항목으로 보입니다. 우리가 읽은 정보(거점·위치 등급·직선거리·기간 근거)는 원문 인용과 시각·구조적으로 나뉜 별도 줄에 "검색 요약에서 읽은 …"처럼 출처를 밝혀 둡니다. 화면에 "네이버 블로그 검색 결과" 출처 표기, 광고 요소 없음.
3. **캐시**: 원본 검색 결과 성공 1시간, 결과 0건 10분, 실패는 캐시 안 함. 방문일 상태는 캐시하지 않고 요청마다 계산. **거점 좌표 캐시는 7일**(8절·11절의 30일을 대체. 기존 서비스의 최장 지역 검색 보관 기간을 넘지 않음).
4. **뉴스는 구현하지 않음**(이 Application 에 권한 없음, 401). 블로그만. 응답에 검색원 목록(`sources`)을 두어 나중에 붙일 수 있게 하되, 호출 코드·테스트 안 되는 분기는 만들지 않습니다. "일부 실패(partial)"는 "검색은 됐지만 일부 거점 좌표 확인이 실패"한 경우입니다.
5. **기간 표시**: 연도까지 확인된 기간만 날짜로 표시하고 7절 표대로 판정. 나머지는 "기간 미확인"(월·일 근거가 있으면 "검색 요약에 적힌 날짜: …"로 원문 그대로, 연도를 채우지 않음). 종료로 확정된 글만 기본 목록에서 숨깁니다.
6. **지역**: 거점이 확인됐고 그 시·도가 요청 지역과 다르면 목록에서 빼고 뺀 건수를 응답에 담습니다. 거점 미확인 글은 지역을 단정하지 않고 "위치 미확인"으로 뒤에 둡니다.
7. **요청 제한**: `EXPENSIVE` 에 `^GET /api/popups$` 등록 + 외부 호출이 필요한 요청에만 전용 한도 둘(분당 3회 `DATEMATE_IP_POPUP_SEARCHES_PER_MINUTE`, 시간당 30회 `DATEMATE_IP_POPUP_SEARCHES_PER_HOUR`). 요청당 외부 호출 상한: 블로그 1 + 좌표 미캐시 거점 최대 3. 재시도 없음, 시간 제한 10초, `observed_http` 경유.
8. **끄는 스위치** `DATEMATE_POPUPS_ENABLED`(기본 켜짐). 0 이면 API 404, 화면은 전환을 그리지 않음(`/api/status` 의 `popups_enabled`). Worker 가 넘기는 환경변수 목록(`cloudflare/validation.mjs`)에 포함.
9. **추출 규칙 v1**: 거점(별칭 안 띄어쓰기 허용, "지난번·이어·비교" 문맥 거점 제외, 지역 검색에서 백화점·쇼핑시설 업종 우선)과 기간(괄호 없는 요일, "에서 … 까지", 두 자리 연도 "26년", 매장 개점일 같은 비행사 날짜 제외). 규칙·사전 버전 문자열은 캐시 키에 들어갑니다. 사전 v1 에 부산·대구 보강과 0단계 보고 3-4 "사전 후보"(검증 가능한 별칭만). v1 재측정은 같은 검색어의 2페이지(start=51, 50건, 최신순) 5지역 새 표본으로 하고, 표본을 본 뒤 고친 규칙의 수치는 "사후 조정"으로 따로 적습니다.

# 작업: 데이트메이트에 신뢰할 수 있는 팝업스토어 탐색 기능 추가

너는 운영 중인 소규모 웹서비스를 개선하는 구현 책임자다. 검색 데이터의 한계, 기존 코드의 구조, 실제 사용 흐름을 함께 판단해라.

저장소는 `cho-web-pj`, 기술 스택은 FastAPI + 바닐라 JS다.

목표는 기능 세 개를 채우는 데 그치지 않는다.

사용자가 데이트 코스를 확인하는 순간 다음을 빠르게 판단할 수 있어야 한다.

- 방문일에 관련된 팝업 후보가 있는가.
- 내 코스와 얼마나 가까운가.
- 기간과 장소 중 무엇이 확인되었고 무엇이 불확실한가.
- 이 후보를 기준으로 주변 코스를 다시 찾아볼 가치가 있는가.

검색 결과가 부족하면 부족한 상태를 정직하고 유용하게 보여줘라. 빈 화면을 피하려고 기간·장소·행사명을 추정해서 채우지 마라.

---

## 1. 이번 실행 범위: 0단계까지만 수행하고 중단

이 문서에는 전체 구현 계약이 포함되어 있지만, 첫 실행에서는 **0단계 데이터 실측과 구현 가능성 보고까지만** 수행해라.

0단계에서 허용하는 작업:

- 저장소와 관련 공식 문서 읽기.
- 기존 검색 클라이언트·캐시·보안 구조 확인.
- 별도 진단 스크립트 작성.
- 날짜 추출·거점 매칭·묶기 등 순수 함수의 최소 구현과 검증.
- 기존 설정의 실제 키를 사용한 제한된 조회.
- 수치와 실제 사례를 포함한 진단 보고.

0단계에서 하지 않을 작업:

- 헤더·코스 결과·지도 등 운영 UI 변경.
- 신규 운영 API 연결.
- 기존 축제 코드 리팩터링.
- 배포, push, 운영 데이터 수정.

실제 키가 없거나 외부 호출이 차단되면 이를 명확히 보고해라. 가짜 데이터로 실제 키 검증을 대체하거나 임의로 1단계에 진입하지 마라.

0단계 보고 후 멈춰라. 사용자가 구현 진행을 지시하면 아래 계약에 따라 1단계를 수행한다.

- `drawPlanMap`과 네이버 지도·Leaflet 전환 구조.
- `node()` / `link()` / `button()`의 실제 구현.
- 헤더 탭과 탐색 화면 전환.
- 축제의 “주변 코스 추천” 동작.
- 네이버 검색 제공자·인증·설정.
- `require_ip`, `web_security.EXPENSIVE`, `store.cache`.
- 관련 테스트와 `tests/test_header_wrap_ui.py`.
- `scripts/format_sources.py`, `app.js` 포맷 검사.
- SQLite 테스트 실행 방법.

확인하지 않은 함수·파일·설정을 존재한다고 가정하지 마라.

작업 시작 시 기존 변경사항과 관련 테스트 상태를 확인하고, 사용자 변경을 보존해라. 이번 작업과 관계없는 재작성·정리·프레임워크 교체는 하지 마라.

## 3. 구현할 사용자 기능: 세 가지

### A. 코스 결과의 팝업 후보 구역

기존 축제 구역과 자연스럽게 이어지는 위치에 제공한다.

- 방문일과 코스 대상 지역을 기준으로 조회.
- 검색된 후보 중 출발지에서 가까운 순으로 표시.
- 직선거리임을 명시.
- 기간·위치의 확인 수준을 표시.
- 출처와 원문 링크 제공.
- “이 팝업 주변 코스 추천받기” 제공.

검색 결과만으로 방문일 운영을 확인하지 못했다면, 구역 제목이나 문구가 운영 중인 팝업 목록처럼 단정하지 않아야 한다.

예를 들어 “이 지역에서 찾은 팝업” 아래에 방문일 기준 상태를 표시하는 방식을 검토해라.

### B. 코스 지도에 팝업 후보 표시

`drawPlanMap`의 기존 흐름에 연결하되, 팝업은 독립 레이어로 관리한다.

- 네이버 지도와 Leaflet 모두 지원.
- 코스 장소·축제와 형태로 구분.
- 위치 확인 수준을 표현.
- 팝업 실패가 기본 지도나 코스 표시를 방해하지 않음.

팝업 후보를 실제 코스 방문지처럼 이동 노선에 연결하지 마라.

### C. 헤더의 “팝업 둘러보기” 탭

장소 둘러보기의 기존 구조를 재사용한다(탭으로 둘지 둘러보기 안의 전환으로 둘지는 0-4 의 4).

- 시·도 선택.
- 검색어 입력.
- 한국시간 오늘 기준 상태 표시.
- 팝업 후보와 모아 보기 글을 구분.
- 결과 없음·일부 조회 실패·전체 조회 실패를 구별.

첫 구현에서 새로운 날짜 선택 UI를 추가하지 않는다. 코스 결과는 선택한 방문일, 둘러보기는 한국시간 오늘을 기준으로 한다.

## 4. 데이터 취득 범위: 검색 결과만 사용

사용할 데이터:

- 네이버 블로그 검색 API.
- 네이버 뉴스 검색 API.
- 거점 좌표 확인을 위한 네이버 지역 검색 API.

금지:

- 검색 결과 링크를 따라가 원문 HTML 가져오기.
- 타 사이트 크롤링.
- LLM을 이용한 추출·보정.
- 다른 데이터 제공자로 조용히 대체.
- 하드코딩한 행사 일정이나 가짜 팝업 데이터로 빈 결과 채우기.

블로그·뉴스의 분석 입력은 API가 반환한 제목·요약·출처 URL·출처 날짜뿐이다.

`description`은 원문 전체가 아니다. 제목·요약에 없는 사실을 읽었다고 주장하지 마라.

검색 제공자의 공식 문서를 확인하고 다음을 구별해라.

- NAVER API HUB와 다른 네이버 검색 API의 호스트·인증 방식.
- 공식 문서상 지원 여부.
- 현재 프로젝트 키의 실제 사용 가능 여부.

뉴스 `/search/v1/news`는 공식 문서 확인과 실제 호출 검증을 별도로 보고해라.

## 5. 0단계 실측 방법과 보고

### 표본

기본 표본은 다음과 같다(0-2 의 2 로 지역이 5곳이 됨).

- 지역: 서울·부산·대구·강원·전북.
- 검색어: 각 지역명 + `팝업스토어`.
- 검색원: 블로그·뉴스 각각.
- 정렬: 최신순.
- 각 조합에서 최대 50건, 첫 페이지.
- 총 최대 500건.

실제 API 제한이나 프로젝트 정책이 다르면 표본 변경 이유와 실제 요청 조건을 기록해라. 결과가 적으면 반환된 수만 사용한다.

표본 결과를 보고 난 뒤 유리한 검색 조건으로 바꾸고 최초 결과처럼 보고하지 마라. 추가 실험은 별도 표로 구분해라.

### 반드시 보고할 수치

지역별·검색원별로 다음을 보고한다.

- 실제 요청 수, HTTP 상태, 오류 코드.
- 반환 글 수.
- URL 기준 중복 제거 후 글 수.
- `팝업` 또는 `팝업스토어` 포함 비율.
- 기간 후보 추출률.
- 거점 매칭률.
- 이름까지 식별한 행사 후보 수.
- 묶기 전후 후보 수.
- 모아 보기 글 수.
- 기간·위치·이름 정보 부족으로 제외하거나 보류한 수.
- 실제 외부 호출 수와 지연 시간.

각 비율에는 분자·분모를 표시한다(분모 정의는 0-2 의 4).

API의 전체 검색 결과 개수를 실제 읽은 글 수로 보고하지 마라.

### 수동 검토

지역별로 추출·매칭된 결과를 최대 20건씩 결정적인 순서로 선택해 검토한다. 결과가 적으면 전부 검토한다.

확인할 것:

- 날짜 형식은 맞지만 예약·응모·후기 날짜를 행사 기간으로 잘못 연결했는가.
- 거점이 실제 제목·요약의 행사 장소와 연결되는가.
- 다른 행사를 하나로 묶었는가.
- 정보가 부족한데 확정했다고 표시했는가.

수동 검토의 판단 범위도 제목·요약까지다. 실제 행사 개최 사실을 독립 검증했다고 주장하지 마라.

정답·오답·판단 불가를 분리하고, 판단 불가를 정답에 포함하지 않는다.

잘못 읽은 사례는 최대 10개를 제시한다. 10개보다 적으면 실제 발견 수만 보고한다.

### 설계 재검토 조건

다음이면 구현 진행보다 설계 조정을 먼저 제안해라.

- 어느 대도시(서울·부산·대구)든 거점 매칭률이 30% 미만. (강원·전북은 거점이 없을 수 있으므로 수치만 보고)
- 날짜 또는 거점을 확정한 표본에서 반복적인 오인식 발견.
- 행사명 식별 실패로 카드 묶기가 대부분 추측에 의존.
- 연도 불명확 등으로 방문일 상태 판정이 거의 불가능.
- 정보 부족을 숨겨야만 화면이 채워지는 구조.
- 외부 호출 수·지연이 기존 서비스 예산과 맞지 않음.

30%는 정확도 합격선이 아니다. 매칭률이 높아도 오인식이 많으면 통과로 판단하지 마라.

실측으로 제품의 한계가 드러나면 “일정이 확인된 팝업 목록” 대신 “출처 중심 팝업 탐색”으로 범위를 축소하는 안을 제시할 수 있다. 사용자 동의 없이 제품 의미를 바꾸지는 마라.

## 6. 기간 추출: 날짜를 찾는 것과 행사 기간을 확인하는 것을 분리

### 추출 순서

1. 제목·요약의 태그와 엔티티를 안전하게 텍스트로 정규화.
2. 날짜 표현 후보 추출.
3. 실제 달력 날짜 유효성 검사.
4. 행사 기간과 연결되는 문맥 확인.
5. 연도·범위의 불확실성 판정.
6. 출처와 근거 문자열 보존.

다음 표현을 테스트한다.

- `2026.11.14~2026.11.30`
- `2026년 11월 14일부터 30일까지`
- `11.14~11.30`
- `11월 14일부터 30일까지`
- `~11.30`
- 연말·연초를 넘는 기간.
- 시작일 또는 종료일만 있는 표현.

다음은 행사 날짜로 읽지 않는다.

- `11:00~20:00`
- `10~20대`
- `2.5~3배`
- 가격·주소·버전·제품 번호.
- 날짜처럼 보이지만 달력상 존재하지 않는 값.

### 연도 정책

기본 정책은 보수적으로 한다.

- 명시된 연도나 같은 문맥에서 명확하게 이어지는 연도만 사용.
- 게시 연도를 행사 연도로 자동 대입하지 않음.
- 방문일에 맞추기 위해 전년도·다음 연도로 이동하지 않음.
- 출처 날짜가 없으면 임의로 오늘을 사용하지 않음.
- 연도가 불명확하면 월·일 근거는 보존하되 상태 판정용 완전한 날짜는 미확인으로 둠.

0단계에서 연도 누락 때문에 유효 후보가 부족하면, 연도 보정의 필요성과 오인식 사례를 보고해라(반사실 수치는 0-2 의 5). 보정 규칙 도입은 별도 결정 사항이다.

### 의미 판별

행사·운영 기간과 연결되지 않는 날짜를 자동 채택하지 마라.

예약·응모·배송·상품 판매·방문 후기 날짜와 구별되지 않으면 미확인이다.

서로 다른 기간 후보가 나오면 가장 넓은 기간으로 합치지 마라.

화면 문구는 다음 의미를 유지한다.

- `검색 요약에서 읽은 기간 · 원문 확인`
- `기간 미확인`
- `출처마다 기간이 달라요`

## 7. 방문일 상태 계약

날짜는 `Asia/Seoul`의 달력 날짜로 처리한다. 시작일·종료일은 포함한다.

| 조건 | 상태 |
|---|---|
| 시작·종료일 확인, 방문일이 기간 안 | 진행 중 |
| 시작일 확인, 방문일이 시작일 이전 | 오픈 예정 |
| 신뢰할 수 있는 종료일 확인, 방문일이 종료일 이후 | 종료 → 기본 목록에서 숨김 |
| 종료일만 확인, 방문일이 종료일 이전·당일 | 기간 미확인, 종료일만 표시 |
| 시작일만 확인, 방문일이 시작일 이후·당일 | 기간 미확인 |
| 연도 불명·출처 충돌·추출 실패 | 기간 미확인 |

상태는 검색 요약에서 읽은 기간 기준이다. 실시간 영업·휴무·예약 가능 여부를 보장하지 않는다.

종료 여부도 출처 충돌로 확정할 수 없다면 자동으로 숨기지 마라.

같은 캐시 데이터라도 방문일이 달라지면 상태를 다시 판정한다.

## 8. 거점 사전과 위치 정확도

거점은 팝업이 자주 열리는 건물·동네 약 30곳으로 시작한다(확정 시점은 0-2 의 3).

예:

- 더현대 서울.
- 용산 아이파크몰.
- AK플라자 홍대.
- 롯데월드몰.
- 성수·한남·도산 일대.
- 부산·대구·대전 주요 백화점.

각 거점에는 다음 메타데이터만 코드로 관리한다.

- 안정적인 ID.
- 정식 이름.
- 검증 가능한 별칭.
- 시·도와 필요한 하위 행정구역.
- 건물/동네 유형.
- 지역 검색용 검색어.
- 동네인 경우 명시적으로 선정한 기준 장소가 있다면 그 이름.

좌표는 코드에 하드코딩하지 않는다. 네이버 지역 검색 결과를 검증한 뒤 30일 캐시한다.

### 매칭 규칙

- 넓은 브랜드명만으로 특정 지점을 선택하지 않음.
- 긴·구체적인 별칭을 우선.
- 행정구역과 지점명을 함께 검증.
- 글에 여러 거점이 있으면 단일 행사 장소로 강제 연결하지 않음.
- 검색 결과 첫 번째 항목을 무조건 채택하지 않음.
- 이름·주소가 충분히 일치하지 않으면 위치 미확인.

네이버 지역 검색 결과의 업체 좌표를 동네 중심점이라고 주장하지 마라.

### 위치 등급

최소한 다음을 구분한다.

- 확인된 건물 위치.
- 동네의 명시적 기준점.
- 위치 미확인.

건물 좌표는 행사장 입구나 층별 위치를 의미하지 않는다.

동네 기준점은 `성수 일대(대략)`처럼 표시한다. 해당 기준점까지의 거리는 `약 2km · 일대 기준`처럼 표현한다.

위치 미확인 후보:

- 지도에 표시하지 않음.
- 거리값을 만들지 않음.
- 거리순 목록 뒤에 배치.
- 좌표가 필요한 코스 추천 버튼은 비활성화하고 이유 표시.

좌표의 축·스케일·범위는 실제 제공자 응답과 공식 문서로 확인해 공용 좌표 형식으로 정규화한다.

## 9. 행사 이름 추출과 카드 묶기

`같은 거점 + 비슷한 제목`만으로 묶지 마라.

순서:

1. URL 중복 제거.
2. 모아 보기 글 분류.
3. 단일 행사명 식별 가능 여부 확인.
4. 거점·이름·기간의 호환성 검사.
5. 보수적인 묶기.

### 행사명

- 제목·요약에서 명시적으로 식별되는 이름만 사용.
- 거점 이름이나 검색어를 행사명처럼 조합하지 않음.
- 전체 글 제목을 확정된 팝업 행사명으로 둔갑시키지 않음.
- 행사명을 식별하지 못한 글은 별도 참고 글로 남길 수 있음.

### 묶기

- 거점 ID와 정규화한 행사명이 같아도 다른 회차·명백히 다른 기간이면 분리.
- 이름 정규화는 공백·일부 기호 등 안전한 범위로 제한.
- 모호하면 합치지 않음.
- 기간 없는 글을 같은 이름의 여러 회차 중 하나에 임의 배정하지 않음.
- 출처 간 기간 충돌을 숨기거나 넓은 기간으로 합성하지 않음.
- 카드 순서·묶기 결과는 같은 입력에서 재현 가능해야 함.

출처 수는 이번 조회 범위의 중복 제거된 글 수다.

‘최근’의 기간을 정의하지 않는다면 `최근 글 N건` 대신 `검색된 글 N건`을 사용한다. 출처 수를 인기 지표로 쓰지 않는다.

`총정리/BEST/모음`은 모아 보기 글의 신호다. 단어 하나만 보고 무조건 분류하지 말고 여러 행사·장소를 소개하는지 함께 확인한다. 애매하면 단일 행사 카드로 승격하지 않는다.

## 10. 조회 범위와 정렬

검색 지역과 거리 기준점을 분리해라.

- 검색 지역: 기존 코스의 대상 지역 값 우선.
- 거리 기준점: 기존 코스의 출발지.
- 둘러보기 지역: 사용자가 선택한 시·도.

코스 대상 지역을 얻을 수 없으면 기존 지역 결정 로직을 확인해 명시적으로 대체한다. 출발지와 목적 지역이 같다고 가정하지 마라.

첫 구현에서는 임의의 거리 반경 필터를 추가하지 않는다. 지역 필터 후 거리가 확인된 후보를 오름차순 정렬한다.

동률 정렬은 안정적인 카드 ID 등 결정적인 기준을 사용한다.

코스 화면의 후보 개수 상한은 기존 축제 패널의 상한과 구조를 먼저 확인해 결정하고, UI 구현 전에 보고해라. 지도와 카드가 서로 다른 후보 집합을 쓰지 않게 한다. 단, 위치 미확인 카드는 지도에서 제외한다.

부분 검색 결과를 해당 지역의 모든 팝업처럼 표현하지 않는다.

## 11. 서버·캐시·비용 계약

새 조회는 다음 기존 구조를 따른다.

- `require_ip`(전용 한도는 0-4 의 2).
- `web_security.EXPENSIVE` 경로 등록.
- `store.cache`.
- 기존 네이버 클라이언트·오류 처리·설정 패턴.

새 의존성이나 DB 마이그레이션을 추가하지 않는다.

“요청 시점 조회”는 유효 캐시가 없을 때 외부 조회한다는 의미다. 매 요청마다 검색 API를 호출하라는 뜻이 아니다.

구현 전에 다음을 명시한다.

- 검색 결과 캐시 TTL.
- 빈 결과 캐시 TTL.
- 좌표 캐시 30일.
- 외부 요청 시간 제한.
- 요청당 외부 호출 상한.
- 동시 요청 상한.
- 같은 검색에 대한 동시 중복 호출 방지 방식.
- 부분 실패와 전체 실패의 응답 계약.

기존 서비스의 정책과 실측 결과를 근거로 값을 정한다. 임의로 무한 재시도하거나 호출 상한을 늘리지 않는다.

30개 거점을 매번 블로그·뉴스로 전부 검색하지 마라. 지역 검색으로 후보를 얻고 실제 매칭된 거점 중 캐시가 없는 위치만 필요한 범위에서 확인해라.

검색 캐시 키에는 지역·정규화한 검색어·조회 조건·처리 규칙 버전을 포함한다.

상태가 계산된 응답을 캐시하면 방문일도 키에 포함한다. 원본 후보 캐시와 방문일 상태 계산을 분리할 수 있으면 우선 검토한다.

외부 API 실패를 정상적인 `결과 0건`으로 저장하지 않는다.

키는 서버에서만 사용하며 응답·브라우저·로그에 노출하지 않는다.

## 12. 프런트엔드와 비동기 계약

- DOM 생성은 기존 `node()` / `link()` / `button()` 사용.
- `innerHTML` 금지.
- 검색 결과의 강조 태그는 화면에 HTML로 삽입하지 않음.
- 출처 링크는 허용된 `http/https` URL만 사용.
- 외부 링크 보안 속성은 기존 공용 링크 정책을 따른다.

코스 결과와 기본 지도를 먼저 렌더링한다. 팝업 조회 완료를 코스 추천 응답이나 첫 화면 표시의 전제조건으로 삼지 마라.

팝업은 독립 요청으로 조회한다.

generation 검사는 다음 모두에 적용한다.

- 성공 응답.
- 오류 표시.
- 로딩 종료.
- 카드 갱신.
- 지도 마커 갱신.

새 검색·코스·날짜 변경 시 이전 요청 취소를 시도하되, 취소만 믿지 않고 generation으로 늦은 응답을 폐기한다.

화면 상태는 구분한다.

- 로딩.
- 정상 결과.
- 정상 조회지만 결과 없음.
- 일부 검색원 실패.
- 전체 조회 실패.
- 설정 또는 키 없음.

실패해도 기존 코스·축제·탭 동작은 유지한다.

## 13. 지도 생명주기와 코스 추천 버튼

### 지도

공통 팝업 데이터에서 각 지도 엔진의 마커를 만든다.

- 이전 팝업 마커와 이벤트를 정리.
- 코스·축제 마커는 건드리지 않음.
- 같은 데이터를 반복 적용해도 마커 중복 없음.
- 지도 초기화 전 응답이 와도 안전하게 반영.
- 네이버 지도에서 Leaflet으로 전환해도 현재 세대의 데이터 유지.
- 팝업 갱신 때문에 지도 중심·확대 수준을 불필요하게 초기화하지 않음.

같은 건물의 여러 팝업은 하나의 위치 마커에서 목록으로 보여주는 방식을 우선 검토한다. 마커 수와 카드 수가 다를 수 있는 이유를 테스트에 반영해라.

### 주변 코스 추천

기존 축제 버튼이 무엇을 하는지 먼저 확인해라(확인 결과와 팝업 버튼의 기본 방침은 0-4 의 1).

- 출발지를 바꾸는가.
- 검색 중심을 바꾸는가.
- 필수 방문지를 추가하는가.

팝업 버튼은 가능한 한 같은 의미와 기존 함수로 연결한다. 의미가 달라지면 버튼 문구도 바꿔라.

기존 방문일·교통수단·취향 중 무엇을 유지하는지 명시한다.

- 위치 미확인: 실행 불가.
- 동네 기준점: `이 일대 주변 코스 추천받기`처럼 표현.
- 기간 미확인 또는 방문일 이전에 아직 열리지 않는 후보: 상태를 버튼 근처에 명시.
- 주변 추천을 행사 영업·예약·방문 가능성 보장으로 표현하지 않음.

운영 시간이 없으면 임의의 영업시간을 만들어 코스에 넣지 마라.

## 14. 디자인: 노선 언어를 실제 판단에 사용

기존 사이트는 하루 코스를 지하철 노선으로 표현한다.

- 장소 = 역.
- 이동 = 구간.
- 팝업 = 일정 기간만 존재하는 방문 후보.

이 관계를 사용하되 평범한 카드 그리드에 역 아이콘을 붙이는 것으로 끝내지 마라.

최소 두 안을 비교한다.

각 안은 다음을 설명해야 한다.

- 사용자가 첫눈에 읽는 정보.
- 기간 확정/미확인의 시각적 차이.
- 코스 포함 장소와 주변 후보의 구별.
- 모바일에서 첫 행동까지 필요한 조작.
- 기존 화면에서 추가·삭제·통합되는 요소.

비교는 짧고 구체적으로 하고, 최종 선택 이유를 한 줄로 남긴다.

### 디자인 제약

- 임시 정차역·노선 옆 분기 목록 등 관계를 드러내는 표현 검토.
- 미확인은 점선과 텍스트를 함께 사용.
- 확인된 날짜는 텍스트로 읽을 수 있어야 함.
- 실제 코스에 포함하지 않은 후보는 이동선에 연결하지 않음.
- 장식적 애니메이션보다 상태·거리·출처·다음 행동 우선.
- 별점, 인기 순위, 허구의 대기 시간, 검증되지 않은 추천 점수 금지.
- 대형 히어로·불필요한 배지·의미 없는 그라데이션을 추가하지 않음.
- 기능마다 새로운 카드·메뉴·설명 영역을 늘리지 않음.

기간을 선 길이로 표현한다면:

- 시작일·종료일과 기준일이 모두 명확할 때만 계산.
- 무엇의 비율인지 설명 가능해야 함.
- 종료일만 있는 경우 임의의 분모를 만들지 않음.
- 정확한 날짜 텍스트를 대체하지 않음.
- 이해에 도움이 없으면 사용하지 않음.

색·글꼴은 `line.css`의 기존 변수를 사용한다. 새 색은 지도 표시용 최대 1개만 허용한다.

새 CSS는 `popups.css` 한 파일에 작성한다. `!important` 추가 금지.

문구는 기존 해요체로 짧고 구체적으로 작성한다.

“핫플”, “놓치지 마세요”, 과장된 추천 표현, 홍보성 이모지는 사용하지 않는다.

## 16. 공용화와 변경 범위

축제 코드를 복사해 이름만 바꾸지 마라.

동시에 팝업 하나를 위해 축제 전체를 추상화하지 마라.

공용화 우선 후보:

- 거리 계산.
- 거리 텍스트.
- 출처 링크 생성.
- 실제로 같은 동작을 하는 작은 UI 구성.

카드 전체 공용화는 필수가 아니다. 팝업의 기간 불확실성과 복수 출처 때문에 조건문이 늘어난다면 별도 구성으로 둔다.

기존 축제의 동작·API 계약·표시를 유지한다.

기존 사용자 변경이나 무관한 코드 정리를 이번 변경에 섞지 않는다.

## 17. 검증

### 단위 테스트

- 정상 날짜·기간 추출.
- 시각·연령·배수·가격 오독 방지.
- 잘못된 날짜·윤년.
- 연도 누락·연말·연초.
- 시작일만/종료일만 있는 상태.
- 예약·후기 날짜와 행사 기간 구분.
- 거점 별칭·동명이점·다른 지점.
- 여러 거점 언급.
- 행사명 식별 실패.
- 같은 브랜드의 다른 회차.
- 출처 간 기간 충돌.
- URL 중복 제거.
- 모아 보기 글 분류.
- 재현 가능한 묶기와 정렬.

### API 테스트

검색 호출은 monkeypatch한다.

- 지역 필터.
- 잘못된 입력.
- 캐시 재사용.
- 방문일 변경에 따른 상태 재판정.
- 키 없음.
- 429·시간 초과·잘못된 응답.
- 블로그만 성공/뉴스만 성공.
- 전체 실패와 정상 빈 결과 구분.
- 외부 호출 상한.
- IP 제한과 비용 제한 경로 등록.

### 브라우저 테스트

`page.route`로 `/api/popups`를 가짜 응답으로 바꾼다.

- 결과 구역과 각 상태.
- 거리 정렬과 위치 미확인 후순위.
- 주변 추천 버튼의 실제 동작.
- 둘러보기 탭과 검색.
- 오래된 성공·오류·로딩 종료 무시.
- 지도 마커 추가·제거·중복 방지.
- 같은 거점의 여러 카드와 마커 관계.
- 네이버 지도·Leaflet 각각의 팝업 연결.
- 4개 화면 폭.
- 긴 이름·빈 결과·부분 실패·오류 문구.
- 팝업 실패 중에도 기존 코스·축제 정상 동작.

지도 SDK를 대체한 테스트와 실제 지도 연결 검증을 구분해라. 실제 외부 지도를 확인하지 않았다면 미확인이라고 기록한다.

### 저장소 검사

- 전체 pytest를 프로젝트가 지원하는 SQLite 설정으로 실행.
- `scripts/format_sources.py --check`.
- `app.js`의 jsbeautifier 형식 유지.
- 기존 관련 회귀 테스트.

테스트 숫자를 늘리기 위해 같은 동작을 반복 검증하지 마라. 데이터 오인식·잘못된 상태·비동기 경합·기존 기능 손상처럼 실제 실패를 잡는 테스트를 우선한다.

3. 지역별·검색원별 수치와 분모.
4. 수동 검토의 정답·오답·판단 불가.
5. 실제 오인식 사례 최대 10개.
6. 정보 부족으로 구현하기 어려운 요구.
7. 진행 가능 / 범위 축소 필요 / 실측 불가 판단.
8. 1단계에서 확정할 구현 계약과 변경 파일 후보.

이 보고 뒤 멈춘다.

### 1단계 완료 보고

1. 실제 사용자 동작이 어떻게 달라졌는지.
2. 선택한 디자인과 이유 한 줄.

실행하지 않은 검사를 통과했다고 쓰지 마라. 기존 실패와 이번 변경으로 발생한 실패를 구분한다.

## 19. 완료 조건과 금지 사항

완료는 “화면 세 개를 만들었다”가 아니다.

다음이 충족되어야 한다.

- 사용자가 기간·장소의 불확실성을 오해하지 않는다.
- 팝업 조회가 느리거나 실패해도 코스 추천은 정상 동작한다.
- 카드와 지도가 같은 후보와 상태를 가리킨다.
- 모바일에서 핵심 정보와 다음 행동을 쉽게 찾는다.
- 기존 축제·코스·헤더 동작을 보존한다.
- 실제 데이터의 한계와 검증 범위를 보고한다.

금지:

- 새 의존성.
- LLM 호출.
- 원문 크롤링.
- DB 마이그레이션.
- 기존 축제 동작 변경.
- 추정 정보를 확인된 사실처럼 표시.
- 근거 없는 인기·별점·대기 시간.
- 배포와 push.

구현 단계에서는 관련 검사가 끝난 이번 작업의 변경만 커밋할 수 있다. 기존 사용자 변경을 함께 커밋하지 마라.

판단이 애매하면 다음 순서로 결정해라.

**정보의 정확성 → 기존 코스 흐름 보존 → 모바일 사용성 → 외부 호출 비용 → 시각적 차별화.**

독창성은 새로운 장식을 많이 붙이는 데서 찾지 마라. 이 서비스의 노선 표현을 통해 사용자가 “기간이 제한된 주변 후보를 발견하고, 불확실성을 이해한 뒤, 다음 행동을 선택하는 과정”이 더 짧고 명확해지는 데서 만들어라.
