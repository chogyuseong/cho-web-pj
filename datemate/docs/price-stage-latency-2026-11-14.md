# 가격 확인 단계 대기 시간 (2026-11-14, 둘째 작업)

앞 작업(`recommendation-latency-2026-11-14.md`) 뒤 운영 실측(열한 번째 배포, 인기 동네 카드 기본 조건)에서
가격 확인이 전주 5.6초(price.price_plans 5348ms), 해운대 5.5초, 강릉 3.9초(3721ms)로 가장 긴 단계가 됐다.
운영의 외부 호출은 건당 평균 약 1.2초(로컬 측정은 0.24초 이하)였다. 측정 → 큰 것부터 개선 → 전후 비교 순서로 했다.

## 1. 요약

- 가격 확인은 거의 전부 가격 검색(네이버 블로그 검색) 대기다. 조회 대상은 **고른 3안의 장소 중 단가가 없는 곳뿐**이고(후보 풀 전체가 아님),
  조회한 가격은 기본 카드 조건에서 **모두 최종 3안에 쓰였다**(가격 검색이 있던 실제 14회에서 매번 6~8건 전부, 고정 입력 96회 504/504건). 쓰이지 않는 조회·중복 조회는 없었다.
- 동시 3건은 실제로 3건씩 겹친다(가격 확인 단계 `peak_parallel` 3, 가격 검색이 있던 14회 모두). DB 쓰기가 줄을 세우는 곳도 남아 있지 않다(예산은 묶음당 한 번).
- 남은 낭비는 **호출마다 새 HTTP 연결**이었다. `httpx.get` 이 호출마다 클라이언트를 만들어 TLS 설정을 다시 읽고(0.5 CPU 에서 11~90ms),
  TCP·TLS 연결(왕복 2번)과 새 연결의 느린 시작(30건짜리 응답에 왕복 1번 더)을 매번 치렀다. 연결을 재사용하면 호출이 왕복 1번 + 서버 시간이 된다.
- 적용: 가격 검색 묶음(price_plans 한 번)이 클라이언트 하나를 함께 쓴다. 같은 7건 묶음 비교(번갈아 8회):
  추가 지연 없음 323 → 168ms, 왕복 +100ms 1489 → 786ms, 왕복 +250ms(건당 1.1초, 운영 평균과 비슷) **3324 → 1680ms**.
- 운영 예상: 운영의 건당 1.2초가 주로 네트워크 왕복이면 전주처럼 7~9건(3차례)은 가격 검색이 약 1.6초, 4~6건(2차례)은 약 0.8초 줄어든다.
  서버 처리나 CPU 가 주원인이면 수십~수백 ms 에 그친다. 어느 쪽인지는 배포 뒤 새 진단(`connect_ms`)으로 바로 알 수 있다(11절).
- "코스 먼저 보여 주기": 가격 확인이 3안을 바꾼 경우는 기본 카드 조건에서 **0건**(실제 16회, 고정 입력 96회, 데모 162회),
  필수 조건(예산)을 건 고정 입력에서는 84회 중 31회(37%, 대부분 안이 빠짐). 그래서 가격 확인 동안 **읽기 전용 '확정 전 후보' 카드**를 보여 주고,
  확정 뒤 달라진 점이 있으면 무엇이 달라졌는지 적도록 했다(7절).

## 2. 측정 장치 (운영에도 남김, 숫자만)

- `timing.external_by_stage`(응답에 실림): 단계별 외부 호출 수, 기다린 시간 합, 실제 차지 시간(`wall_ms`), 최대 동시 수.
  `httpx.Client` 로 보낸 호출은 `connection_observed`(연결을 알 수 있는 호출 수), `new_connections`(새로 맺은 연결 수), `connect_ms`(TCP·TLS 연결에 쓴 시간 합)도 더한다.
  `connect_ms / new_connections` 가 그 호스트까지 왕복 약 2번이다. `httpx.get` 으로 보내는 호출(지역 검색 등)은 연결을 알 수 없어 세지 않는다.
- 로그 `recommendation_timing` 의 `by_kind` 행에도 같은 세 값.
- `timing.counts`(응답·이벤트·로그): `price.places`(단가 없는 장소), `price.cached`, `price.lookups`(새 조회), `price.lookups_used`(그중 최종 안에 남은 장소),
  `price.status_*`, `price.plans_before/after/unchanged/dropped/added/moved`, `price.order_changed`, `price.renamed`, `price.redescribed`,
  재채움은 `price.refill.*`. 0 은 싣지 않는다. 장소 id·이름·검색어는 남기지 않는다(개수만).
- span: `price.cache_read`, `price.lookups`(예산 미리 잡기 포함), `price.cache_write`.
- 테스트: `tests/test_price_stage.py`.

## 3. 측정 방법

- 앞 작업과 같은 운영 근사: PostgreSQL 17 + `tc netem delay 25ms`, 앱 `--cpus=0.5`, DB 풀 4, 운영 이미지(Dockerfile).
  실제 키는 원본 `.env` 를 읽기 전용으로 붙여 `DATEMATE_ENV_FILE` 로 읽게 했다(값은 출력·복사하지 않음). 호스트 포트 8011.
- 외부 호출 지연이 핵심이라 앱 컨테이너의 443 포트 나가는 패킷에만 지연을 더한 환경을 함께 썼다(`tc prio` + `netem`, DB 는 영향 없음).
  - A: 추가 지연 없음(로컬 왕복 약 10ms). B: +100ms. 묶음 비교만 +250ms 도.
  - +250ms 에서 새 연결 호출이 건당 약 1.1초로 운영 평균(1.2초)과 비슷했다. 운영의 왕복 시간은 재지 못했으므로 이것은 **비슷한 크기의 모형**이지 운영 재현이 아니다.
- 추천 측정: 실제 API 16회(B 12회: 전주·해운대·강릉 전/후 번갈아, A 4회: 전주 빈 상태·찬 상태 전/후). 30회 이내.
  네이버 쪽에도 캐시가 있어 같은 검색어를 두 번째로 보내면 서버 시간이 200ms → 60~100ms 로 준다. 그래서 지역마다 전·후 순서를 번갈아 했고,
  효과는 같은 7건 묶음을 같은 프로세스에서 번갈아 8번씩 보낸 비교(`price_plans` 와 같은 경로: `lookup_price`, 동시 3건, 예산 한 번)로 잰다.
- 연결 시간 분해: 같은 검색을 새 클라이언트/공유 클라이언트로 보내 httpx trace(연결·TLS·응답 헤더 시각)를 봤다.
  네이버 API 게이트웨이는 쉬는 연결을 32초 넘게 유지했다(1·4·8·16·32초 쉬고 보낸 요청이 모두 새 연결 없이 나감).

## 4. 가격 확인 구간의 실제 구성

확인한 것(코드와 측정):

1. 단계 시작: 진행 상태 저장(`report`: 작업 기록 쓰기·취소 확인 읽기).
2. `price_plans`: 캐시 한 번 읽기 → 새로 찾을 몫의 제공자 예산 한 번 잡기 → 가격 검색 N건(동시 3건) → 새 가격 한 번에 저장.
   N = 고른 3안(최대 3안)의 장소 중 등록 단가가 없는 서로 다른 장소에서 캐시가 없는 것. 전주 7, 해운대 8, 강릉 6.
3. 필수 조건 거르기 → (experience 선택기, 빠진 안이 있을 때만) 예비 후보 재채움 → 3안 다시 고르기·이름 붙이기 → 검증 요약 → 코스 저장.

| 항목 | 측정 |
|---|---|
| 동시성 | 가격 확인 단계 `peak_parallel` 3(가격 검색이 있던 14회 모두). 7건이면 3·3·1 차례, 기다린 시간 합 ÷ 실제 차지 시간 ≈ 2.4(이상값 2.33). 줄 세우는 DB 쓰기 없음 |
| 건당 시간(B, 새 연결) | 약 500~690ms = 클라이언트 만들기 + TCP 1왕복 + TLS 1왕복(TLS 1.3) + 요청 1왕복 + 서버 + 느린 시작 1왕복 |
| 건당 시간(B, 재사용 연결) | 약 170~300ms = 요청 1왕복 + 서버 |
| 연결 맺기(B) | 새 연결마다 약 223ms(왕복 2번). 같은 장치로 본 장소 검색 단계의 블로그 본문 5건도 건당 약 222ms |
| 쓰인 비율 | 기본 카드: 실제 14회 매번 전부(전주 7/7, 해운대 8/8, 강릉 6/6), 고정 입력 504/504. 필수 예산 조건을 건 고정 입력: 348/468(74%) — 빠진 안의 장소. 재채움 조회 37건 중 1건만 최종 안에 남음 |
| 캐시 | 같은 조건 재검색(5분 안): 7/7 적중, price_plans 83ms, 외부 호출 0. 찾은 가격은 1시간, '못 찾음'은 5분이라 5분 뒤 재검색은 못 찾은 곳만 다시 조회(전주 5/7, 해운대 5/8, 강릉 4/6) |
| 재채움 | 기본 카드 조건(필수 조건 없음)에서는 빠지는 안이 없어 일어나지 않음(실제 16회, 고정 입력 96회 모두 0). 필수 예산 조건 고정 입력에서 일부 발생, 추가 조회는 상한 6건 |
| DB(B, 25ms 지연) | 가격 확인 단계 DB 블록 14개 약 1.5초 — 운영(블록당 약 21ms)이면 약 0.3초로 추정 |

추정: 운영의 price_plans 5.3초(전주)는 같은 구성(3차례 × 건당 약 1.7초)이다. 운영 건당 시간 중 네트워크 왕복의 몫은 재지 못했다.

## 5. 적용한 개선 (결과 불변)

**가격 검색 묶음의 연결 재사용** (`app/pricing.py` `search_client`, `price_plans`)

- 새로 찾을 가격이 있을 때만 `httpx.Client` 하나를 만들어 묶음의 모든 검색이 함께 쓰고 끝나면 닫는다. 모두 캐시면 만들지 않는다.
- 보내는 요청(주소·검색어·헤더·시간 제한 7초)은 `httpx.get` 과 같다(테스트로 확인). 쿠키는 받지도 보내지도 않는다.
- 연결 수는 제한하지 않는다(풀 대기가 새로 생기지 않게). 동시 실행은 전처럼 동시 3건과 전체 슬롯 6개가 정한다. 상한·요청 제한·캐시 시간은 그대로.
- `lookup_price` 의 호출 모양은 그대로다(묶음 클라이언트는 문맥 변수로 넘김). 단건 호출은 전처럼 `httpx.get`.

같은 7건 묶음(전주 가격 검색), 번갈아 8회씩(+250ms 는 4회), 중앙값:

| 추가 왕복 지연 | 전(호출마다 새 연결) | 후(묶음 안 재사용) | 건당 평균 전 → 후 | 새 연결 1개 맺기 |
|---|---:|---:|---:|---:|
| 없음 | 323ms | 168ms | 118 → 62ms | 31ms |
| +100ms | 1489ms | 786ms | 504 → 298ms | 223ms |
| +250ms | 3324ms | 1680ms | 1119 → 637ms | 533ms |

(묶음 시간은 가격 검색이 실제 차지한 시간. 같은 검색어를 되풀이해 네이버 쪽 캐시가 찬 상태라 서버 시간은 짧은 편이다. 연결 비용은 서버 시간과 무관하다.)

- 3안(장소·순서·이름·비용)은 지역마다 모든 실행에서 같았고, 확정 전 후보와도 같았다(16회 모두 `price.plans_unchanged` 3).

운영 예상(추정, 호출 수·동시성 기준): 가격 검색 N건은 ⌈N/3⌉ 차례로 나간다. 전에는 차례마다 새 연결(왕복 약 4번 + 서버), 이제는 첫 차례만 새 연결이고
다음 차례부터 왕복 1번 + 서버다. 왕복을 R 이라 하면 둘째 차례부터 차례마다 약 3R 이 준다(+ 클라이언트 만들기).
운영 건당 1.2초가 +250ms 모형처럼 왕복 위주라면(R ≈ 0.26초) 전주(7건, 3차례) 약 1.6초, 해운대(8건, 3차례) 약 1.6초, 강릉(6건 이하, 2차례) 약 0.8초.
네이버 서버 처리나 컨테이너 CPU 가 주원인이면 효과는 그보다 작다.

### 설계와 조건

- 가격 확인 단계에 들어갈 때 서버가 작업 상태에 `preview_options`(안별 이름 + 장소 id·이름, 가격·비용·조건 확인 값 없음)를 싣는다.
  예전 `preview`(이름 목록)는 그대로 둬서 배포 직후 옛 화면도 전처럼 동작한다. 취소하면 둘 다 지운다.
- 화면(`static/plan-progress.js` `PlanPreview`): 결과 자리에 점선 테두리의 **'확정 전 후보 · 가격 확인 중'** 묶음을 보여 준다.
  - (b) 카드는 글자뿐이다(버튼·링크·입력 없음). 저장·결정·공유·교체·수단 변경은 확정 코스(id)가 생긴 뒤에만 보인다.
  - (c) 비용 자리는 '비용 · 가격 확인 중'. 금액·0원·추정값은 싣지도 그리지도 않는다.
  - (a) 확정되면 결과가 카드를 대신하고, 확정 전 후보와 장소 id 로 맞춰 달라진 점(빠짐, 새로 들어옴, 자리 이동, 방문 순서, 이름)을 결과 맨 위에 적는다.
    완료 안내(role=status)에도 '가격 확인 전 후보와 달라진 점이 있어요'를 붙인다. 이유는 서버가 알려 주지 않으므로 지어내지 않는다. 같으면 아무것도 덧붙이지 않는다.
  - (d) 새로고침하면 진행 중 검색에 다시 붙어 카드를 다시 그린다. 실패·취소 때는 카드를 지우고 실패 안내에 '확정되지 않아 지웠어요'를 적는다.
    긴 폴링을 안 하는 서버(같은 단계를 바로 답함)에서도 같은 상태로 그린다.
  - (e) 카드는 role=status 영역 밖(결과 영역, 검색 중 aria-busy)에 두고, 진행 안내에는 '찾은 후보 N개를 아래에 먼저 보여 드려요' 한 줄만 넣는다.
    진행 안내는 내용이 바뀔 때만 다시 그린다(전에는 같은 단계 응답마다 다시 그려 화면 낭독기가 되풀이할 수 있었음). 카드에 초점을 옮기지 않는다.
  - (f) 390px·320px 에서 가로 넘침 없음(테스트).
- 효과(체감): 3안을 가격 확인 단계만큼 먼저 본다(운영 실측 기준 3.9~5.6초, 이번 개선 뒤에는 그보다 짧음).

## 8. 결과가 바뀌지 않음을 확인한 방법

- `tests/test_recommendation_speed.py` 골든 비교(전주·성수, 빈 상태·찬 상태, 외부 호출 종류·횟수 포함)가 기준 파일을 바꾸지 않고 통과한다.
  가격 검색이 이제 묶음 클라이언트로 나가므로, 그 테스트의 가짜 네이버(`naver` 고정 장치)가 같은 가짜 응답을 `httpx.Client` 경로(MockTransport)로도 돌려주게 했다.
  기대값·기준 파일은 그대로다.
- 묶음 클라이언트가 `httpx.get` 과 같은 요청(방법·주소·헤더·시간 제한)을 보내는지, 쿠키를 다시 보내지 않는지, 묶음마다 하나만 만들고 닫는지 테스트.
- 실제 API 16회에서 지역마다 3안(장소·순서·이름·비용)이 전후 모두 같았다.

## 9. 하지 않은 것과 제안

- **가격 조회를 코스 구성과 겹쳐 미리 시작**: 하지 않음. 최종 3안은 코스 구성 끝(빔 탐색 뒤 3안 고르기)에서야 정해지고, 그 뒤에도 블로그 근거 대안·조건 완화·
  검색어 줄여 다시 찾기가 3안을 바꿀 수 있다. 3안이 확정된 시점부터 가격 확인까지는 진행 상태 저장(DB 몇 번, 운영 수십 ms)뿐이라 겹칠 몫이 없다.
  더 일찍(빔 상위 후보) 시작하면 3안을 덮으려고 훨씬 많은 장소를 조회해야 해 쓰이지 않는 호출이 는다.
- **(제안) 가격 동시 3건 → 4건**: 7~8건이 3차례 → 2차례가 되어 한 차례(재사용 연결 기준 왕복 1번 + 서버, 운영 추정 0.3~0.6초)가 준다.
  6건 이하·9건은 차례 수가 같다. 네이버 검색 API 의 초당 한도·예의 기준을 확인하고 정할 일이라 바꾸지 않았다.
- **(제안) 장소 검색과 같은 연결 풀 쓰기**: 장소 검색 단계의 블로그 검색·지역 검색(같은 호스트)도 같은 클라이언트를 쓰면, 게이트웨이가 연결을 32초 넘게 유지하므로
  가격 확인 첫 차례도 새 연결 없이 나가고(약 3R), 지역 검색 둘째 차례도 빨라진다. 가격 확인 밖의 여러 모듈과 시험 장치를 바꿔야 해 이번 범위에서 뺐다.
- **재채움**: 필수 조건이 있을 때 재채움 조회는 거의 쓰이지 않았다(고정 입력 37건 중 1건). 어떤 후보를 조회할지 바꾸면 결과가 바뀔 수 있어 그대로 뒀다(상한 6건).
- **자동차 경로 확인**(코스 구성 단계, 관찰만): 3안 × 구간 수만큼 차례로 조회한다. 자동차 조건에서 운영 지연이 크면 이 구간이 길다. 이번 범위(가격 확인) 밖이라 손대지 않았다.
- 가격 확인 단계의 나머지(검증 요약·코스 저장 DB, 운영 추정 약 0.3초)는 그대로.

## 10. 전과 달라지는 동작

- 가격 검색 묶음이 연결을 함께 쓴다. 한 연결이 끊기면 그 연결로 보낸 검색만 실패('가격 미확인' 표시)하는 것은 전과 같다.
- 응답의 `diagnostics.timing` 에 `external_by_stage`, `counts` 가 더해진다(숫자만). 로그 `by_kind` 행에 연결 값 세 개.
- 작업 상태에 `preview_options` 가 더해진다(작업 주인만 봄, 취소 때 지움).
- 화면: 가격 확인 동안 확정 전 후보 카드, 확정 뒤 달라진 점 안내, 실패·취소 때 안내 한 줄. 진행 안내는 내용이 바뀔 때만 다시 그린다.

## 11. 배포 뒤 확인할 것

- 전주 한옥마을 카드 처음 검색 1번: `result.diagnostics.timing.external_by_stage['가격 확인']` 에서
  `new_connections`(가격 검색이 4건 이상이면 3), `connect_ms / new_connections`(운영의 왕복 약 2번), `wall_ms`(전: price_plans 약 5.3초)를 본다.
  `connect_ms / new_connections` 가 수백 ms 면 왕복 위주라 효과가 6절 예상대로 크고, 수십 ms 면 운영 지연은 서버·CPU 쪽이다.
  같은 값이 '장소 검색' 단계(블로그 본문)에도 있다.
- `timing.counts`: `price.lookups_used` = `price.lookups`, `price.plans_unchanged` = 3 인지.
- 화면: 가격 확인 단계에 확정 전 후보 카드가 보이고, 완료 뒤 사라지며, 휴대폰 폭에서 넘치지 않는지.
