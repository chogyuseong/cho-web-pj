# DateMate 완성도 개선을 위한 개발 프롬프트

아래 세 프롬프트는 각각 독립적으로 사용할 수 있다. 첫 번째 작업부터 권한다. 검색 결과를 기다리다가 연결이 끊긴 사용자는 지금도 같은 작업을 복원할 수 있지만, 그 방법을 알기 어렵다. 두 번째와 세 번째는 실제 화면에서 문제가 재현될 때 진행할 제품 개선안이다.

## 1. 연결이 끊겨도 찾던 코스로 돌아가기

> DateMate의 모바일 사용자가 코스 검색 중 지하철에서 통신이 끊겼다가 돌아오는 상황을 개선해 줘. 사용자의 목표는 이미 시작한 검색의 결과를 보는 것이다.
>
> 먼저 `datemate/static/plan-progress.js`의 `PlanSearch.wait`, `resumePlanSearch`, `showSearchFailure`와 최초 제출·취소 버튼의 호출부를 따라가라. 서버의 기준은 `datemate/app/plan_jobs.py`에서 확인해라. 현재 클라이언트는 일시 오류가 세 번 이어지면 대기를 끝낸다. 작업 ID가 남아 있으면 새로고침으로 복원할 수 있지만, 공통 실패 화면의 버튼은 조건 입력 화면으로 보낸다. 브라우저에서 상태 조회만 연속 실패시켜 이 차이를 먼저 재현해라.
>
> 일시적인 조회 실패로 대기가 끝났고 현재 탭에 해당 작업 ID가 남아 있으면, 사용자가 결과 영역에서 ‘진행 중인 검색 다시 연결’을 누를 수 있게 해라. 기존 복원 경로를 재사용해 같은 ID를 조회해라. 다시 연결하는 동안 버튼의 중복 입력을 막고, 서버가 이미 완료했다면 결과를 즉시 표시해라. 서버가 취소·실패·만료를 확인해 준 경우에는 그 상태에 맞는 설명과 가능한 다음 행동을 보여라. 조회 실패만으로 서버 작업이 실패했다고 표시하지 마라. 문구는 한 문장으로 짧게 쓰고 상태 변화는 기존 라이브 영역에서 한 번만 읽히게 해라.
>
> 연속 탭, 기다리는 중 취소, 늦게 도착한 이전 응답, 새로고침을 점검해라. 기존 확정 전 후보의 처리, 축제·팝업 복원, 저장된 코스 딥링크 진입 조건을 유지해라. 실제 외부 API 대신 작업 생성과 상태 조회 응답을 제어할 수 있는 기존 테스트 방식을 우선 써라.
>
> **완료 기준**은 최초 제출부터 재연결 성공까지 작업 생성 POST 1회, 동일 ID로 상태 조회, 최종 결과 1회 표시다. 별도 사례로 404 또는 410에서는 재연결 버튼이 사라지고, 취소 후 늦게 도착한 성공 응답이 결과를 되살리지 않는지 확인해라. 변경 전 재현 결과와 변경 후 요청 횟수를 보고해라.

## 2. 두 코스 중 내 조건에 더 맞는 쪽 고르기

> DateMate 결과 화면에서 ‘두 안 중 어느 쪽이 덜 걷고 예산 안에 들까?’에 답하기 쉽게 해 줘. `datemate/static/plan-results.js`의 결과 탭, `datemate/static/plan-evidence.js`의 기존 비교표, `datemate/static/experience.js`의 필수 조건 표시를 함께 읽어라. 이미 예상 전체 비용, 이동 시간, 주요 활동, 장소 차이를 비교하는 표가 있다. 390px 화면에서 실제로 코스 두 개를 비교해 보고, 어느 정보가 부족해서 상세 화면을 왕복하게 되는지 먼저 기록해라.
>
> 예산과 총 도보 제한을 입력한 사례 하나를 기준으로 개선해라. 우선 서버가 제공하는 비용 범위, 도보 시간, 전체 이동 시간, 필수 조건 판정의 의미와 누락 시 표현을 확인해라. 사용자가 선택한 조건에서 결정을 바꾸는 차이 한두 개만 기존 비교 영역에 드러내라. 예를 들어 ‘전체 이동은 짧지만 도보는 12분 더 걸려요’는 두 안의 같은 기준 도보 값이 모두 있을 때만 쓸 수 있다. 전체 이동 시간을 도보 시간으로 대체하지 마라. 예산이 무제한이면 예산 충족 문구를 생략해라. 비용 범위가 예산 경계를 걸치면 불확실성을 그대로 보여라. 필수 조건 충족 여부는 기존 서버 판정을 사용해라.
>
> 기존 탭과 표 중 한 곳을 골라 수정해라. 같은 내용을 카드마다 반복하거나 새로운 종합 점수를 만들지 마라. 오래된 저장 코스처럼 값이 없는 경우, 동률, 결과 한 개, 결과 세 개를 포함해라. 새 외부 조회 없이 동작해야 한다.
>
> **완료 기준**은 390px 화면과 키보드 조작에서 비용 범위와 도보 차이를 같은 비교 영역에서 확인할 수 있고, 모르는 값이 0원 또는 0분으로 표시되지 않는 것이다. 동일 입력의 개선 전후 화면과 표시 문구의 근거 필드를 제시해라. 기존 화면만으로 이미 충분한 사례는 변경 대상에서 제외해라.

## 3. 추천이 부족할 때 무엇을 바꾸면 되는지 설명하기

> DateMate가 요청한 수만큼 코스를 만들지 못했을 때, 사용자가 어떤 조건을 유지하고 무엇을 바꿀지 결정할 수 있게 해 줘. `datemate/app/search_relaxation.py`와 `datemate/tests/test_search_relaxation.py`에서 완화 단계가 누적되는 방식과 필수 조건 처리를 읽어라. 그다음 추천 서비스가 실제로 선택한 단계가 응답을 거쳐 `datemate/static/recommendation-feedback.js`와 결과 화면에 어떻게 표시되는지 추적해라.
>
> 작은 지역 반경과 짧은 구간 이동 제한을 함께 건 고정 입력으로 결과 0개, 일부 충족, 완화 후 충족을 각각 준비해라. 예산을 필수로 선택한 사례도 포함해라. 화면에서 사용자가 입력한 조건, 실제 적용한 조건, 아직 시도하지 않은 제안을 구별할 수 있는지 확인해라. 두 단계가 누적 적용된 결과를 마지막 단계 하나의 효과로 설명하면 안 된다. 예를 들어 반경과 이동 제한이 모두 바뀌었다면 원래 값과 적용 값을 함께 보여라. 근거가 없을 때 ‘반경만 넓히면 3개가 나와요’ 같은 약속을 하지 마라.
>
> 기존 조건 차이 안내를 수정해 가장 중요한 변경부터 보여 주고 나머지는 펼쳐 볼 수 있게 해라. 결과가 없으면 근거가 있는 조정 후보 하나를 제시하고, 사용자가 조건 편집으로 돌아갔을 때 무엇을 바꿀지 알아볼 수 있게 해라. 변경을 제안하는 것만으로 원래 폼 값이나 필수 조건을 수정하지 마라. 표시할 차이가 없는 성공 사례에서는 추가 문구를 생략해라.
>
> **완료 기준**은 필수 예산 유지, 누적 변경의 정확한 전후 값, 결과 0개에서 조건 편집으로 복귀, 일반 성공 화면의 중복 안내 방지다. 실제 추천 응답에 근거가 부족하면 먼저 부족한 필드를 특정하고, 필요한 최소 범위에서만 응답을 확장해라. 기존 응답과 과거 저장 코스도 계속 렌더링되는지 확인해라.

## 각 프롬프트 끝에 붙일 검증 지시

> 이 작업은 로컬에서 구현하고 검증해라. 해당 동작을 이미 다루는 테스트와 실행 지침부터 찾아라. Python 테스트는 `datemate` 기준으로 관련 케이스를 실행하고, 화면 동작은 고정 응답으로 실제 브라우저에서 확인해라. 문자열 존재 검사만으로 요청 횟수나 상태 전환을 검증했다고 판단하지 마라. 마지막에는 사용자가 겪던 현상, 바뀐 동작, 실행한 명령과 결과, 확인하지 못한 환경을 짧게 보고해라. 외부 키의 실제 값이나 개인 위치를 로그·스크린샷에 남기지 마라.
