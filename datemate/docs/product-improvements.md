# 실행 가능한 코스로 개선한 흐름

## 1. 식당을 선택하면 일정 전체 재계산

식당 카드의 `이 식당을 일정에 넣기`에서 추가 위치 또는 교체할 장소를 선택한다. 고정한 장소는 교체할 수 없다. 가격이 있는 메뉴는 사용자가 직접 선택한다. 대표 메뉴와 일반 식사 메뉴를 우선 정렬하고, 냉동·포장·중량 상품은 뒤에 둔다. 1인 1개 주문은 비용 계산용 가정이며 인원별 금액·체류·이동·종료 시간·귀가·전체 예산을 다시 계산한다.

미리보기는 원본을 바꾸지 않는다. `이 변경안으로 확정`을 눌러야 자식 일정이 생기며 `교체 되돌리기`로 돌아갈 수 있다. 중복 확정 요청은 SQLite 트랜잭션으로 일정 한 개만 생성한다. 추가·교체에 따른 고정 위치 이동을 보존하고, 미리보기 후 고정 상태가 바뀌면 적용을 막는다. 확인된 휴무·영업시간 밖 방문·동일 장소 중복·피할 활동·동네 범위 밖 식당은 허용하지 않는다. 자동차는 변경 동선을 재조회하며 실패 시 추정임을 표시한다.

## 2. 필수 조건과 개인 상황

만남 목적(평소·첫 만남·기념일), 우선 관심(균형·대화·음식·사진·체험), 정보 선호(기존+신규·최근 운영 자료만·새 발견)를 선택한다. 장소 분류·이동·운영 자료를 바탕으로 비교하는 규칙이며 소음·인파·기념일 만족도를 실제로 검증한 모델은 아니다.

예산·종료·이동·실내외·예약·테마·식사·동네를 필수로 지정할 수 있다. 비용 검색 후에도 해당 조건이 불일치 또는 미확인이면 추천/변경 확정에서 제외한다. 추정 범위의 충족은 실제 가격·경로 보증이 아니다. 조건을 모두 충족한 결과가 없는 경우 자동으로 필수 조건을 풀지 않는다.

## 3. 확인 자료와 제보

상단 네 가지 확인에 영업/예약·이동·예산·식사를 보여준다. 최근 90일 안에 기록한 출처와 영업시간·요일 휴무 자료가 있는 장소를 구분한다. 주소 연결만 한 신규 장소를 영업 검증 완료로 표시하지 않는다. 이 날짜 기준은 실시간 영업 확인이 아니다.

장소 변경 제보는 확인 대기 상태다. 제보만으로 폐업·이전 사실을 확정하지 않고 추천 우선순위를 낮춘다. 최근 운영 자료만 요청한 경우 확인 대기 장소는 제외한다. 운영자는 `scripts/review_place_reports.py`로 목록을 보고, 출처를 직접 확인한 뒤 `--resolve-id`, `--source`, `--note`로 처리 기록을 남긴다. 공식 장소 원본은 자동으로 덮어쓰지 않는다.

## 4. 피드백과 측정

옵션 선택, 교체 이유(가격·거리·취향·이미 방문), 실제 이용 자기 신고·불편·재사용 의향을 저장한다. 동일 브라우저/코스 피드백은 갱신한다. 본인의 피드백 조회·삭제와 브라우저별 집계를 제공한다. 다음 추천 반영 체크박스를 선택했을 때만 이전의 취향 거절·이미 방문 장소를 제외한다. 가격·거리 피드백은 현재 입력을 임의로 바꾸지 않고 기록한다.

서버에서 완료된 추천의 계산 시간을 측정한다. API 실제 금액은 계측하지 않으며 임의 금액을 만들지 않는다. 브라우저/자기 신고 지표는 실제 방문·실사용자 수와 다르다. 대규모 실사용 검증이나 추천 품질 개선 효과가 입증됐다고 주장하지 않는다.

## 5. 두 브라우저의 코스 합의

코스 링크를 상대방에게 직접 공유한다. 이 기능은 외부 메시지를 자동으로 보내지 않는다. 두 브라우저에서 장소별 좋아요·다른 곳 원함·상관없음을 저장한다. 모두 좋아하는 장소는 고정하고 반대가 있는 장소는 제외해 새 초안을 만든다. 고정 장소에 반대 의견이 있으면 먼저 조정해야 한다. 두 브라우저가 참여해야 하며 세 번째 참여는 막는다. 신원 인증을 의미하지 않는다.

원본 소유 브라우저만 변경안을 계산·확정한다. 의견이 바뀐 뒤 오래된 초안을 적용할 수 없다. 변경안의 새로운 장소는 자동 동의 처리하지 않는다. 상대방이 접속하려면 공개 배포 주소 또는 접근 가능한 같은 네트워크 주소가 필요하다.

## 식당 위치 매칭

첫 코스부터 마지막 코스까지 각각 직선 반경 500m 안의 식당을 최대 3곳 매칭한다. 지도에 범위 원과 식당 번호를 표시하고 클릭하면 주소·메뉴 링크를 확인한다. 같은 식당이 여러 코스에 연결되면 마커 번호를 합친다. 별도 지역 추천은 코스 주소에서 가장 많이 등장하는 구 전체를 대상으로 리뷰순 후보 최대 5곳을 표시한다. 네이버 지역 검색은 반경 검색 API가 아니므로 검색된 결과의 좌표를 거리 검증하여 걸러낸다. 지역 추천이 부족하면 음식점·한식 검색으로 보충하지만, 결과가 부족할 때 다른 구·카페를 섞지 않는다. 별점 또는 지역 전체의 절대 인기 순위를 의미하지 않는다.

## 검색어·자유 입력 활동 해석

검색어와 자유 입력은 같은 해석 규칙으로 활동 유형·예산·인원·장소 수·실내외·이동수단을 반영한다. 카페와 식당은 구분하고, 카페 투어처럼 단일 활동 위주 요청은 식사 자동 포함보다 우선한다. 전시+산책처럼 여러 활동이면 각각 포함한 조합을 우선하며, 제외 표현은 후보에서 제외한다. 지역명이 없는 검색어는 선택한 위치 기준 지역을 덧붙인다. 블로그에 요청한 활동 후보가 부족할 가능성에 대비해 지역 API의 업종·주소·좌표가 확인된 장소를 보충한다. 카페 투어가 실제 카페 3곳으로 나오는 것을 두 입력칸에서 모두 브라우저 검증했다. 검색량 한계로 후보가 부족할 때는 입력 활동 불일치를 표시한다. 조용함·혼잡도·대기시간 같은 현장 특성은 확인 자료 없이 충족으로 처리하지 않는다.

## 운영상 남는 한계

콘셉트별 검색은 지역 기본 검색어에 선택한 콘셉트와 구체적인 활동 키워드를 추가한다. 즐거움은 놀거리·체험, 편안함은 산책·힐링, 지적 활동은 전시·박물관, 동심은 장난감·오락실로 검색한다. 결과가 0건일 때만 지역 기본 검색으로 넓히고 그 사실과 실제 검색어 기록을 화면에 표시한다. 장소명·설명·태그에서 확인한 관련 단서를 후보 추림과 코스 순위에 반영하며, 장소별 단서가 없으면 보완 후보임을 표시한다. 이는 규칙 기반 관련성 비교이며 실제 분위기나 만족도를 보장하지 않는다.

- 도보·대중교통은 실제 경로 공급자가 연결되지 않아 추정이다.
- 새 장소의 폐업·영업·웨이팅·소음은 자동 확정할 수 없다. 확인 자료와 실사용 제보가 필요하다.
- API 비용, 실제 재방문, 실제 만족도는 별도 운영 측정이 필요하다.
- Cloud Run 배포는 보류 중이며 SQLite/Chroma의 영구 보존은 아직 외부 DB로 이전하지 않았다.
