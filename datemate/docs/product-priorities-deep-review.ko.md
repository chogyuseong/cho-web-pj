# DateMate에서 다음에 만들 것

2026-11-19 기준 저장소 분석. [기존 3개 제안](product-improvement-prompts.ko.md)과 [추가 80개 제안](product-improvement-prompts-80.ko.md)의 개발 순서를 다시 판단했다. 구현 순서는 **두 사람의 합의가 정확히 저장되는지 → 기다리던 결과에 돌아올 수 있는지 → 추천한 하루를 실제로 선택할 근거가 있는지**로 제안한다.

## 1. 합의 계산 중에 상대가 마음을 바꾸면 생기는 문제

두 사람이 A 전시와 B 식당을 검토한다. 내가 ‘다시 계산’을 누른 뒤 상대가 전시를 ‘빼주세요’로 바꾼다. 전시는 옛 의견으로 이미 선택됐는데, 초안에는 새 의견으로 계산했다는 기록이 붙을 수 있다.

| 시점 | 코드가 하는 일 | 실험 결과 |
|---|---|---|
| 계산 시작 | `agreement_draft`가 의견을 읽어 고정·제외 장소를 정한다. | A의 반대 0표. 제외 목록에 A가 없다. |
| 추천 계산 중 | 두 번째 브라우저에서 의견이 바뀔 수 있다. | 고정 입력으로 반대를 1표로 바꿨다. |
| 초안 생성 | `make_draft`가 의견을 다시 읽어 적용 시 비교할 스냅샷을 저장한다. | 초안에 A가 남았고 스냅샷에는 A 반대 1표가 기록됐다. `can_apply`는 참이었다. |
| 적용 검사 | 최신 집계와 초안 스냅샷을 비교한다. | 실험에서 두 집계가 같았다. 이 비교만으로는 계산 도중의 변경을 잡을 수 없다. |

실험은 저장소의 두 함수 본문을 그대로 실행하고 추천기·저장소·투표 응답을 대체해 변경 시점을 고정했다. HTTP와 DB를 통한 최종 저장은 별도 검증 대상이다. 기존 `test_changed_partner_vote_invalidates_existing_preview`가 다루는 ‘초안 완성 후 변경’과 발생 시점이 다르다.

**개발 프롬프트**

> 두 브라우저의 의견으로 코스를 계산할 때 계산에 사용한 집계를 초안에 그대로 전달해라. 계산 중 집계가 달라지면 적용 전 기존 충돌 처리로 돌아가도록 해라. 실행 순서는 테스트에서 이벤트나 제어 가능한 콜백으로 고정해라. 임의 지연에 기대지 마라. 반대 0→1, 의견 그대로, 미리보기 후 변경, 같은 초안 재적용을 각각 API에서 검증해라. 오래된 초안으로 자식 일정이 생성되지 않는지 DB에서도 확인해라. 출발점은 `app/experience.py`와 `tests/test_experience.py`다.

**기존 28번도 범위를 바로잡아야 한다.** 공유받은 사람과 만든 사람 양쪽 화면이 모두 기본값을 중립으로 보내고, 서버의 `save_votes`는 모든 장소 ID가 있어야 저장한다. 중립은 현재 재계산에서 찬성이나 필수 표로 쓰이지 않는다. 따라서 무응답을 구분하는 주된 효과는 의견 수집의 정확성과 참여 상태에 있다. 먼저 ‘아무 선택 없이 저장’, ‘한 곳만 응답’, ‘모든 곳에 명시적으로 중립’을 구분하고, 기존 저장값은 입력 당시의 의도를 복원할 수 없으므로 소급 재분류하지 않는다.

## 2. 검색 복구는 적은 변경으로 끝까지 검증할 수 있다

`static/plan-progress.js`의 실제 함수를 Node에서 실행하고 상태 조회와 세션 저장소를 대체했다. 같은 ID의 상태 조회를 세 번 실패시키자 작업 ID가 남았다. 같은 ID로 다시 기다리자 네 번째 조회에서 완료 결과를 받고 ID를 지웠다. 최초 POST 응답을 이미 받은 상황에서는 복구에 필요한 서버 기능이 있다. 실패 안내의 현재 버튼은 조건 입력으로 이동한다.

가장 작은 작업은 **ID가 남은 일시 조회 실패에만 ‘이 검색 이어보기’를 제공하는 것**이다. 최초 생성 요청의 응답 자체가 유실되어 브라우저에 ID가 없는 상황은 다른 사례다. 이 차이를 무시하고 모든 오류에 같은 버튼을 붙이면 버튼이 아무 일도 못 하는 경우가 생긴다. 1번 프롬프트의 완료 기준에 이 사례를 추가한다. 모바일 실제 브라우저에서 뒤로 가기·취소·재연결을 순서대로 확인한다.

## 3. 장소가 많아져도 약속을 정할 근거가 늘지 않을 수 있다

저장소의 `data/real_places.json` 152개 원본 행을 집계했다. 영업시간, 가격, 휴무일, 마지막 입장, 예약, 체류 시간 여섯 필드는 각각 값이 든 행이 0개였다. 별도 `operating_facts.json`은 장소 키 8개, `operating_evidence.json`은 장소 키 2개에 필드별 근거 10건을 담고 있었다. 10건은 모두 10월 29일 확인·유효기간 30일로, 11월 19일에는 코드의 날짜 기준 안에 든다. 런타임에는 추가 자료와 외부 공급자가 결합되므로 이 숫자로 서비스 전체 커버리지를 추산할 수 없다.

과거 실연동 기록도 이 구분이 필요한 이유를 보여 준다. `docs/live-acceptance.json`의 네 요청은 모두 3안을 받았다. 그중 은평구의 세 안은 모두 검색 조건 조정 기록이 있었다. 이 자료만으로 조정이 불만족스러웠는지 알 수 없다. 반면 ‘세 안 생성’만 집계하면 원래 조건 그대로 얻은 결과와의 차이가 사라진다는 점은 확인할 수 있다. `docs/input-combinations-10000-final.json`의 1만 건은 입력 해석·정규화 5천 건과 저장 코스 채팅 5천 건이다. 방문 가능성 평가는 별도 모집단이다.

**개발 프롬프트**

> 기존 추천 평가에 한 동네의 당일 약속 6건을 추가해라. ‘퇴근 후 마감 직전 전시’, ‘둘이 5만 원’, ‘비 오는 날 실내’ 세 요청을 자료가 충분한 후보와 희박한 후보로 각각 구성해라. 각 요청에서 원래 조건을 지킨 안의 수, 완화한 조건, 선택을 보류하게 만드는 미확인 필드를 기록해라. 그런 다음 운영시간 또는 가격 한 필드만 검증된 고정 자료로 보강하고 같은 후보·같은 시각·같은 입력으로 다시 돌려라. 어느 필드 보강이 실제로 한 안을 선택 가능하게 했는지 사례별로 보고해라. 자동 판정과 사람이 공식 안내를 확인한 결과는 각각 기록해라. 운영 수집·배포 없이 오프라인에서 시작할 수 있다.

|---|---|---|
| 20. 미확인 이동 시간을 0분과 구분 | 실제 JS 합산에 12분과 누락값을 주면 12가 나온다. 다만 일반 플래너는 이동 분이 없는 방문·귀가 구간을 반환 전에 거른다. | 읽기 가능한 과거 저장본이나 다른 생성 경로에서 부분 구간이 발견될 때. 먼저 데이터를 관찰하고 공통 포매터 변경을 결정한다. |

| 4. 두 출발지의 공평한 중간 지점 | 기본 대중교통 시간은 거리 기반 추정이며 별도의 노선 비교는 사용자가 요청하는 미리보기다. 강을 건너거나 환승이 많은 두 동네는 거리와 실제 부담의 순위가 바뀔 수 있다. | 직접 고른 세 동네의 두 사람별 이동 시간을 같은 기준으로 확인할 수 있을 때. 한 사람의 경로만 있으면 순위를 보류한다. |

## 5. 다음 제품 실험은 ‘얼마나 늦어도 괜찮은가’

36번 지각 복구 기능을 전부 만들기 전에 **현재 코스가 지각을 흡수할 수 있는지**부터 보여 주는 실험을 권한다. 예를 들어 16:40 도착, 전시 입장 마감 17:00이면 20분 늦어도 입장 마감 자체는 맞춘다. 그러나 40분 관람, 영업 종료 17:30이면 실제로 허용되는 지각은 10분이다. 반대로 식당이 18시에 열고 원래 17:45 도착 예정이라면 10분 지각은 기존 대기에 흡수될 수 있다. 모든 시각을 10분씩 미는 방식은 두 사례 모두 잘못 설명한다.

**개발 프롬프트**

> 사용자가 남은 첫 장소와 지연 분을 입력하면 현재 방문 순서를 고정하고, 기존 시간 평가 규칙으로 이후 도착·체류·종료를 다시 계산하는 읽기 전용 실험을 만들어라. 1차에서는 재추천이나 저장 없이 ‘그대로 가능’, ‘어디서 처음 어긋나는지’, ‘자료 부족으로 판단 보류’를 구별해라. 16:40 도착·17시 입장 마감·17:30 영업 종료·40분 관람 사례에서 +10분은 가능하고 +11분은 영업 종료를 넘겨야 한다. 17:45 도착·18시 영업 시작 사례에서는 +10분이어도 체류 시작이 같아야 한다. 휴게 시간, 종료 필수 조건, 추정 이동 구간도 검증해라. 사용자가 순서를 지키기 어려운 이유를 이해할 수 있는지 확인한 뒤 대체 장소 추천 여부를 결정해라.

이 실험의 관찰 항목은 ‘재추천 버튼을 눌렀는가’보다 **어느 장소를 그대로 가도 되는지, 어느 장소에 먼저 연락해야 하는지 사용자가 정확하게 답했는가**가 적합하다. 일정 데이터를 바꾸기 전에 화면의 판단 지원만 평가할 수 있다.
