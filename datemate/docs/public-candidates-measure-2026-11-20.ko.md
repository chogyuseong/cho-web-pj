# 추천 후보를 공공 자료로 바꾸기 전후 측정 (2026-11-20)

네이버 검색 API 특약 2단계의 나머지(docs/naver-terms-stage2-design.ko.md 3.8(b)·3.5(b)·3.7(a), 브랜치 fix/naver-terms-stage2-b)를 만들며,
추천 후보의 출처를 네이버 지역 검색에서 공공 자료(한국관광공사 TourAPI, 소상공인 상가정보)로 바꾸기 전과 후를 실제 키로 쟀다.
스크립트는 `scripts/measure_public_candidates.py` 이고 바꾸기 전 코드(main 610afab 계열)와 바꾼 뒤 코드에서 같은 파일을 돌렸다.

## 어떻게 쟀나

- 조건 표본: 서울 12건(성수·홍대·강남·익선동·잠실·이태원·망원·건대·노원·신림·혜화·여의도, 기본/테마/요청 활동 섞음),
  서울 밖 6건(부산 해운대, 전주 한옥마을, 강릉 안목해변, 대구 동성로, 경주 황리단길, 제주 애월(자동차)). 방문일 2026-11-21(토), 13~19시, 3곳, 식사 포함이 기본.
- 추천 전체(`recommendation_service.generate`)를 실제 외부 API 로 돌렸다. DB 는 임시 SQLite(캐시가 빈 상태). 이동 시간은 양쪽 모두 거리 추정(네이버 Maps 키를 비움).
- '조건 그대로' = 완화·대안 코스가 아니고 미충족 조건이 없는 안. '확인 필요' 비율은 3안에 나온 서로 다른 장소 기준.
  - 영업시간: 일정 계산에 쓰는 값(hours)이 없는 장소. 영업 안내 글: 한국관광공사 안내(detailIntro2)가 없는 장소.
  - 사진: 등록 사진도 한국관광공사 사진도 없는 장소(네이버 검색 사진은 1차에서 이미 없앴다).
  - 가격: 등록·확인 단가가 아닌 장소(계획용 가정 금액 포함).
- 한계: 표본 18건, 한 번씩. 사람이 코스를 보고 매긴 만족도가 아니다. 바꾸기 전 사진·영업 안내 수치는 첫 측정(같은 표본), 나머지는 가격 지표를 고친 둘째 측정 값이다.

## 가는 길에 버린 방법 (기록)

처음에는 관광공사 반경 목록(locationBasedList2) 한 번으로 주변 항목을 받았다. 같은 표본에서 서울 밖의 '조건 그대로인 안'이 5→1건(6%)으로 떨어졌고
전주 한옥마을 3km 안의 관광지가 1곳뿐이라 원인을 찾았다. 2026-11-20 실제 응답:
- 경복궁에서 400m 떨어진 좌표로 반경 1km·관광지 타입을 불러도 경복궁이 없다(1건). 종로구 예전 지역 코드(areaCode=1·sigunguCode=23) 목록은 관광지 3건.
- 같은 종로구를 법정동 코드(lDongRegnCd=11·lDongSignguCd=110)로 부르면 관광지 147·문화시설 160·음식점 187건. 항목의 예전 코드(areacode·cat1~3) 칸이 비어 있고
  법정동 코드와 새 분류(lclsSystm1~3)만 채워져 있다.
그래서 시·군·구 목록을 법정동 코드로 통째로 받아 우리가 거리로 거르고, 분류도 새 분류표(246개)로 다시 짰다. 위 표의 '후'는 이 방식의 결과다.
어느 시·군·구인지는 상가정보 반경 조회로 약국의 시·군·구 코드를 세어 안다(상가정보의 5자리 코드 = 관광공사 법정동 시·도 2자리 + 시·군·구 3자리).

## 잃는 것 (숫자에 안 잡힘)

- **한국관광공사에 없는 가게**: 후보의 대부분이 관광공사 항목이라, 관광공사가 싣지 않은 동네 인기 가게는 후보에 없다. 모자란 종류만 상가정보로 채우는데,
  상가정보는 사업자 등록 상호라 간판과 다를 수 있고(표본에서 '이탈리안푸드'·'요하푸드' 같은 회사 이름이 식당으로 뽑혀 걸러 냄) 사진·영업시간·평판이 없다.
  고를 신호가 없어 '지점 표기 없는 곳 먼저, 가까운 순'이다. 표본에서 상가정보 장소는 서울 83곳 중 9곳, 서울 밖 44곳 중 0곳.
- **요청 활동의 폭**: 영화관·공연장은 관광공사 분류에 있는 곳만, 방탈출·보드게임·만화카페는 상가정보 '오락' 업종 중 상호에 그 낱말이 있는 곳만 찾는다.
  공방은 관광공사 공예체험·공방 분류와 상가정보 교육 업종 중 상호에 공방·도자·원데이 등이 든 곳만. 볼링·당구·탁구 등은 상가정보 업종으로 찾는다.
- **'후기 많은 순' 식당과 구 단위 '유명 맛집 TOP 5'**: 대신할 공공 자료가 없어 없앴다. 주변 식당은 '관광공사에 실린 곳 먼저, 가까운 순'.
- **민영 주차장**: 주차장은 공공데이터(공영 위주)만. 좌표가 없는 서울 노외 주차장 일부도 목록에서 빠진다. '네이버 지도에서 주차장 찾기' 링크로 잇는다.
- **둘러보기의 합친 목록**: 네이버 검색 16건을 합쳐 줄 세운 목록 대신, 공공 자료 목록 + 접어 둔 '네이버에서 더 찾기'(검색어 최대 4개, 검색어마다 5건, 받은 그대로).
  블록의 가게는 사진·상세·코스로 이어지지 않는다(네이버 지도 링크만).

## 호출량

측정한 호출 수(추천 1회 평균, 캐시가 빈 상태 → 같은 동네를 다른 사용자가 다시):

| API | 바꾸기 전 | 바꾼 뒤(처음 보는 동네) | 바꾼 뒤(다른 사용자, 같은 동네) |
|---|---|---|---|
| 네이버 검색(지역+블로그) | 서울 4.2 · 서울 밖 9.0 | 1.0(블로그 1건) | 1.0 |
| 네이버 지역 검색만 | 서울 3.2 · 서울 밖 8.0 | 0 | 0 |
| 한국관광공사(후보 목록) | 0 | 서울 6.3 · 서울 밖 5.8 | 0 (공용 캐시 7일) |
| 소상공인 상가정보 | 0 | 서울 1.5 · 서울 밖 1.7 | 0 (공용 캐시 7~30일) |

- 관광공사 후보 목록은 **시·군·구 하나에 관광 타입 5건**(관광지·문화시설·레포츠·쇼핑·음식점)이고 7일 동안 모든 사용자가 나눠 쓴다. 표본 18건이 22개 시·군·구에 걸쳐 110건이었다.
  전국 시·군·구 약 250곳이 일주일에 한 번씩 다 불려도 1,250건/주(하루 약 180건)다.
- 관광공사 영업 안내(detailIntro2)는 **코스·둘러보기에 보인 관광공사 장소마다 1건**, 7일 보관. 추천 1회에 서로 다른 장소 약 6곳, 둘러보기 한 쪽에 24곳.
- 둘러보기 기본 목록: 시·도와 활동마다 관광공사 1~2건(하루 보관), 동네 검색어가 있으면 이름 검색 1건 + 상가정보 1~2건. 다른 사용자는 0건.
  네이버 지역 검색은 '네이버에서 더 찾기'를 펼칠 때만 최대 4건(전에는 열 때마다 3~15건).
- 주변 식당 패널: 코스 장소마다 상가정보 1~2건(격자 캐시 7일), 관광공사는 추천 때 받은 목록을 다시 쓴다.
- 레저 패널: 관광공사 레포츠 목록(시·군·구마다 1건, 추천 때 받았으면 0건) + 상가정보 1~2건.
- 같은 업체 확인(인허가)은 그대로 배경에서 한 곳씩이지만, 식당·카페 후보가 공공 자료 장소가 되어 조회 대상이 늘었다(전에는 네이버 검색 장소라 조회하지 않음).

한도 판단(추정 포함)

| 하루 사용자(추천 1회 + 둘러보기 0.3회 가정) | 관광공사 새 호출(장소가 모두 처음일 때) | 개발계정 1,000건/일 |
|---|---|---|
| 10명 | 후보 목록 ≤50 + 영업 안내 ≤130 | 여유 |
| 50명 | 후보 목록 ≤150 + 영업 안내 ≤650 | 이 기능 상한(600)에 닿음. 축제·기존 장소 조회와 합치면 한도 근처 |
| 100명 | 영업 안내만 ≤1,300 | 넘음 |

- 그래서 이 기능의 관광공사 호출에 **하루 상한 600건**을 걸었다(`DATEMATE_TOUR_CANDIDATE_CALLS_PER_DAY`). 넘으면 그날은 새 동네의 관광공사 후보와 영업 안내 없이
  상가정보·카탈로그·이미 받아 둔 목록으로 추천한다(멈추지 않음). 축제와 기존 카탈로그 장소 조회 몫(약 400건)은 남는다.
- **개발계정으로는 하루 약 40~50명까지**가 안전선이다(같은 장소가 반복되면 더 버틴다 — 7일 보관). 그 이상을 기대하면 배포 전에
  공공데이터포털에서 한국관광공사 국문 관광정보 서비스의 **운영계정 전환(활용사례 등록) → 트래픽 증량**을 신청해야 한다(계정 소유자 작업, Q8).
- 상가정보·인허가 한도는 활용신청 화면에서 확인하지 못했다(미확인). 상가정보는 하루 상한 5,000건을 걸어 두었다(`DATEMATE_STORE_INFO_CALLS_PER_DAY`).
  추천 1회에 많아야 약 8건(시·군·구 알아내기 1 + 후보 묶음 ≤3 + 주변 식당 ≤5)이라 100명/일이면 ≤800건이다. 마이페이지의 일일 트래픽 값을 확인해 상한을 맞출 것.
- 제공자 지표(provider_metrics)와 시간당 예산은 이제 공공데이터포털을 기관별로 나눠 센다(apis.data.go.kr/B551011 관광공사, /B553077 상가정보, /1741000 인허가).

## 상가정보 분기 파일을 쓰는 방식(검토만)

- 지금은 API 로 충분하다: 응답 0.1~1.5초, 업종 조건으로 걸러 받을 수 있고, 격자 캐시로 같은 동네는 7일에 한 번만 부른다.
- 파일(https://www.data.go.kr/data/15083033/fileData.do, 시·도별 CSV 합계 수백 MB)을 받아 지역별 색인을 만들면: 한도·장애와 무관하고 전국 업소를 우리 기준(예: 오래된 가게)으로
  미리 고를 수 있다. 대신 분기마다 받아 다시 만드는 작업, 색인 저장소(컨테이너 이미지에는 넣기 어렵고 DB 표나 객체 저장소 필요), 시작 시간·메모리 부담이 생긴다.
- 권장: 상가정보 API 한도가 문제로 드러나거나(미확인) 상가정보 후보의 품질을 높일 신호(인허가일 등)를 붙이기로 할 때 다시 본다. 파일 내려받기는 로그인이 필요할 수 있다(사용자 할 일).
