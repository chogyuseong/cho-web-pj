# 코스 추천 대기 시간 측정과 개선 (2026-11-14)

운영(전주 한옥마을 카드 기본 조건)에서 처음 검색 20.5초(장소 검색 약 12초), 같은 조건 재검색 6.7초였다.
단계 경계만 보여서 12초 안의 구성을 몰랐다. 측정 장치를 넣고, 큰 구간부터 고치고, 같은 조건으로 다시 쟀다.

## 1. 측정 장치 (운영에도 남김)

- `app/perf_trace.py`: 추천 1회(`recommendation_service.generate`) 동안만 켜진다. 그 밖에서는 아무것도 하지 않는다.
- 추천 응답 `diagnostics.timing` (저장된 코스에는 넣지 않음)
  - `stages`: 준비·장소 검색·코스 구성·가격 확인의 시작 시각과 소요(ms). 단계 이름은 화면 진행 문구와 같다.
  - `spans`: 주요 구간(예: `research.course_search`, `course_search.blog_bodies`, `intent_discovery.lookups`,
    `compose.recommend`, `price.price_plans`, `save.plans`, `catalog.places`)의 횟수와 합계 ms.
  - `external`: 외부 호출 수(`calls`)·실패(`failed`), 기다린 시간의 합(`wait_ms_sum`), 실제로 차지한 시간(`wall_ms`, 겹친 구간은 한 번),
    가장 많이 겹친 수(`peak_parallel`). 호출 시간은 실제 요청 구간만이고, 요청 한도 확인·지표 기록의 DB 시간은 `db` 로 따로 센다.
    응답에는 호스트 이름이 드러나는 종류별 표(`by_kind`)와 예산 거절 수(`rejected`)를 싣지 않는다(아래 서버 기록에만).
  - `cache_hits`: course_blog, price, driving_route, intent_local 적중 수.
  - `db`: `store.connect()` 블록 수와 그 안의 시간 합, 단계별(`by_stage`).
- 서버 기록
  - 추천 이벤트(experience_events, kind=recommendation)의 `timing`: 단계별 ms, 외부 호출 합계(`calls`, `failed`, `rejected`,
    `wait_ms_sum`, `wall_ms`, `peak_parallel`), 캐시 적중, DB 합계·단계별.
  - 로그 `recommendation_timing status=… {…}`: 이벤트의 `timing` 에 `by_kind`(단계·호스트·종류별 수·실패·거절·ms·최대 ms)를 더한 것.
    종류는 고정 경로 이름만 쓴다: blog_search, local_search, blog_body, driving_route, geocode, reverse_geocode, image_search, llm, other.
    블로그 글 주소·검색어·키는 남기지 않는다(테스트 `test_summary_has_no_query_text_or_post_path`).
  - 작업 저장 뒤 로그 `recommendation_job_saved … persist_ms … stored_chars …`(저장한 작업 상태의 문자 수).
  - 시간 기록 계산이 실패하면 경고 로그(`recommendation_timing_failed`)만 남기고 timing 을 빼며, 추천 결과와 실패 경로의 원래 오류는 그대로다.
- 테스트: `tests/test_perf_trace.py`.

## 2. 측정 방법

- 로컬 Docker. 운영 이미지(Dockerfile) 그대로, 실제 키는 원본 `datemate/.env` 를 읽기 전용으로 붙여 앱이 읽게 했다
  (`--env-file` 은 따옴표로 감싼 값을 그대로 넘겨 네이버가 401 을 돌려줘서, 같은 파일을 `DATEMATE_ENV_FILE` 로 읽게 함. 값은 출력·복사하지 않음).
- 요청: 홈 카드 기본 조건(전주 한옥마을·부산 해운대·강릉 안목해변, 방문일 2026-11-15, 11:00–19:00, 2명, 10만 원, 도보 3곳).
  `POST /api/plan-jobs` 뒤 진행을 폴링하고, 완료 응답의 `diagnostics.timing` 을 읽었다.
- 캐시 빈 상태 = DB 를 새로 만든 직후 그 지역 첫 검색, 찬 상태 = 바로 이어서 같은 조건 다시 검색.
- 두 환경
  1) SQLite, CPU 제한 없음: DB 왕복이 거의 0 이라 운영과 크게 다르다(처음 검색 3.2초).
  2) **운영 근사**: PostgreSQL 17 컨테이너에 `tc netem delay 25ms`(DB 응답마다 25ms 지연), 앱 컨테이너 `--cpus=0.5`
     (Cloudflare standard-1 의 1/2 vCPU 가정), DB 풀 4(worker.js 와 같음).
     이 설정의 변경 전 값이 운영 기록과 거의 같았다: 처음 검색 19.9초(운영 20.5초), 장소 검색 13.0초(운영 약 12초),
     재검색 6.6초(운영 6.7초). 운영의 Neon 왕복 시간과 CPU 는 확인하지 못했으므로 이 근사는 **추정**이다.
- 외부 호출은 실제 네이버 API(지역 검색, 블로그 검색, 블로그 본문). 추천은 전후 합쳐 19회(키를 못 읽어 외부 호출이 401 로 끝난 1회 포함, 캐시 빈 상태 9회) 했다.

| 구간 | 시간 | 내용 |
|---|---:|---|
| 장소 검색 전체 | 12.96초 | DB 블록 92개(합계 24.6초, 스레드끼리 겹침), 외부 호출 14건(실제 차지 약 1.6초) |

| ㄴ 종류별 지역 검색(intent_discovery) | 8.66초 | 검색 8건 3.77초(네트워크 합 0.83초), 찾은 장소 저장 3.57초(장소마다 읽기 1번·쓰기 1번) |

- 확인한 것(코드와 측정): 외부 호출 1건마다 DB 쓰기 2번(시간당 제공자 예산 확인, 호출 지표 기록)이 따르고, PostgreSQL 에서는
  모든 쓰기가 전역 잠금(pg_advisory_xact_lock)을 거친다. 그래서 동시 4건으로 보낸 지역 검색도 실제로는 겹치는 수가 2를 넘지 않았다
  (`peak_parallel` 2). 지연 25ms 에서 읽기 1번 약 79ms, 쓰기 약 109ms, 예산 확인(범위 2개) 약 212ms 였다.
- 확인한 것: 블로그 본문 장소 대조가 장소 수 × 글 수만큼 본문(최대 6만 자)을 다시 정리해 CPU 를 썼다(0.5 CPU 에서 1.6~2.4초).
- 추정: 운영의 12초도 같은 구성(대부분 DB 왕복)이라는 것. 근사 환경의 값이 운영과 맞았을 뿐, 운영 DB 왕복 시간은 재지 못했다.

## 4. 적용한 개선 (결과는 바뀌지 않음)

1. 찾은 장소·검색 캐시를 한 번에 읽고 쓴다(`store.cached_many`, `store.cache_many`). 지역 검색 결과 저장, 종류별 '방금 검색함' 표시,
   가격 캐시가 대상. 이미 저장된 장소를 덮어쓰지 않는 규칙은 그대로.
2. 추천·코스 변경 작업 안의 외부 호출 지표(provider_metrics)는 작업이 끝날 때 한 번에 쓴다(합계는 같음).
3. 묶음 호출(지역 검색, 블로그 본문 5건, 가격 검색)의 시간당 제공자 예산을 한 번에 잡는다(`telemetry.prepaid`).
   차례로 잡는 것과 같은 수만 허락되고, 쓰지 않은 몫은 끝날 때 돌려준다. 허락되지 않은 몫은 전처럼 호출마다 확인해 거절된다.
   추천 1회 60건 상한, 기본 지역 검색 8건, 동시 4건, 블로그 본문 동시 5건, 가격 동시 3건은 그대로다.
4. 지역 검색 묶음의 '권한 없음' 표시 확인을 검색마다가 아니라 묶음마다 한 번.
5. 블로그 본문 장소 대조에서 글마다 본문을 한 번만 정리하고, 같은 장소 목록을 두 번 읽지 않는다.
6. 진행 폴링을 긴 폴링으로: 화면이 마지막으로 본 단계를 보내면(`GET /api/plan-jobs/{id}?wait=8&stage=…`) 서버가 그 단계가 바뀌거나
   끝나거나 취소될 때까지 최대 8초 기다렸다 답한다. 기다리는 동안 DB 를 읽지 않고 스레드도 잡지 않는다(메모리 상태를 0.1초마다 확인).
   다른 인스턴스의 작업이면 기다리지 않고, 기다려 주지 않는 서버(1초 안에 같은 단계로 답함)에는 화면이 전처럼 1초 쉰다.
   요청 수는 단계가 바뀔 때마다 1번(+8초마다 1번)으로 전(약 2초마다 1번)보다 줄어 Worker 의 IP 별 제한(600/60초)에 여유가 생긴다.

## 6. 결과가 바뀌지 않음을 확인한 방법

- `tests/test_recommendation_speed.py::test_same_input_and_cache_state_give_the_same_recommendation_as_before`:
  네이버 지역 검색·블로그 검색·본문·가격 검색을 고정 자료로 답하게 하고 실제 장소 모드 추천 전체(generate)를 전주·성수 조건으로
  캐시 빈 상태와 찬 상태에서 돌린다. 결과(3안 전체 JSON, 조건 확인, course_search, 가격 뒤 선택 진단, 외부 호출 종류·횟수)를
  변경 전 커밋 dd5b03d 의 코드로 만든 기준 파일 `tests/fixtures/recommendation_golden.json` 과 비교한다(시각 값만 뺌).
  기준 파일은 변경 전 코드에서 두 번 만들어 같음을 확인했다.
- 장소 대조는 변경 전 함수를 테스트에 그대로 옮겨 같은 입력의 결과가 같은지 본다.
- 예산 한 번에 잡기는 차례로 잡은 것과 DB 의 수가 같은지, 한도를 넘지 않는지, 남은 몫을 돌려주는지 본다.

## 7. 하지 않은 것과 이유

- 블로그 검색과 종류별 지역 검색을 동시에: 하지 않음. 지역 검색의 '부족한 종류' 계산은 장소 목록(이전에 찾은 장소 포함)을 읽고,
  블로그 장소 대조도 같은 목록을 읽는다. 동시에 돌리면 한쪽이 방금 저장한 장소를 다른 쪽이 읽을지가 실행마다 달라져 결과가 바뀔 수 있다.
  개선 뒤 두 구간은 각각 약 1.4초·1.0초라 얻을 것도 1초 안쪽이다.
- 블로그 본문을 결과 뒤로 미루기: 하지 않음. 본문은 장소 대조(블로그 점수 → 빔 탐색 정렬)와 광고·협찬 판단에 쓰여 코스를 바꾼다.
  사진·축제·장소별 후기는 원래 추천 경로에 없다(화면이 결과 뒤에 따로 부름).
- 가격 확인 전에 코스 먼저 보여 주기: 하지 않음. 가격 확인 뒤 필수 조건으로 안이 빠지고(filter_required), 예비 후보로 다시 채우고(_refill),
  3안을 다시 고르며 이름(option_purpose)도 다시 붙는다(select_options stage=after_pricing). 코스 저장(id)도 그 뒤라
  먼저 보인 카드가 바뀌거나 사라지고 고른 카드를 유지할 수 없다. 진행 문구의 후보 이름(preview)은 전처럼 보인다.
  가격 확인은 이제 빈 상태 약 2.1초, 찬 상태 약 1.2초다.
  → 이어진 작업에서 가격 확인이 3안을 바꾸는 빈도를 재고(기본 카드 조건에서 0건), 읽기 전용 '확정 전 후보' 카드와 확정 뒤 달라진 점 안내로 적용했다.
  가격 검색 연결 재사용과 함께 `price-stage-latency-2026-11-14.md` 에 적었다.
- 완료 응답 줄이기: 하지 않음. 약 105~110KB 이고 대부분이 코스 3개(코스마다 course_search 포함, 상세 화면이 씀)다.
  Cloudflare 가 브라우저로는 압축해 보내고, 긴 폴링으로 완료를 아는 지연이 줄어 효과가 작다.
- 코스 구성(빔 탐색, 0.5 CPU 에서 0.5~1.2초): 결과를 바꿀 위험이 있어 손대지 않았다.
- 그 밖에 남은 것: 작업 접수(POST /api/plan-jobs) 약 0.95초(요청 한도·세션·작업 기록 쓰기), 코스 저장 0.37초(코스마다 쓰기),
  검증 요약 0.23초(코스마다 같은 조회). 전역 쓰기 잠금 자체는 바꾸지 않았다.

## 8. 전과 달라지는 동작

- 지역 검색 묶음 도중 처음 401·403 을 받으면, 전에는 아직 시작하지 않은 검색이 '권한 없음' 표시를 보고 건너뛰었고 이제는 그 묶음 안에서는 보낸다
  (모두 '권한 없음'으로 끝나는 것은 같음. 묶음 상한 8건 안).
- 찾은 장소·새 가격은 검색 묶음이 끝난 뒤 저장한다. 도중에 처리 오류가 나면 전에는 일부가 남았고 이제는 남지 않는다.
- 작업 안의 외부 호출 지표는 작업이 끝날 때 쓴다. 작업 도중 프로세스가 죽으면 그 지표는 남지 않는다.
- 묶음 예산은 묶음을 시작한 시각의 시간 구간에 센다(정각을 걸치면 다음 시간 구간이 아니라 앞 구간에 셈).
- 묶음 예산을 미리 잡는 DB 쓰기가 실패하면 경고 로그(`provider_budget_prepay_failed`)를 남기고 전처럼 호출마다 확인한다.
  쓰지 않은 몫을 돌려주는 쓰기가 실패하면 경고 로그(`provider_budget_release_failed`)만 남기고 결과는 그대로 돌려준다
  (돌려주지 못한 몫은 그 시간 구간에 쓴 것으로 남아 예산을 덜 쓰는 쪽으로만 틀린다).

## 9. 운영에서 확인할 것

- 배포 뒤 전주 한옥마을 카드로 처음 검색 1번, 재검색 1번. 완료 응답의 `result.diagnostics.timing` 에서
  `stages`, `db.by_stage`, `external.peak_parallel`(4 근처면 동시 실행이 살아 있음)을 본다. 이 셋은 응답에 남는다.
  종류별 호출(`by_kind`: 호스트·종류별 수와 ms)과 예산 거절 수(`rejected`)는 응답에 없으므로 로그(`npx wrangler tail`)의
  `recommendation_timing` 한 줄에서 본다(거절 수는 추천 이벤트의 `timing.external.rejected` 에도 있음).
- 개발자 도구 네트워크에서 `/api/plan-jobs/…?wait=8&stage=…` 요청이 단계마다 1번 정도이고 단계 표시가 늦지 않은지.
- 운영의 Neon 왕복이 근사(25ms)보다 크면 남은 DB 블록(빈 상태 약 35개, 찬 상태 약 25개)의 비중이 커진다. 그때는 `db.by_stage` 로 다음 대상을 고른다.
- `scripts/operations_report.py` 의 제공자별 호출 수가 전처럼 쌓이는지(지표 묶어 쓰기).
