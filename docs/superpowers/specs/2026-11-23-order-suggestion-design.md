# 방문 순서 제안 — 설계 (2026-11-23, 짧은 설계. 사용자 '모든 권한 … 가장 완성도 있고 효과적인 것으로 판단')

## 왜
배포-이어가기.txt 7절에 남은 '순서 바꾸기'. 코스는 장소를 고른 순서대로 저장돼 A 골목 → B 골목 → A 골목처럼 되돌아가는 동선이 생길 수 있다
(datemate/docs/product-improvement-prompts-80.ko.md 14번 '두 장소 사이 되돌아가는 동선 줄이기').
그 문서의 완료 기준: 고정한 방문 순서·예약 시간을 깨는 단축안은 제외, 줄어든 분은 같은 산정 방식으로 비교.

## 접근 — 견준 것
- A. 사용자가 장소를 끌어 옮겨 순서를 직접 정하기: 버림. 어떤 순서가 영업시간·종료 시각을 지키는지 사용자가 시행착오로 찾아야 하고,
  끌어 옮기기 화면(터치·키보드 접근성)과 '안 되는 순서' 안내가 따로 필요하다.
- B. 코스를 열 때마다 자동으로 계산해 알려 주기: 버림. 순서 계산(최대 120가지)이 코스를 여는 모든 요청에 붙는다.
- **C. 접힌 상자를 펼치면 서버가 가장 많이 줄어드는 순서 하나를 제안(고름)**: 지각 확인과 같은 자리·같은 모양. 계산은 펼친 사람에게만.

## 정한 것 (app/order_suggestion.py)
- 비교: 지금 순서와 후보 순서를 모두 추정 구간(routes.candidate_routes — 외부 호출 없음)으로 다시 계산해 이동 시간 합을 견준다
  (장소로 가는 구간 + 귀가 + 축제로 가는 구간). 자동차 코스의 저장된 실제 길찾기 값은 비교에 쓰지 않는다 — 한쪽만 실제 값이면 줄어든 분이 가짜가 된다.
- 제자리: 고정한 장소(conditions.locked)·예약한 장소(reservation=True). 나머지끼리만 자리를 바꾼다.
- 후보 조건: planner.evaluate 통과(영업시간·마지막 입장·휴게·종료·구간 상한·예산·총 도보), 조건 확인에 '지키지 못함'이 새로 생기지 않음,
  축제 방문이 같은 자리 종류로 남음, 지금보다 늦게 끝나지 않음(조건이 느슨한 코스).
- 제안: 이동이 MIN_SAVING(5분) 이상 줄어드는 순서 가운데 가장 많이 줄어드는 하나. 없으면 까닭을 글로.
- 견주지 않는 코스(까닭 표시): 장소 1곳, 보관 기한이 지난 코스, 지각을 반영한 코스(지연이 장소 번호에 묶임),
  구간마다 수단을 바꾼 코스(수단 예외가 (출발, 도착) 짝에 묶여 순서를 바꾸면 사라짐), 움직일 수 있는 장소가 1곳 이하.
- API: `GET /api/plans/{id}/order-suggestion`(읽기 전용, 저장·외부 호출 없음), `POST /api/plans/{id}/reorder {order:[장소 id…]}` —
  서버가 다시 계산한 제안과 같을 때만 저장(다르면 409). 저장은 plan_changes.save_change(새 코스 id·parent — 되돌리기·이력 그대로,
  자동차 구간은 실제 길찾기 재확인 → 길찾기 재요청 제한·EXPENSIVE 목록에 reorder 추가). 두 경로 모두 만든 브라우저만(404).
- 화면: static/order-suggestion.js — 일정 위 「순서를 바꾸면 이동이 줄어들까?」 접힌 상자(지각 확인 아래). 펼치면 한 번 묻고
  '1. A → 2. C → 3. B 순서로 돌면 이동이 약 N분 줄어요' + 이동·끝나는 시각 변화 + [이 순서로 바꾸기]. 공유받은 코스·기한 지난 코스·1곳 코스에는 상자 없음.

## 하지 않는 것
- 순서를 직접 정하기, 여러 제안 보여 주기, 장소를 빼거나 바꾸는 것까지 섞은 제안, 지각을 반영한 코스·구간별 수단 코스에서의 제안.
- 추천 단계에서 순서를 미리 최적화하기(추천은 이미 여러 순서를 탐색한다 — 이 기능은 사용자가 장소를 바꾼 뒤 생긴 되돌아가는 동선을 겨냥한다).

## 되돌리기 영향
- DB 마이그레이션 없음. 새 경로 2개와 화면 스크립트 1개가 빠질 뿐, 순서를 바꿔 저장한 코스는 보통 코스와 모양이 같다.
